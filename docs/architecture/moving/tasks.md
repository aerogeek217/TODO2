### useUndoStore, UndoSnackbarAction, NoticeOptions — stores/undo-store.ts

Undo/redo stacks (max 50), push/undo/redo/clear; **a merge key** (`UndoEntry.mergeKey`): a push whose key is the newest entry's, with no group open, merges into it — the entry keeps its undo and its name and takes the push's redo, the redo stack is cleared, the snackbar shown again when asked (`push` returns the newest entry; `mergeTarget(key)` says beforehand which entry a push would merge into, `dropNewest(entry)` removes it when it is still the newest — a run typed back to its start); a compound step never merges (the layout's divider keys, the settings writes' `mergeKey`); an entry pushed with an `action` (`{ label, run }` — the checklist's Complete task) shows it as a button beside Undo, its own step when taken (`undo` / `redo` never reject: an entry whose undo or redo throws stays on its stack where it was — the next undo / redo tries it again — and the snackbar notice says `Couldn't undo: <description>` / `Couldn't redo: …` — or, for an `UndoRefused` (a reason the user can fix, e.g. a layout to open first), its message), `UndoGone` (its subject is gone for good — a task a purge deleted: the entry is dropped, never retried, with the error's message as a notice; a compound step skips its gone parts and is gone only when every part is), isPerformingUndoRedo guard, `runGroup(description, fn)` — every compound op (check-in replies) runs through it: one shared queue, so groups never overlap; `fn` gets the group's token, and when it settles (resolved or thrown) with the group still open the group ends as one entry named `description` (a string or a function read then) with the snackbar. `undo()` / `redo()` pressed while a `runGroup` group is open or queued wait for it (`groupsSettled`), so they take back or redo the whole compound step, never a part of it (cr31 L5). Under it `beginGroup()` → a token, `endGroup(token, …)` / `abortGroup(token, …)` (a token that isn't the open group's does nothing and warns); while a group is open, pushes neither trim the stack nor show a snackbar — `endGroup` trims and decides the snackbar; an unrelated undoable write landing inside a group's window is merged into it (accepted: groups take milliseconds). `abortGroup(token, description)` (a compound op that failed part-way: takes back the group's entries newest first, as an undo — no new entries pushed meanwhile — and leaves none; resolves `false` and keeps what it couldn't take back as one entry named `description`), snackbar state with auto-dismiss (a timer ends only the snackbar it was started for — `snackbarTimerId` must still be its own — so a replaced timer, or one left from before the store was reset, clears nothing); `notify(description)` shows a notice (no Undo, `NOTICE_SNACKBAR_MS`) without touching the stacks; an entry's optional `detail` is the snackbar's second line (shown for `NOTICE_SNACKBAR_MS`), passed through `undoable(…, detail)` / `optimistic`'s `undo.detail` (e.g. `markFollowedUp(ids, description, detail)`) `notify(description, { action?, onEnd? })`: a notice with an offer (Cancel's Restore) and what follows its end without the offer taken — it timed out, was dismissed or another snackbar (a push, a group's end, another notice) replaced it; `clear()` (a data replace) runs no `onEnd`.
