### useWorkspaceStore, settleLayoutWrites, isLayoutEditStep, EditUndoOptions, layoutEditChanged, LayoutEditSession, listsHeldByEdit — stores/workspace-store.ts (part 2)

The layout is one table (D26: `grid` tracks and `cells` over them, `models/workspace-layout`; the ops are `utils/workspace-layout-ops`). **Structural edits commit at once, each one undo step** (`edit` → `commit` → `writeLayout`; in the layout edit mode `edit` changes the draft instead, a step of the mode's own undo — below): `addWidget(kind, target, seed?)` (a `LayoutDropTarget`: a cell's strip, a split, an insert or an empty layout's first cell; `Added “<tab>”`), `moveTab(tabId, target)` (`Moved “<tab>”`), `movePanel(cellId, target)` (a whole cell; `Moved cell`), `removeWidget` (`Removed “<tab>”`: the ⋯'s Remove widget, a tab's × — `Remove <title>` —, a strip Number's ×; layout edit mode E4 — a lone widget's cell stays as an empty cell, `removeTabKeepCell`, no neighbour taking its space), `closeTab` (the same, but a cell it empties closes by the absorb rule), `closeCell` (the absorb rule: a neighbour takes its space, or it stays empty; `Closed cell` / `Closed cell “<tab>”` / `Closed cell (N tabs)`), `splitCell(cellId, side)` (a new empty cell on that side; returns its id; `Split cell`), `insertTrack(edge)` (a row / column at the layout's edge with one new empty cell; returns its id; `Inserted row` / `Inserted column`), `mergeCells(aId, bId)` (`false` unless they make a rectangle; `Merged cells`), a part-line `moveEdge(stretch, delta, opts, undo?)` (a divider's Alt-drag) (`Moved divider`, an undo step with no snackbar — `EditUndoOptions.quiet`: the table shows the move; `undo.mergeKey` — the divider's arrow keys pass `divider:<identity>` — makes a run of them one step), `patchTabConfig(tabId, kind, patch, description?)` (default `Changed “<tab>”`; the widget editors' Save names its own: `Edited number “<name>”`, `Edited breakdown “…”`), `changeTabKind(tabId, kind, seed?)` (`Changed “<tab>” to <Kind>`; a new Neglect map without `seed.neglectTagIds` colours by the `Project: …` tags of the tag store — `seedFor` → `utils/neglect-map.projectTagIds`). Each sets `working` and `saved` to the new layout (`modifiedAt` stamped) and writes it with `layoutRepository.putAndPrune` — the row and, in the same transaction, **the lists the layout owns that the row no longer names** (`storedListRefs`: list tabs and Numbers that follow a list) removed: deleted with their ranks (drafts dropped, `forgetLists`), or handed to another layout whose stored row names them (`OwnedListsRemoved.handedOver`, the list store reloaded). An edit whose result is the same structure (view state only) is written as view state, no step. A structural edit that would make the layout show a list it doesn't own — a list tab's list naming another layout's list or one with no owner (`foreignListRefs`: only lists the edit adds; a list that no longer exists is no one's) — is refused: nothing changes, `addWidget` returns `null`. **The undo step** (with the snackbar; `isLayoutEditStep` tells one) keeps an `EditRun` — the layout's id, its body before the first edit and after the last, each commit's removals and its own undo's: Undo restores the removed lists first (`layoutRepository.restoreLists`, newest commit's first; the list and rank stores reloaded), then commits the body as before, carrying the view state of the moment (`utils/workspace-layout-view.withViewStateOf`: sizes — `copySizes` —, row collapse where `sameTrackIn`, each cell's active tab where it still holds it, each tab's `viewState`) and its name and hue as they are now; Redo restores what that commit removed and commits the body after the edit the same way. Both run only while that layout is open (else `UndoRefused` `Open layout “<layout>” to undo: <step>.`, the entry staying) and drop the step with `UndoGone` `Can’t undo: <step> — its layout is gone.` once it is. Steps merged by a key share their run: the merged step's undo goes back to before the first and brings back every removal of the run. **Writes** are made in call order (the edits' `putAndPrune` and the view changes' `updateView` transactions run in the order created, so a view change made right after an edit lands on top of it, and an edit's write includes every view change made before it); a write that lands clears `writeFailed` and the layout's repair mark; one that fails sets `writeFailed` (only while that layout is still open) with the notice `Couldn't save layout "<name>".` and keeps what is on screen — the next commit of the layout writes all of it, and `retryWrite()` (the `Couldn't save · Retry` button) writes `saved` again (→ whether it is stored). A write of a layout that is gone (deleted just before the edit, or in another browser tab) writes nothing — `putAndPrune` → `null`: no row is made again — and says `Layout "<name>" was deleted: this change wasn't saved.`, with no `writeFailed` (nothing to retry). The lists a step whose own write failed stopped showing are deleted by that next write, which hands them to the step (`ListClaim`, `settleListClaims`; its own step keeps the rest), so its Undo — or Redo — brings them back. `load(id)` and `createLayout` / `duplicateLayout` first wait for the layout's writes still running, then retry a failed write (`readyToLeave`) and stay on the layout when it fails again (`Couldn't save layout "<name>". Retry before leaving it, or its last changes are lost.`). `settleLayoutWrites()` resolves once every commit's write (and what follows it) has run — a test hook, registered with `settleModuleWork`. **Repaired on read:** a layout `layoutRepository` repaired (`ReadLayout.fixes` — e.g. a retired widget kind dropped) opens without the bad parts, and the snackbar says `Repaired layout "<name>" — <fixes>. Your next change to it keeps the repair.` (logged too). Nothing writes the repair back on open: its view-state edits stay in memory (`updateView` skips it), `load` writes only `lastUsedAt` and `rename` only the name; its first structural edit writes the whole layout (repair and view state), dropping it from `repairedIds` — and removing the lists only the dropped parts named, as part of that edit's step (an undo of that first edit doesn't bring those back: the repaired table doesn't show them either). The page load's first `init()` (concurrent first calls share it) deletes the open layout's own lists its stored row doesn't show (`pruneOwnedLists`, not undoable — what an interrupted edit left). `init()` (idempotent: `layoutRepository.ensureDefault`, then opens the `activeLayoutId` layout, falling back to the most recently used — call after startup has loaded the sync file), `createLayout(name)` (stores an empty layout under the name, last, and opens it; `null` for a blank name or a failed write, with `Couldn't create layout "…".`), `load(id)` (never rejects: a failed read / write says `Couldn't open layout "<name>".` and keeps the open layout, cr31 L10; stamps `lastUsedAt` with a field patch), `duplicateLayout(name)` (Duplicate layout…: the open layout as committed stored as a new layout, last, and opened; the lists it shows copied for it — each as edited (its draft, a blank draft name keeping the saved name), with its ranks — in one transaction (`layoutRepository.insertWithListCopies`, the copy's tabs repointed), the list / rank stores reloaded; the source keeps its own; `null` for a blank name or a failed write, `Couldn't duplicate layout "<name>".`), `rename(id, name, hue?)` (only the name and hue; no undo step; a failed write keeps the old name and says so), `delete(id)` (refuses the last; never rejects — a failed delete says so and resolves false, and a failure after it committed (opening the next layout) drops its tab and says `Deleted layout "<name>", but couldn't open another. Reload the page.`, cr31 L10; deleting the open layout opens the most recently used; the layout's lists, ranks and drafts go with it — `deleteUnlessLast`, one transaction; not undoable, the confirm says so; its edits' undo steps then say the layout is gone). The removed Eisenhower's hidden list a v78 database may hold belongs to no layout and is never loaded: none of these touch it. **View-state edits** — `setActiveTab(tabId)`, `setTrackCollapsed(trackIds, collapsed)` (row tracks by id — one, or a cell's several in one write: Collapse row), `patchTabViewState(tabId, kind, patch)` — apply to `working` and `saved` and write the stored row at once (`layoutRepository.updateView`, read and written in one transaction; last write wins; `modifiedAt` untouched; no undo step); a failed view-state write is logged and kept for the session. **Sizes are view state:** `setTrackSizes(sizeById, opts?)` (batched, by track id, either axis: a weighted track's weight, a fixed one's px), `copyTrackSizes(from, axes, opts?)` (a drag's frame: an axis's sizes from a layout the drag computed, or the start's put back; a fit row's new height, its `fitPx`, too), `clearTrackFitPx(trackId)` (a fit row fits again) and `moveEdge(stretch, delta, opts)` while it only moves a whole line (its two tracks' sizes) change `working` and go onto `saved` and the stored row through the same path, an axis at a time (`copySizes`). They take `{ live: true }` for the frames of a divider drag — only `working` changes, no write per frame — and `endResize()`, which the divider calls once when the drag ends, saves what the frames changed (a keyboard step or double-click saves at once). New track / cell / tab ids are random and checked against the layout (`layoutIds`: tracks, cells and tabs). `refreshAllStores` clears the undo stack and re-runs `init()` once the store is hydrated. `load(id)` (cr34 H4, answer 26): the switch's read and writes are awaited first, then the change on screen is one synchronous step, with no view transition (nothing morphs — every cell is new — and a transition froze the page, losing presses, while the new layout mounted)
