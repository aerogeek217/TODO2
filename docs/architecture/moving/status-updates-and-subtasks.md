### useSubtaskStore, useSubtasks — stores/subtask-store.ts

Every task's checklist (cr28): `byTodo` (task id → subtasks in order — `utils/subtasks.compareSubtasks`), loaded once (`load` / `ensureLoaded`, from `WorkspacePage` and `useBuiltList`; reloaded by both `refreshAllStores` and `refreshTaskStores`). Writes save at once, each its own undo step: `add(todoId, title, { done? })` (last on the checklist; `Add subtask “…”`), `rename(id, title)`, `setDone(id, done)` (`Check “…”` / `Uncheck “…”` — the check that finishes an open task's checklist shows the snackbar with the detail `All N subtasks are done` and the action **Complete task**, which completes the task through `task-hooks.completeTask` only while it is still open), `move(id, index)` (within the task: only the rows whose place changed are written), `moveToTask(id, todoId)` (last on the other task's checklist), `remove(id)` (`Subtask removed`, with the snackbar), `resetDone(todoId)` (unchecks every done one — a recurring task's completion, inside the todo store's step). A title is stored as one trimmed line (`subtaskTitle`) — blank is refused, no write. **Never rejects:** a failed write is logged, the snackbar says `Couldn't add the subtask.` (… rename / check / move / remove) and it resolves as nothing written. **Every write is activity on its task:** it stamps the task's `modifiedAt` in the same transaction (`subtaskRepository`'s `TaskTouch`; a move stamps both tasks) and tells the todo store through `task-hooks.notifyTasksStamped`; its undo puts back each task's earlier stamp and its redo the one it wrote, only where the task still holds the other (`utils/task-stamps`). `addRows(rows)` (no undo step: a duplicate's copies, the new-task editor's pending rows, a note's indented lines — the task's create step covers them; the one choke point for whole rows, so each title goes through `subtaskTitle` as `add`'s does and a row left with none is not written — one such row would make every export, backup and the sync file unimportable), `restoreRows(rows)` / `forgetTodos(ids)` (the todo store's delete and its undo). `useSubtasks(todoId)` (a stable empty list for none). The load, `addRows`, `restoreRows` and `forgetTodos` are `task-child-rows`'

### useStatusUpdateStore, useStatusUpdates, newestStatusUpdate, NewStatusUpdate — stores/status-update-store.ts

Every task's status updates (cr27): `byTodo` (task id → entries, newest first — `utils/status-updates.compareStatusUpdates`), loaded once (`load` / `ensureLoaded`, from `WorkspacePage`; reloaded by both `refreshAllStores` and `refreshTaskStores`). Writes save at once, each its own undo step: `add(todoId, { date, text, followedUp? })` (`Add status update`), `addToMany(todoIds, entry, description)` (one step — the follow-up popover's bulk line), `update(id, { date?, text? })` (`Edit status update`; only the fields that change), `remove(id)` (`Status update removed`, with the snackbar). Text is stored as one trimmed line (`statusUpdateText`) — blank is refused, no write — and a day after today as today (`statusUpdateDay`). **Never rejects:** a failed write is logged, the snackbar says `Couldn't add the status update.` (… save / remove) and it resolves as nothing written (`undefined` / `[]` / `false`) — `services/mark-followed-up` reads that to abort its group. **An entry write is activity on its task:** an add, edit or removal stamps the task's `modifiedAt` in the same transaction (`statusUpdateRepository`'s `TaskTouch`), so updates keep a task from going stale and count for the Modified filter; its undo puts back the stamp the task had before, its redo the one it wrote, each only where the task still holds the other (`utils/task-stamps`); the todo store's copy follows through `task-hooks.onTasksStamped(listener)` (the todo store subscribes once for both entry stores and the assignments). A task delete's undo (`restoreRows`) and `addRows` stamp nothing. `addRows(rows)` (no undo step: a duplicate's copies, the new-task editor's pending entries, a task draft's — the task's create step covers them, its undo reads them from the database; each text through `statusUpdateText` as `add`'s, a row left with none not written), `restoreRows(rows)` / `forgetTodos(ids)` (the todo store's delete and its undo). `useStatusUpdates(todoId)` (the entries, a stable empty list for none), `newestStatusUpdate(todoId, byTodo?)` (also a selector). The load, `addRows`, `restoreRows` and `forgetTodos` are `task-child-rows`'
