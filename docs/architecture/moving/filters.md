### FilterCriteria, fixedAnchor, countActiveFilters, composeScreenFilter, criteriaToPredicate / predicateToCriteria — utils/filter-criteria.ts

`FilterCriteria`: personIds, statusIds, tags as null|Set of number ids; showCompleted, searchText, dates (`DateFilters`: a clause per date type — `deadline` = due date / `followup` = next follow-up / `lastFollowup` = last followed up / `completed` (a completed task's `completedAt`) / `created` / `modified` — each a range of `DateAnchor`s (with `includeNoDate` on the optional dates: due, next and last follow-up), Has a date or No date (the optional dates only; Completed is a range only); every clause must pass, `utils/filter-match.matchesDateMatch`; the screen filter's `setDateRange` sets the due-date range), markers — the Priority filter (`MarkersFilter | null`: a list of conditions, each a chip — the task is (or, `not`, isn't) any of its values, a marker or No priority, as a Status filter reads; all must hold, Urgent = effective urgent against `settings.urgentDueWithinDays`; `utils/markers.matchesMarkerClause`). `countActiveFilters` — one per control (people, status, tags, dates — however many types filter, they count once —, markers, show completed, search) and one for an expression (the screen filter's typed one); drives the mobile Filters badge. **The completion gate** (`admitsCompleted(f)`, cr24 P4): completed tasks pass when `showCompleted` is on **or a Completed date range is among the clauses or the expression's top-level `and` terms**; the range then keeps only the tasks completed in it (an open task has no completion date), so a "Done this week" list needs no Show completed. A Completed range inside an `or` (or a `not`) is a plain date clause and doesn't open the gate (the `or` would keep open tasks by its other terms). A recurring task's completed occurrence doesn't count: completing it advances the task to its next occurrence (still open, no `completedAt`), so a Completed range never lists it. `composeScreenFilter(screen, list)` — the two stages a task must both pass: narrowing clauses AND strictly (even on the same field — screen `@Alice` + list `@Bob` = tasks assigned to both), completion ORs into both (`admitsCompleted` of either side: a list's Completed range lets completed tasks past the screen stage too, and the chips' past the list's). The same gate decides what else counts completed tasks: the counter's total and `tasks` / `open tasks` words (`ScreenTaskCounts.withCompleted`), the filtered-tasks dialog's description, the calendar's hidden count; the glance widgets already match with completed tasks in (`statsFilter`) and count open ones, so a Completed range there leaves only the completion trend (Created vs completed). Converters between runtime `FilterCriteria` (Sets) and serializable `TodoPredicate` (arrays); `predicateToCriteria` reads the date clauses through `utils/date-filters.readDateFilters` (anchors via `readDateAnchor`; clauses that filter nothing left out), builds an id Set only from an array (anything else = no filter) and normalizes markers (`{}` → null) Optional `negate` — the "is not" switches of people / status / tags (`utils/filter-negation`); composing keeps each side's own switches (screen Status is not Waiting AND list Status is Waiting, Done → Done). Optional `expression` — a stored filter's expression (`TodoPredicate.expression`, the same `FilterExpr`, carried over as it is by both converters): a task must pass it on top of every clause (an expression's own clauses are empty); completion stays the root's (`admitsCompleted`: only a top-level Completed range opens it). A list's, a pane's or the check-in's filter may have one; the top bar's chips never do.
