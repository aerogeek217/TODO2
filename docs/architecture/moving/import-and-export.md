### auditData, AuditIssue, AuditSample — data/audit.ts

Scans the database (the data tables in one read transaction, `readDataTables`) and returns an `AuditReport`; each `AuditIssue` carries `table`, `description`, `count`, `ids` (or string `keys`), a `fix` (`'delete' | 'clear-field' | 'drop-store' | 'sanitize' | 'adopt-lists'`, `field` for clear-field) and up to 25 sample rows (highlighted fields + a note) for the detail popup (`AuditIssueDetailDialog`). Checks, in order: **unknown-table** (raw IDB store walk vs. `KNOWN_DB_TABLES` — e.g. a store left behind by an older schema; `drop-store` clears it via raw IDB), **unknown-row** (every row of every registry table except settings through `validateRow`; `delete`, except what `REPAIRS` keeps), **layouts** (a layout `validateRow` rejects is repaired, never deleted — `sanitize` through `pickLayout`, the sample naming what goes, e.g. `Cleanup: size reset, tab dropped`; so cleanup never deletes a layout, the active one included), **subtasks** (one whose title alone is too long is repaired — `sanitize`, the title as `subtaskTitle` cuts it, `Cleanup: title shortened`; one with no title is deleted), **sanitisable rows** (rows passing `validateRow` that still hold a part import would drop — `rowFixes`: a list's malformed people / status / tag / Priority (markers) filter or over-long text filter, a person's initials to normalise; `sanitize`), **unknown-setting** (`db.settings` keys failing `isKnownSettingKey`; delete by `keys`), settings rows with a recognized key but an **invalid value** (delete by `keys`), **sanitisable settings** (a readable value holding parts import would drop — `rowFixes('settings')`: keyboard shortcut overrides that are unknown, refused or clashing; `sanitize` by `keys`, the sample naming each), orphaned `todoPeople` / `todoTags` join rows, `listOrders` rows whose task or list is gone, `todoEvents` and `statusUpdates` rows whose task is gone (all `delete`, one helper; each sample names the missing targets), todos pointing at a deleted status (`clear-field statusId`), **lists that belong to no layout** — no owner, or a layout that is gone; never the retired Eisenhower's (`adopt-lists`: `layoutRepository.adoptUnownedLists` — the first layout that shows each, else a new layout `Recovered lists`; never deleted; sample note `no owner` / `owner layout N not in layouts`) —, and **orphan-recurrence-rule** — todos with `recurrenceRule` but no due date (`clear-field recurrenceRule`). There are no project / canvas / placement checks

### validateImportData, ValidateImportOptions, MAX_REPORTED_ROW_ERRORS, MAX_IMPORT_SIZE_BYTES — data/import-validation.ts

Runs *after* the upgrade pipeline (call `prepareImport`, not this, from import paths). Returns `{ ok, data, warnings }`. `options.requireFullDatabase` (default true — restores) requires `todos` and `settings` arrays (every full export carries both, possibly empty), else fails with "File is not a valid TODO2 database (missing tasks or settings)"; appends pass false (a task archive carries only task tables). Strict except that well-formed `settings` rows with unrecognized keys are dropped into `warnings`, and a `layouts` row its check rejects is **repaired** (`ImportTableRules.repairs` / `read`: `pickLayout`, the repair the database read and the audit use; the repaired row is what is stored, the fixes a warning `Fixed 1 layout: "Plain" (tab name shortened)` — one bad layout field no longer makes every backup and the sync file unreadable, cr34 H2; a row that is no object, or whose `id` doesn't read, is still refused); a failure lists *every* bad row (first `MAX_REPORTED_ROW_ERRORS` = 10, then a count; a single bad row keeps the one-line message). Only registry tables are read — other keys in the file (e.g. a stray `projects` array) are ignored. Schema validation covers all models, color sanitization, size limits (≤ 100k rows per table; task titles and notes, the workspace note and person / tag / status / list names have no length limit — the file-size cap bounds them — because an import must accept every value the app can store; an empty or non-string title / name is still rejected; caps kept where no writer can exceed them: `uid` 200, a status update's `text` 500 (non-empty; its `date` / `createdAt` date-like, `followedUp` optional — only `true` kept), initials 4 (then normalised: trimmed, uppercase, at most 3 — `utils/person.normalizeInitials` —, with a fix note), layout names 200, setting keys 100 / values 200), the setting key allowlist and per-key value checks (numeric ids, retention range, `weekStartsOn`, follow-up interval, `color.*` hex). Stored predicates must have the core predicate shape (`predicate-shape.checkPredicateShape`) and are rebuilt from known keys by `pickPredicate`: a malformed people / status / tag id filter, Priority (markers) filter or date clause is dropped and a text filter over 500 characters shortened, reported in `warnings` (`Fixed the filters of N lists: "…" (people filter dropped, …)`) instead of failing the import; likewise a person's initials are normalised with a warning (`Fixed N people: …`). Messages quote a name / title shortened to 60 characters; list definitions need a current sort / group literal and a `runtimeFilter.field` of person / status / tag (a removed value is rewritten by its schema step's transform before validation runs).

### validateImportData, ValidateImportOptions, MAX_REPORTED_ROW_ERRORS, MAX_IMPORT_SIZE_BYTES — data/import-validation.ts (part 2)

Every table's `id` is absent (the database numbers the row) or a whole number from 1, and ids are unique within a table (`duplicate id 4 (same as index 0)`), as `settings` keys are (`duplicate key "…"`) — never a raw `BulkError` from the restore. Todos require a non-empty `uid`, and the validator rejects duplicate uids across rows and two `listOrders` rows for the same list + task pair (the unique indexes would otherwise abort the restore)
