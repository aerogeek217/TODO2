# Models & Data Layer

Detail reference for `src/models/` (TypeScript interfaces) and `src/data/` (Dexie persistence). Load when touching schema, repositories, migrations, import/export, or model shapes.

## Models

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| TodoSortBy, TodoGroupBy, TODO_SORT_BY_VALUES, TODO_GROUP_BY_VALUES, isTodoSortBy, isTodoGroupBy, LIST_SORT_VALUES, LIST_GROUP_VALUES | models/todo-sort-group.ts | Unified sort + group dimensions for every list surface (list definitions and the list widgets that show them), stored on `ListDefinition.sort` / `.grouping` as flat literals. `TodoSortBy` is a 7-literal union (`'manual' \| 'name' \| 'deadline' \| 'followup' \| 'created' \| 'people' \| 'status'`); `TodoGroupBy` is a 6-literal union (`'none' \| 'deadline' \| 'followup' \| 'people' \| 'status' \| 'tag'`); `'deadline'` is the due date (UI label "Due"). `ListSortBy` / `ListItemSortBy` / `ListGroupBy` (`models/app-view.ts`) are type aliases over these unions. `LIST_SORT_VALUES` / `LIST_GROUP_VALUES` are per-surface subset arrays (no production consumer — the list UIs offer `utils/list-options` choices). `isTodoSortBy` / `isTodoGroupBy` back import validation and `buildListSections`' guard (an unknown stored grouping reads as `'none'`). | TodoItem | models/todo-item.ts | Core todo entry (id optional, pre-insert); optional `notes`, `progress`, `statusId`, `dueDate` (UI "Due"; a day; the recurrence anchor), `recurrenceRule`. `uid: string` (stable identity across export / import — unique Dexie index `&uid`; minted by `todoRepository.insert` via `newTodoUid` unless passed; duplicate detection keys on it, never on `id`) and `completedAt?: Date` (set on completion, cleared on reopen — the retention purge clock). `NewTodoItem` = insert payload with optional `uid`. Follow-up: `lastFollowupAt?: Date` (exact moment from "Followed up", or a day when edited; never in the future) and `nextFollowupAt?: Date` (a day at local midnight; new tasks get today + `settings.followupDefaultInterval`; no index — filtered in memory). `focus?: boolean` — in focus (only `true` is stored; taking a task out deletes the key; no index). Read by the Focus marker and the Markers filter. `urgent?: boolean` / `important?: boolean` — flags (only `true` stored; no index). A task is also urgent when its due date is within `settings.urgentDueWithinDays` (`utils/urgency.isEffectivelyUrgent`) — that never sets the flag. No project or canvas fields (removed in v60; a former project is a `Project: <name>` tag) |
| PersistedTodoItem | models/todo-item.ts | TodoItem with guaranteed id (post-insert) |
| RecurrenceRule | models/recurrence.ts | Recurrence pattern: type (daily/weekly/biweekly/monthly/quarterly/yearly), optional originalDayOfMonth to prevent drift. **The rule requires a due date** — `recurrenceAnchor` (services/recurrence.ts) returns null without a `dueDate`, and `advanceRecurring` short-circuits, so a rule on a task without one is dead weight. Enforced on write by `todoRepository.update` / `bulkUpdate`: every merged row that carries `recurrenceRule` without a due date has the rule dropped before persistence — `bulkSetDeadline(ids, null)` silently drops the rule the same way `TaskEditPopup` does on the UX layer. Legacy rows on existing databases are caught by the matching `auditData` orphan-recurrence-rule pass |
| ListDefinition, PersistedListDefinition, ListMembership, ListSort, ListGrouping, RuntimeFilterSpec, RuntimeFilterField | models/list-definition.ts | Saved list definition: name, sortOrder, `pinnedToDashboard`, membership (only `custom` — carries a `TodoPredicate`), `sort: TodoSortBy` and `grouping: TodoGroupBy` (flat literals), optional `maxTasks?: number` + `limitMode?: 'hard' \| 'scroll'` (visible-task cap; `'hard'` (default) truncates the list widget's sections, `'scroll'` keeps every task). Optional `runtimeFilter?: { field: 'person' \| 'status' \| 'tag'; label? }` ("Prompt" in the UI) declares a per-render picker merged into the predicate at interpret time via `applyRuntimeFilter` in `services/dashboard-lists.ts`. Only the field is part of the definition: the picks (OR-combined id arrays) are temporary — workspace list tabs keep them in `list-widget-store` (never saved) and pass them to `buildDashboardLists`. v60 turned stored `'project'` prompts into `'tag'` |
| TodoPredicate, DateAnchor, RelativeDateToken, RELATIVE_DATE_TOKENS, MarkerKey, MARKER_KEYS, MarkerSet, MarkersFilter, HOT_MARKERS | models/filter-predicate.ts | Serializable predicate DSL mirroring live filter fields (number arrays + `DateAnchor`s — no Sets, no Dates). Stored inside `ListMembership.custom`; runtime converts to `FilterCriteria` via `predicateToCriteria` at evaluation time. Clauses: `showCompleted`, `personIds` (plain membership over a todo's assigned people, `0` = unassigned sentinel; there is no person filter mode), `statusIds`, `tags` (tag ids, OR; optional on read), `searchText`, `dateField` + `dateRangeStart` / `dateRangeEnd` (`fixed` ISO / `relative` token / `offset` days) + `dateRangeIncludeNoDate`, tri-state `hasDeadline`, `hasFollowup?` (optional on read), and `markers?: MarkersFilter \| null` — `'hot'` (the task must be hot by the Settings Hot rule, `utils/hot`) or a `MarkerSet` `{ urgent?, important?, focus? }` with only `true` values, every one required (strict AND; Urgent = effective urgent); absent / null / `{}` = no filter. `MarkerSet` is also one Hot rule line and the flags a filter seeds on new tasks. No project clause (v60 folded `projectIds` into `tags`) |
| Person | models/person.ts | Assignable person with name + initials + optional `color?: string` (hex; stored inline, not indexed; validated on import as an optional CSS color). Avatars / chips / people group headers fill with `person.color`, avatars falling back to `NEUTRAL_PERSON_COLOR` (constants.ts) when unset. Edited in Settings (`PeopleEditor` color input). An `Org: <name>` person (created by the v55 merge) is an ordinary person — the prefix is only a naming convention |

| PersistedStatus | models/status.ts | Status with guaranteed id (post-insert) |
| Tag | models/tag.ts | First-class normalized tag: `{id?: number, name: string, color: string}`. A `Project: <name>` tag (created by the v60 project merge) is an ordinary tag — the prefix is only a naming convention |
| PersistedTag | models/tag.ts | Tag with guaranteed id (post-insert) |

| TodoEvent, PersistedTodoEvent, TodoEventType | models/todo-event.ts | Append-only history log entry; the dashboard trend reads `created` / `completed` / `reopened` (`services/stats/trend.ts`), and the rows travel with exports and task archives. One row per tracked-field mutation on a todo (`dueDate` / `statusId` / `isCompleted`) plus a `created` event at insert time. `TodoEventType ∈ {'created' \| 'scheduled' \| 'deadline' \| 'status' \| 'completed' \| 'reopened'}` — `'scheduled'` is history only (the scheduled date was removed in v53; no new ones are written, old ones are kept). `fromValue` / `toValue` encoding: ISO date string for dates (old `'scheduled'` rows may hold `'fuzzy:<token>'`) / numeric `statusId` for status / null for unset / null on both sides for `created` / `completed` / `reopened` (the type carries the meaning). | ListOrder, PersistedListOrder | models/list-order.ts | A task's place in a list's manual order: `{id?, listDefinitionId, todoId, rank}` — one row per placed (list, task) pair; fractional ranks, read only while the list's sort is `manual`. ## Data Layer

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| Todo2Database | data/database.ts | Dexie DB class with schema versioning. Tables: `todos` (`++id, isCompleted, dueDate, sortOrder, statusId, &uid`), `people`, `settings`, `todoPeople`, `backups`, `statuses`, `listDefinitions`, `notes` (`++id, modifiedAt`), `tags`, `todoTags`, `todoEvents`, `layouts`, `listOrders`. The `.version(N).stores(…)` chain stays so Dexie can walk to the current schema. Upgrade bodies before v49 are empty (legacy translators were stripped once `OLDEST_SUPPORTED_DB_VERSION` was pinned). **v49** is the one hand-written upgrade: an idempotent backfill walks `todos` rows where `scheduledDate?.kind === 'fuzzy'` and `setAt` is unset, then stamps `setAt` from the most recent `'scheduled'` `todoEvents` timestamp (fallback `todo.createdAt`). From v50 on every version wires its `.upgrade()` as `(tx) => applySchemaUpgradeInTx(tx, N)` so the live DB and imported files run the same registry transform. **v50** `upgradeV50` revives string-typed Date fields; **v51** `upgradeV51` backfills `uid` + `completedAt` and adds the `&uid` index; **v52** `upgradeV52` drops the `floatingHorizons` / `floatingScoreboard` / `floatingSnoozeGraveyard` tables (declared `null`) and cleans the matching settings; **v53** `upgradeV53` removes `scheduledDate` (no store change); **v54** `upgradeV54` removes hide-by-status (no store change); **v55** `upgradeV55` merges orgs into people and drops the `orgs` / `todoOrgs` / `personOrgs` tables (declared `null`); **v56** `upgradeV56` adds the `layouts` table (`++id`) and seeds the Default layout; **v57** `upgradeV57` strips list `favorited` and saved list-tab prompt picks (no store change); **v58** adds the `listOrders` table (`++id, listDefinitionId, todoId, &[listDefinitionId+todoId]`) — no registry entry (an empty table = every task unranked); **v59** `upgradeV59` turns the taskboard into Focus and drops `taskboards` / `floatingTaskboards`; **v60** `upgradeV60` turns projects into tags and drops `projects` / `canvases` / `listInsets` / `floatingCalendars` / `floatingNotes` / `floatingStatus` (declared `null`), restating `todos` without the `projectId` / `canvasId` indexes and `notes` without its `canvasId` index; **v61** `upgradeV61` rewrites stored list predicates from `focus` to `markers` (no store change). The latest version is declared with `CURRENT_DB_VERSION` (not a literal) — when bumping, turn the previous one into its literal first |

| SETTING_KEYS, ALL_SETTING_KEYS, SettingKey | data/setting-keys.ts | The persisted settings keys: `themeMode`, `defaultStatusId`, `quickStatusId`, `seededAssignedStatusId`, `completedRetentionDays`, `weekStartsOn`, `maxTags`, `followupDefaultInterval`, `urgentDueWithinDays` (`off` or a day count 0–365; validated on import), `hotRule` (JSON array of lines, each an object of markers set to `true`, ≥ 1 line, ≥ 1 marker per line, unknown keys rejected on import; import stores it normalized with duplicate lines collapsed), `activeLayoutId` (plus the structured `color.<theme>.<key>` rows, not enumerated). `ALL_SETTING_KEYS` is the import allowlist |

| todoRepository | data/todo-repository.ts | Full CRUD + queries for TodoItem, bulkUpdate (batched transaction), bulkDelete (atomic multi-delete). `delete` / `bulkDelete` clear the todo's `todoPeople` / `todoTags` / `todoEvents` rows and its `listOrders` ranks in the same transaction as the row drop. **Recurrence-orphan invariant:** `update(todo)` and `bulkUpdate(mutations)` merge the change against the existing row and run a private `dropOrphanedRule` helper — when the merged row has `recurrenceRule` but `hasRecurrenceAnchor` (data/recurrence-anchor.ts) is false, the rule is dropped before the write, so every caller converges on `TaskEditPopup`'s silent-clear semantic. **Completion clock:** `insert` / `update` / `complete(id, completed, completedAt?)` / `bulkUpdate` keep `completedAt` in step with `isCompleted` via `resolveCompletedAt` (utils/completed-at.ts): newly completed → now (or the explicit value — undo passes the original back), still completed → kept, reopened → removed. `insert` mints `uid`. `getByIds(ids)` / `getByUids(uids)` (DB reads for the purge prompt / `purgeCompleted`, which must not depend on what the store has loaded).
