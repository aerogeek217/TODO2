## The database and its versions

`Todo2Database` (`data/database.ts`) is the Dexie class. Its stores are declared once, at the schema floor, and each schema step after the floor declares only what it changes.

### Tables

`todos`, `people`, `settings`, `todoPeople`, `backups`, `statuses`, `listDefinitions`, `notes`, `tags`, `todoTags`, `todoEvents`, `statusUpdates`, `subtasks`, `layouts` and `listOrders`. Among their indexes:

- `todos`: `++id, isCompleted, dueDate, sortOrder, statusId, &uid`
- `notes`: `++id, modifiedAt`
- `statusUpdates`: `++id, todoId, date`
- `subtasks`: `++id, todoId`
- `listOrders`: `++id, listDefinitionId, todoId, &[listDefinitionId+todoId]`

### The floor's declaration

- One declaration holds the floor's whole store layout: `this.version(OLDEST_SUPPORTED_DB_VERSION).stores(FLOOR_STORES).upgrade(refuseBelowFloor)`.
- Dexie 4 needs no declaration of the versions before it. Opening a database, it diffs the stores it finds against the declared ones and runs only the upgrades of versions above the database's own. So the floor's `.upgrade()` runs exactly for a database below the floor.
- `refuseBelowFloor` throws `DatabaseTooOldError`. That aborts the version-change transaction: IndexedDB rolls back every store and index change, and the database keeps its old version, stores and rows.

### A schema step's declaration

A schema step N declares `this.version(N).stores({ …only what N changes })` after the floor's declaration. Its `.upgrade()` is `(tx) => applySchemaUpgradeInTx(tx, N)`, the same registry transform an import of an older file runs, and the step raises `CURRENT_DB_VERSION`. v88, v89 and v90 are three: `this.version(N).stores({})`, no store changed.

## The schema upgrades

`data/schema-upgrades.ts` is the permanent upgrade pipeline: one transform per schema version, run both by the Dexie upgrade of the browser's database and by the import of a file at or above the floor ([import and export](features/import-and-export.md)).

### The pipeline

- `SCHEMA_UPGRADES` is a `ReadonlyMap<number, SchemaUpgrade>` from a target version to its transform, `(data: DataSet) => DataSet`. A `DataSet` is table name → plain rows (`DataRow`). It holds v88's, v89's and v90's.
- A transform is pure and immutable and takes the whole dataset. It tolerates missing tables (a partial dataset such as a task archive) and returns the same array reference for a table it leaves alone.
- `upgradeDataSet(data, from, to, registry?)` applies the entries `from+1 … to` in order. A version without an entry is the identity. The optional registry is the tests' seam.
- `applySchemaUpgradeInTx(tx, N)` is the Dexie side. It reads every store in `tx.idbtrans.objectStoreNames` but `backups` into a `DataSet`, applies entry N, and clears and bulk-adds only the tables whose array reference changed.
- Dexie 4 runs a version step in this order: N's new tables exist, empty, when the callback runs; the tables N declares `null` still exist during it and are deleted right after. So a step **transforms and drops a table in the same version**, and its transform also drops the key from its output.
- `test/data/import-pipeline-upgrade.test.ts` keeps the pipeline exercised with a synthetic next-version step: the file import and the Dexie upgrade agree.

### What a schema step adds

The header of `schema-upgrades.ts` lists it:

- its transform, `data/upgrades/v<N>-<what>.ts`, registered as `[N, upgradeV<N>]`
- the `this.version(N)` declaration
- the `import-validation` `check*` / `pick*` changes
- its tests: the transform's own, the export → restore round trip, and "v(N-1) reader refuses vN"

### What each upgrade does

- **v88**: every List wall tab (`listwall`) becomes a List board showing its layout's lists, `{ kind: 'shortcuts', config: { source: 'layout' } }`. Its id, name, icon and every other field are kept, and so are its place in its cell and the cell's active tab (`data/upgrades/v88`, `test/data/v88-upgrade.test.ts`). Nothing else changes. A v87 build refuses v88 data (`v87-reader-refuses-v88.test.ts`): its repair would drop the board's `source`.
- **v89**: a task's plan state is a planned day or none. Every task loses `unplanned`; its `doDate` is kept (a task held in Unplanned goes back to its own day, the Unplanned filter, or out of the Planner). Planned's `held` clause goes from every stored predicate — a list's, a layout tab's config at any depth (a Planner's Unplanned filter, a Number's filter), the `checkinTaskFilter` setting's JSON: `dates.planned: { match: 'held' }` is deleted; in an expression a `held` atom leaves its `and` / `or` (one item left becomes that item, none left takes the node too), a `not` of it goes, and an expression left empty is deleted, so `planned any or unplanned` reads `planned any`. A row with nothing to change comes back as the same object (`data/upgrades/v89`, `test/data/v89-upgrade.test.ts`). A v88 file imported goes through it and comes in with no warning. The import repair drops a stray `unplanned` silently, as any unknown key, and reads a `held` clause as malformed: a graphical one is dropped with a fix, an expression holding one is dropped (`expression dropped`). A v88 build refuses v89 data by its version stamp (`v88-reader-refuses-v89.test.ts`).
- **v90**: the Pivot goes, and every Number lives in a Numbers widget (kind `numbers`, `config: { items }`). In every layout each `pivot` tab goes first: a cell whose active tab went shows the tab before it (else the one after), and a cell left without tabs closes by the absorb rule, the grid lines nothing uses then going (`data/upgrades/v90/layout-tabs`). Then a cell whose tabs are all Number tabs (`number`; one or more) becomes one Numbers widget holding them in strip order, and its active tab is that widget. In a cell mixing Numbers with other kinds each Number becomes a Numbers widget of one in its place, and the active tab follows it. Each Number keeps its id, config and icon as its item's; a tab name a Number stored apart from its config names it only when its config has none. A new widget's id is `n-` + its first Number's id, numbered while taken. The Numbers leave tracks, `fitPx` and collapse untouched. A layout with neither a Pivot nor a Number tab comes back as the same object (`data/upgrades/v90`, `test/data/v90-upgrade.test.ts`). It runs on the browser's database (`version(90)`) and on every file read through the import pipeline: an import, a backup restore, a sync file's load. A v89 build refuses v90 data by its version stamp (`v89-reader-refuses-v90.test.ts`): its repair would drop every Numbers widget.

## The layout check and repair

`data/layout-shape.ts` checks and repairs the table of a `layouts` row: its `grid` and its `cells`.

- `checkLayoutBody` returns `true` or the path of the first bad field.
- `pickLayoutBody` rebuilds the body with only model keys and returns `{ grid, cells, fixes }`. It also turns a body the check rejects into a valid one, naming each repair in `fixes`.
- `checkLayout` / `pickLayout` in `import-validation.ts` use them. So the audit repairs a stored layout instead of deleting it, the read of a stored layout repairs it ([workspace layout](features/workspace-layout.md)), and an import repairs it with a warning ([import and export](features/import-and-export.md)).

### The table

`checkLayoutBody` names a path such as `grid.columns[0].weight`, `cells[2].area` or `cells[0].tabs[0].kind`.

- Every track has an id and a size: a positive `weight`, or `px`. Only a row track may be `collapsed` or hold a `fitPx`.
- Every cell has an id, an `area` of whole track indices with spans ≥ 1, and a strip of valid tabs. An empty strip is an empty cell.
- Ids are unique across tracks, cells and tabs, at most 100 characters long, and never the name of an `Object.prototype` member (`isId`: `constructor`, `__proto__`, …), because ids key plain records.
- The cells tile the grid exactly (`workspace-grid.validateTiling`), and every inner line is some cell's edge.
- An empty layout has no tracks and no cells.
- The number of tracks, cells or tabs isn't checked. Past `LAYOUT_PART_LIMIT` (1,000) cells, or tracks on an axis, the check also leaves the table's tiling and lines unchecked: the repair restacks it, and the tiling check is quadratic.

### Tabs, by kind

A tab has an id, a kind, a `config` object and, when present, a `viewState` object. The check refuses a tab whose kind `isWidgetKind` doesn't know, and the repair drops it. A tab's own name and icon are in the `withTabLabel` row above; the Planner's, the List board's and Work clusters' settings are in their model rows.

A list tab (`lens`):

- `config.listDefinitionId` is a finite number when present. A deleted list's id is kept; the tab says so.
- `viewState.detailsWidth` is a finite number ≥ 0. List tabs (`ROWS_KINDS`) are the tabs that keep a details width.
- `viewState.zoom` is one of the levels. The repair keeps a level and drops any other, a `tab or cell settings reset` fix: the tab opens at the Settings default. The details width is kept.

A calendar:

- Its `dateTypes` are booleans, and all may be false. `plan` may be absent, from before calendars showed plans: it reads `true`, in the repair and in the database read alike, and is no fix.
- Its `viewState.titles` is a boolean when present.

A Neglect map:

- The check wants `colourBy` of a known kind (`tags` with a list of finite numbers, `people`, `none`) and `hiddenStatusIds` absent or a list of finite numbers.
- The repair (`pickNeglectConfig`) keeps only those keys, a repeated id once, and no view state. A bad `colourBy` becomes `none`, a tag list keeping its numeric ids; a bad `hiddenStatusIds` keeps its numbers, or goes when it isn't a list. Each is a `tab or cell settings reset` fix. A stored `untouchedDays` is dropped quietly, as any stray key.

A Numbers widget:

- The check wants `config.items`, a list of at least one Number, each an object with an id fresh in the layout's id space (`config.items.<i>.id`) and an optional icon that reads (`.icon`). A widget left with no Number is dropped (`tab dropped`), a Number with a bad or repeated id, or not an object, dropped (`tab or cell settings reset`); its own name and icon are a tab's. The layout keeps `LAYOUT_PART_LIMIT` Numbers (`Number past the limit of 1,000 dropped`), and `layoutPartCount` counts them.

A Number (an item; its paths under `config.items.<i>`):

- The check wants its scalar fields as `numberConfigProblem(raw)` has them.
 It names the first bad one. A shape field of another shape (a stray), or the shape's own field missing or unreadable, is among them.
- The check wants each of its predicates to be a stored predicate that `pickPredicate` reads unchanged: its `filter`, a share's `of` and each group item's `filter`, named `config.of` and `config.items.<i>.filter`. `config.filter` names a filter the read would change, and `config.filter.<field>` a missing core field.
- The repair is `pickNumberConfig(raw, filter, readPredicate)` over `pickPredicate`. A filter that isn't an object is no filter: every open task. What it resets is a `tab or cell settings reset` fix.
- A bad field is reset to its default: the name `Number`, Auto, a count, never lit (0 when above / below lacks a threshold), against yesterday. A bad color, lit or unlit, and a bad breakdown are dropped.
- The shape's field is repaired too (`pickShapeField`): a stray is dropped; `oldestBy` becomes the last follow-up; a goal becomes at least 10 a week, though `pickNumberGoal` keeps a bound that reads; a group keeps its first 6 items; a list ref is `{ listDefinitionId }` or none, picked later; an absent `of` is every open task.
- A group item is a name (a bad one: `Number`), a picked filter and a hex color or none. A group with no item at all gets one `Open` count of every open task.
- So a `{ metric }` config that v78 left unconverted reads as a new Number named `Number`.

Created vs completed (`trend`):

- The check wants a known `range` and, when present, a `name` ≤ 80, a known `show` and a `filter` read as a chart's (`trendConfigProblem`, then `checkChartFilter`).
- The repair (`pickTrendConfig`) resets a bad range to 14 days and drops a bad optional field, each a `tab or cell settings reset` fix. An absent optional field stays absent, with no fix. A stray key is dropped. It has no view state.

A Breakdown (`breakdown`):

- The check wants the scalar fields as `breakdownConfigProblem` has them, its view state's sorts (`breakdownViewProblem`) and the filter as a Number's.
- The repair resets a bad field to its default and drops a bad optional one, as `pickBreakdownConfig` / `pickBreakdownView` do. A missing filter is no filter, every open task, and a fix.
- A Breakdown column's bad or repeated `id` gets a new one. Its `age: { yellowAfterDays }` with a bad threshold gets 14, and an `age` that isn't an object is dropped. Each is a fix.
- A `badges` or `checkins` left in a Breakdown's config is dropped, a fix. v79 wrote `columns` on every stored Breakdown from its `badges` and the data's Settings ranges, and removed both.
- A glance tab keeps no view state but a Breakdown's sorts.

A Review tab:

- It has no settings. Its config, an object, passes the check whatever it holds. Its view state's `sort` must be a sort.
- The repair writes `config: {}`. A config key (`by`, `pick`), a view-state key other than `sort` (`currentId`, `skipped`) and a sort that doesn't read are each dropped as a fix. v79 removed those keys from stored layouts.

### What the repair does to the table

For a body that passes the check, `pickLayoutBody` changes little:

- A stale `activeTabId` is dropped, so the first tab is active.
- A calendar offset is clamped.
- A details width is rounded and capped at 4000. A bad one is dropped.
- The cells come back in reading order.
- A tab's stored `viewState.ignoreLens` is dropped quietly before its view state is read (`withoutLensSwitch`). That is never a fix. v81 removed the key from stored layouts.

For a body the check rejects, `fixes` names each repair: `2 tabs dropped`, `size reset`, `grid line merged`, ….

- A track, cell or tab that isn't an object, or has a bad or repeated id, is dropped.
- A bad size is reset, a weight to the axis's average. A size is bad when it isn't a finite positive number or is past `LAYOUT_SIZE_MAX` (1e6, so no sum of sizes is `Infinity`).
- Bad tab settings fall back to the kind's defaults.
- A name past its limit is **cut** to it, never reset (`tab name shortened`; `glance-widgets.readStoredName`, `PickedConfig.shortened`). The limit is 200 for a tab's own name and 80 for a Number's (its item's), a Breakdown's or Created vs completed's `config.name` (`NUMBER_NAME_MAX` / `CHART_NAME_MAX`, what the editors' name fields take).
- A bad `activeTabId` or `collapsed` is dropped.
- A cell whose every tab was dropped closes (`closeCell`): a neighbor takes its space, or it stays empty. They all stay empty when closing them would cost past `LAYOUT_CLOSE_WORK_MAX`: cells emptied × cells × lines over 2 million.
- An inner line no cell's edge lies on goes (`normalizeGrid`).
- When the cells don't tile the grid (a bad area, a dropped track or cell), the grid is rebuilt: every cell kept, in its old reading order, stacked in one column (`cells restacked in one column`).
- Past `LAYOUT_PART_LIMIT`, the repair keeps the first 1,000 column tracks, row tracks, cells and tabs, each counted over the whole layout. The rest are dropped with a fix (`tracks past the limit of 1,000 dropped`): an import warning, and a stored layout repaired at read.

### Kinds and keys the model does not have

- A tab of a retired kind is an unknown kind and dropped like one, and a cell it leaves without tabs closes. The retired kinds are `dashboard` (v77 converted every one); `followup`, `next7`, `stale`, `recent`, `changes`, `today`, `eisenhowerSummary`, `people`, `tags` and `status` (v78 dropped or converted every one); `eisenhower`, `tagMap` and `statusFlow` (v79 dropped every one); `radar` and `pulse` (v83 dropped every one); `listwall` (v88 made every one a List board); and `pivot` (v90 dropped every one).
- A layout's `lensId` is no field. v79 removed it from every stored layout, and import, a sync-file load and the audit drop one that is left through the picker, without a fix or a warning.
- A cell's `stripShown` and a layout's `activeColumnId` are no fields. v78 dropped them.

## The predicate check and repair

`data/predicate-shape.ts` reads a stored list predicate (`TodoPredicate`). Import validation, `listDefinitionRepository.getAll` and the audit all read through it. How a filter behaves is in [filters](features/filters.md).

### The check

`checkPredicateShape` is the core shape import requires: a boolean `showCompleted`, a string `searchText` and `dates` an object. It returns `true` or the bad field. It doesn't look at the expression or the or groups.

### The read

`pickPredicate(raw)` returns `{ predicate, fixes }`, the predicate rebuilt from known keys only.

- Unknown keys, and unknown keys inside clauses and anchors, are dropped silently.
- Optional `markers` / `tags` stay absent when absent.
- A missing required field gets its default. A malformed core field is reset to its default: that happens only to rows already stored, since import rejects them.
- What the read drops or changes below is listed in `fixes`, unless it says silently.

Date clauses:

- Each is rebuilt in its stored form: in date-type order, a range with neither end not stored, `includeNoDate` only when true and only on the optional dates.
- An unknown date type or a malformed clause is dropped (`due date filter dropped`, `completed date filter dropped`, `unknown date filter dropped`). A clause is malformed with an unknown `match`, a bad range end or `includeNoDate`, or Has a date / No date on completed / created / modified.
- An "or none" on Completed's range goes with a fix and the range stays (`completed date filter's "or none" dropped`).
- A range's "is not" (`not`, since v71): `true` is kept, and `false` or absent reads as "is". Any other value drops the clause. So does an "is not" on Completed: it isn't defined there, and dropping only the switch would turn the filter round. `includeNoDate` beside `not` goes silently.
- A range end stored as an ISO string is read as a `fixed` anchor.

Id, Priority and text filters:

- A people / status / tag filter that isn't `null` or an array of finite numbers within `PREDICATE_ID_LIST_MAX` is dropped to `null`. The limit is 100,001: a full table plus the `0` sentinel.
- A malformed Priority (`markers`) filter is dropped to `null`. A well-formed one is stored as the filter reads it: a condition naming nothing and a repeated value dropped, the values in their order, at most `MARKER_CLAUSES_MAX` conditions. Past that it is `priority filter capped`.
- A text filter over `PREDICATE_SEARCH_TEXT_MAX` (500, `models/filter-predicate`) is shortened. The list's Text contains input has the same limit.

The "is not" switches (`negate`):

- A `true` switch is kept. `false` / `null` reads as "is", silently.
- Any other value on a known field drops that field's filter (`people filter dropped`). Which way it filtered is unknown, so it goes rather than turning round.
- A `negate` that isn't an object drops every id filter that is set (`unknown "is not" switches dropped`).
- An unknown key goes (`unknown "is not" switch dropped`).
- An "is not" with nothing ticked becomes no filter, and a switch on a field that doesn't filter goes. Both are silent (`withNormalizedNegation`).

The expression (`readExpression`):

- Each node is rebuilt from its known keys: an `and` / `or` of 1 to `EXPRESSION_NODES_MAX` items, a `not`, an id atom with a whole id ≥ 0, a known priority value, non-blank text, or a date atom whose match reads as a date clause does.
- Text over `PREDICATE_SEARCH_TEXT_MAX` is shortened (`text filter shortened`). A date atom's "is not" / "or none" become `not` / `or … none` nodes.
- The expression is then put in its normal form (`normalizeExpression`).
- A node the read can't take, or an expression past `EXPRESSION_NODES_MAX` / `EXPRESSION_DEPTH_MAX`, drops the whole expression (`expression dropped`): which way it filtered is unknown.

Or groups (`orGroups`, stored before v75):

- They are not part of the model. v75 made each stored filter with them an expression, and `pickPredicate` folds any it still reads into one.
- They are read by the same `pickClauses` as the predicate's narrowing fields.
- An `orGroups` that isn't an array is dropped (`or groups dropped`).
- An item that isn't a record, or whose every clause was malformed, is dropped (`or group dropped` / `N or groups dropped`). Its clause fixes are reported once each.
- One that filters nothing goes silently.
- Past `OR_GROUPS_READ_MAX` (30, what a v74 build held) the rest go unread (`or groups capped`).

Graphical or an expression, never both:

- An expression or or groups make the whole filter an expression (`utils/filter-expression.wholeExpression`): the clauses, each or group as an `or` of its clauses, then the expression, ANDed. `withExpression` empties the clauses.
- So a predicate read never holds `orGroups`.
- When the clauses folded in would take the whole past the expression caps, the expression and the or groups go instead, reported (`expression dropped` / `or groups dropped`), and the clauses stay clauses. What import stores then reads back the same.

## Row validation

`data/import-validation.ts` holds import's per-table rules, keyed by the table registry (`tables.ts`). What an import refuses or repairs as the user meets it is in [import and export](features/import-and-export.md).

### A table's rules

`IMPORT_TABLES` gives each table:

- a `check`: `true` or the bad field
- a `pick`: the row rebuilt from model keys, so `Object.keys(pick(row))` is the model's full field list
- a `fixer`, where a valid row can still carry a part import drops or changes

`ImportData` is the registry's `DataTableArrays`: every table present, possibly empty. `KNOWN_DB_TABLES: ReadonlySet<string>` is the registry plus `backups`, which is Dexie-only and never round-trips through import.

### The pickers

- Every `pick*` copies only model keys. A stray `projectId`, `canvasId` or `scheduledDate` on a task is dropped.
- Nested objects are picked too: a task's `recurrenceRule` keeps only `every` / `originalDayOfMonth`, and a list's `membership` only `kind` / `predicate`.
- Date fields are revived through `toDate`, so rows reach Dexie as real `Date`s.
- Each builds its row as a literal that `satisfies AllFields<Model>`: every model key, optional ones included. Adding a model field without carrying it through restore fails `tsc -b`.
- `IMPORT_TABLES[table].pick`, uncompacted, exposes each model's field list to `test/data/export-roundtrip.test.ts`. Its seed must populate every field and round-trip deep-equal with real Dates.

### What the fixers name

- Tasks: `repeat without a due date dropped`. A task's `recurrenceRule` is kept only with a `dueDate`, as the UI offers it and `withOrphanedRuleDropped` keeps it.
- People: `initials normalised`.
- Statuses: any string passes `checkStatus` as an `emoji`, and the pick drops one that isn't one emoji (`emoji dropped`). `emojiShow` is kept only as `color`.
- List definitions: malformed filters (see [The predicate check and repair](#the-predicate-check-and-repair)) and an unknown `sortDirection` (`unknown sort direction dropped`; `null` reads as none). The warning is `Fixed N lists: …`.
- Layouts: what `pickLayout` repairs (see [The layout check and repair](#the-layout-check-and-repair)), and the layout's own `hue` and `icon`.
  - A layout's `hue`, when present, must be one of `HUE_NAMES` or a hex color: `checkLayout` names `hue`. The pick drops any other value with the fix `hue reset`.
  - A layout's optional `icon` must read as an `IconValue` (`models/icon.isIconValue`: none, a known line key, or one emoji with an optional `show`; never a status glyph): `checkLayout` names `icon`. The pick keeps `pickIconValue` of it and drops any other with the fix `icon reset`, so the layout glyph shows again.
- Settings: keyboard shortcut overrides that are unknown, unreadable, refused or clashing, and a check-in filter's people, Show completed or malformed clauses. A check-in filter that isn't a predicate, or is over `CHECKIN_FILTER_SETTING_MAX_LEN`, reads as no filter. The warning is `Fixed settings: keyboard shortcuts (…)` / `check-in filter (…)`, and the value is rewritten without them.

### The same rules for the audit

- `validateRow(table, row): true | string` dispatches to the table's `check`. The audit's unknown-row pass uses it.
- `rowFixes(table, row)` names what import would drop or change in a row (`people filter dropped`, `initials normalised`, …), and `sanitizeRow(table, row)` returns the row as import stores it. The audit's `sanitize` and layout passes use both.
- `isKnownSettingKey(key)` is true for any `ALL_SETTING_KEYS` member or a theme color key (`parseColorSettingKey`). The audit's unknown-setting pass and `checkSetting` use it.

### Settings rows

- `ALL_SETTING_KEYS` is the import allowlist, together with the structured `color.<theme>.<key>` rows, which are not enumerated. Any other `color.*` key is unrecognized.
- An unrecognized key is dropped on import with a warning, and the audit reports it.
- A key an upgrade deleted is an unrecognized key like any other in a file that still holds it: `eisenhowerPanes` and `eisenhowerSource` (v79), and `lenses`, `lensPresetsSeeded` and `activeLensId` (v81).
- How each key's value is checked is in [settings](features/settings.md).
