# Models & Data Layer

Detail reference for `src/models/` (TypeScript interfaces) and `src/data/` (Dexie persistence). Load when touching schema, repositories, migrations, import/export, or model shapes.

## Models

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| TodoSortBy, TodoGroupBy, TODO_SORT_BY_VALUES, TODO_GROUP_BY_VALUES, isTodoSortBy, isTodoGroupBy | models/todo-sort-group.ts | Unified sort + group dimensions for every list surface (list definitions and the list widgets that show them), stored on `ListDefinition.sort` / `.grouping` as flat literals. `TodoSortBy` is a 7-literal union (`'manual' \| 'name' \| 'deadline' \| 'followup' \| 'created' \| 'people' \| 'status'`); `TodoGroupBy` is a 6-literal union (`'none' \| 'deadline' \| 'followup' \| 'people' \| 'status' \| 'tag'`); `'deadline'` is the due date (UI label "Due"). The list UIs offer the `utils/list-options` choices. `isTodoSortBy` / `isTodoGroupBy` back import validation and `buildListSections`' guard (an unknown stored grouping reads as `'none'`). There is no `'project'` value: v60 rewrote stored project grouping to `'tag'` and project sort to `'manual'` |
| TodoItem | models/todo-item.ts | Core todo entry (id optional, pre-insert); optional `notes`, `progress`, `statusId`, `dueDate` (UI "Due"; a day; the recurrence anchor), `recurrenceRule`. `uid: string` (stable identity across export / import — unique Dexie index `&uid`; minted by `todoRepository.insert` via `newTodoUid` unless passed; duplicate detection keys on it, never on `id`) and `completedAt?: Date` (set on completion, cleared on reopen — the retention purge clock). `NewTodoItem` = insert payload with optional `uid`. Follow-up: `lastFollowupAt?: Date` (exact moment from "Followed up", or a day when edited; never in the future) and `nextFollowupAt?: Date` (a day at local midnight; new tasks get today + `settings.followupDefaultInterval`; no index — filtered in memory). `focus?: boolean` — in focus (only `true` is stored; taking a task out deletes the key; no index). Read by the Focus marker and the Markers filter. `urgent?: boolean` / `important?: boolean` — flags (only `true` stored; no index). A task is also urgent when its due date is within `settings.urgentDueWithinDays` (`utils/urgency.isEffectivelyUrgent`) — that never sets the flag. No project or canvas fields (removed in v60; a former project is a `Project: <name>` tag) |

| RecurrenceRule | models/recurrence.ts | Recurrence pattern: type (daily/weekly/biweekly/monthly/quarterly/yearly), optional originalDayOfMonth to prevent drift. **The rule requires a due date** — it advances from the `dueDate`, and `advanceRecurring` (utils/recurrence.ts) short-circuits without one, so a rule on a task without one is dead weight. Enforced on write by `todoRepository.update` / `bulkUpdate`: every merged row that carries `recurrenceRule` without a due date has the rule dropped before persistence — `bulkSetDeadline(ids, null)` silently drops the rule the same way `TaskEditPopup` does on the UX layer. Legacy rows on existing databases are caught by the matching `auditData` orphan-recurrence-rule pass |
| ListDefinition, PersistedListDefinition, ListMembership, ListSort, ListGrouping, RuntimeFilterSpec, RuntimeFilterField | models/list-definition.ts | Saved list definition: name, sortOrder, membership (only `custom` — carries a `TodoPredicate`), `sort: TodoSortBy` and `grouping: TodoGroupBy` (flat literals), optional `maxTasks?: number` + `limitMode?: 'hard' \| 'scroll'` (visible-task cap; `'hard'` (default) truncates the list widget's sections, `'scroll'` keeps every task). Optional `runtimeFilter?: { field: 'person' \| 'status' \| 'tag'; label? }` ("Prompt" in the UI) declares a per-render picker merged into the predicate at interpret time via `applyRuntimeFilter` in `services/build-list.ts`. Only the field is part of the definition: the picks (OR-combined id arrays) are temporary — workspace list tabs keep them in `list-widget-store` (never saved) and pass them to `buildList`. v60 turned stored `'project'` prompts into `'tag'` |
| TodoPredicate, DateAnchor, RelativeDateToken, RELATIVE_DATE_TOKENS, MarkerKey, MARKER_KEYS, MarkerSet, MarkersFilter, HOT_MARKERS, emptyPredicate | models/filter-predicate.ts | Serializable predicate DSL mirroring live filter fields (number arrays + `DateAnchor`s — no Sets, no Dates). Stored inside `ListMembership.custom`; runtime converts to `FilterCriteria` via `predicateToCriteria` at evaluation time. Clauses: `showCompleted`, `personIds` (plain membership over a todo's assigned people, `0` = unassigned sentinel; there is no person filter mode), `statusIds`, `tags` (tag ids, OR; optional on read), `searchText`, `dateField` + `dateRangeStart` / `dateRangeEnd` (`fixed` ISO / `relative` token / `offset` days) + `dateRangeIncludeNoDate`, tri-state `hasDeadline`, `hasFollowup?` (optional on read), and `markers?: MarkersFilter \| null` — `'hot'` (the task must be hot by the Settings Hot rule, `utils/hot`) or a `MarkerSet` `{ urgent?, important?, focus? }` with only `true` values, every one required (strict AND; Urgent = effective urgent); absent / null / `{}` = no filter. `MarkerSet` is also one Hot rule line and the flags a filter seeds on new tasks. No project clause (v60 folded `projectIds` into `tags`). `emptyPredicate()` — no clause set (every open task); new custom lists start from it |
| Person | models/person.ts | Assignable person with name + initials + optional `color?: string` (hex; stored inline, not indexed; validated on import as an optional CSS color) + optional `email?: string` (trimmed, absent when empty; not indexed; always one valid address — `utils/person.isValidEmail`: the person editor requires it and import drops an email failing it, with a warning; read by email check-ins). Avatars / chips / people group headers fill with `person.color`, avatars falling back to `NEUTRAL_PERSON_COLOR` (constants.ts) when unset. Edited in Settings (`PeopleEditor` color input). An `Org: <name>` person (created by the v55 merge) is an ordinary person — the prefix is only a naming convention |

| TodoPerson | models/todo-person.ts | Many-to-many join: todo ↔ person |
| Status | models/status.ts | User-defined workflow state: name, color, sortOrder, `icon` (key from StatusIcon registry, default 'circle'). A status never hides tasks by itself — lists narrow by status only through an explicit status filter |
| PersistedStatus | models/status.ts | Status with guaranteed id (post-insert) |
| Tag | models/tag.ts | First-class normalized tag: `{id?: number, name: string, color: string}`. Canonical casing is whatever the creator entered; uniqueness is enforced case-insensitively at the repository level. Assigned via `todoTags` join, never inlined on `TodoItem`. A `Project: <name>` tag (created by the v60 project merge) is an ordinary tag — the prefix is only a naming convention |
| PersistedTag | models/tag.ts | Tag with guaranteed id (post-insert) |
| TodoTag | models/todo-tag.ts | Many-to-many join: todo ↔ tag |
| Note, PersistedNote | models/note.ts | The single global markdown note: `{content, createdAt, modifiedAt}`. One row backs every notes widget |
| TodoEvent, TodoEventType | models/todo-event.ts | Append-only history log entry; the dashboard trend reads `created` / `completed` / `reopened` (`services/stats/trend.ts`), and the rows travel with exports and task archives. One row per tracked-field mutation on a todo (`dueDate` / `statusId` / `isCompleted`) plus a `created` event at insert time. `TodoEventType ∈ {'created' \| 'scheduled' \| 'deadline' \| 'status' \| 'completed' \| 'reopened'}` — `'scheduled'` is history only (the scheduled date was removed in v53; no new ones are written, old ones are kept). `fromValue` / `toValue` encoding: ISO date string for dates (old `'scheduled'` rows may hold `'fuzzy:<token>'`) / numeric `statusId` for status / null for unset / null on both sides for `created` / `completed` / `reopened` (the type carries the meaning). Idempotent — events are emitted only when the value actually changes (`from !== to`). Backing store: `db.todoEvents` (Dexie v42, `++id, todoId, type, timestamp`). The pre-floor Dexie v49 upgrade reads the most recent `'scheduled'` event per todo (fuzzy `setAt` backfill on pre-v49 databases) |
| WorkspaceLayout, PersistedWorkspaceLayout, LayoutColumn, LayoutCell, LayoutTab, WidgetKind, WIDGET_KIND_SPECS, WidgetKindSpec, WIDGET_KINDS, widgetKindLabel, UNKNOWN_WIDGET_LABEL, isWidgetKind, EisenhowerQuadrant, EISENHOWER_QUADRANTS, TabConfigOf, TabViewStateOf, createTab, getActiveTab, toggleCalendarDateType | models/workspace-layout.ts | `toggleCalendarDateType(types, type)` switches a calendar's date type but never the last one off. ## Data Layer

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| Todo2Database | data/database.ts | Dexie DB class with schema versioning. Tables: `todos` (`++id, isCompleted, dueDate, sortOrder, statusId, &uid`), `people`, `settings`, `todoPeople`, `backups`, `statuses`, `listDefinitions`, `notes` (`++id, modifiedAt`), `tags`, `todoTags`, `todoEvents`, `layouts`, `listOrders`. The `.version(N).stores(…)` chain stays so Dexie can walk to the current schema. Upgrade bodies before v49 are empty (legacy translators were stripped once `OLDEST_SUPPORTED_DB_VERSION` was pinned). **v49** is the one hand-written upgrade: an idempotent backfill walks `todos` rows where `scheduledDate?.kind === 'fuzzy'` and `setAt` is unset, then stamps `setAt` from the most recent `'scheduled'` `todoEvents` timestamp (fallback `todo.createdAt`). From v50 on every version wires its `.upgrade()` as `(tx) => applySchemaUpgradeInTx(tx, N)` so the live DB and imported files run the same registry transform. **v50** `upgradeV50` revives string-typed Date fields; **v51** `upgradeV51` backfills `uid` + `completedAt` and adds the `&uid` index; **v52** `upgradeV52` drops the `floatingHorizons` / `floatingScoreboard` / `floatingSnoozeGraveyard` tables (declared `null`) and cleans the matching settings; **v53** `upgradeV53` removes `scheduledDate` (no store change); **v54** `upgradeV54` removes hide-by-status (no store change); **v55** `upgradeV55` merges orgs into people and drops the `orgs` / `todoOrgs` / `personOrgs` tables (declared `null`); **v56** `upgradeV56` adds the `layouts` table (`++id`) and seeds the Default layout; **v57** `upgradeV57` strips list `favorited` and saved list-tab prompt picks (no store change); **v58** adds the `listOrders` table (`++id, listDefinitionId, todoId, &[listDefinitionId+todoId]`) — no registry entry (an empty table = every task unranked); **v59** `upgradeV59` turns the taskboard into Focus and drops `taskboards` / `floatingTaskboards`; **v60** `upgradeV60` turns projects into tags and drops `projects` / `canvases` / `listInsets` / `floatingCalendars` / `floatingNotes` / `floatingStatus` (declared `null`), restating `todos` without the `projectId` / `canvasId` indexes and `notes` without its `canvasId` index; **v61** `upgradeV61` rewrites stored list predicates from `focus` to `markers` (no store change); **v62** `upgradeV62` drops every `status` tab from the stored layouts (no store change); **v63** `upgradeV63` drops `pinnedToDashboard` from list definitions and renames `color.*.canvasBg` to `color.*.appBg` (no store change). The latest version is declared with `CURRENT_DB_VERSION` (not a literal) — when bumping, turn the previous one into its literal first |
| CURRENT_DB_VERSION, OLDEST_SUPPORTED_DB_VERSION | data/database.ts | Two source-of-truth schema constants. `CURRENT_DB_VERSION` (63) is the latest declared `.version(N)`; the `migration-check.test.ts` `db.verno` assertion guards bumps. `OLDEST_SUPPORTED_DB_VERSION` is **pinned at 49** (literal): any on-disk DB or imported `__schemaVersion` below it triggers `MigrationDialog` via `services/migration-check`; files at or above it import through the `schema-upgrades` registry. Never raised automatically — raising it is a deliberate user decision (and frees the registry entries at or below the new floor) |
| DataTableRows, DataTableName, DataTableArrays, DATA_TABLE_NAMES | data/tables.ts | **The table registry**: every data table (all but `backups`) and its row type — todos, people, settings, todoPeople, statuses, listDefinitions, notes, tags, todoTags, todoEvents, layouts, listOrders, in that (export and restore) order. Export, restore, import validation, the audit and file sync all walk it, and the compiler makes each cover every table: `DATA_TABLES` checks the Dexie class against it, `IMPORT_TABLES` is keyed by `DataTableName`, `ImportData` / `ExportData` are mapped from it. Adding a table: add it to `DataTableRows` + `DATA_TABLE_ORDER`, declare it on the Dexie class, follow the compile errors |
| DATA_TABLES, ALL_DATA_TABLES | data/database.ts | `DATA_TABLES` — the data tables by name, typed by row; assigning `db` to it is the compile-time check that the Dexie class declares every registry table with the registry's row type. `ALL_DATA_TABLES` — the same tables in `DATA_TABLE_NAMES` order (excludes backups); used by export, restore and the file-storage hooks |
| ensureSeededStatuses | data/database.ts | Idempotent seeder for the built-in Assigned status row; settings-pointer-as-truth (`seededAssignedStatusId`); used by `restoreFromImportData` after a fresh import. (A "Follow-up" status in user data is an ordinary status — no longer seeded) |
| SETTING_KEYS, ALL_SETTING_KEYS, SettingKey | data/setting-keys.ts | The persisted settings keys: `themeMode`, `defaultStatusId`, `quickStatusId`, `seededAssignedStatusId`, `completedRetentionDays`, `weekStartsOn`, `maxTags` (no longer read — tags have no cap; a stored row stays valid), `followupDefaultInterval`, `urgentDueWithinDays` (`off` or a day count 0–365; validated on import), `hotRule` (JSON array of lines, each an object of markers set to `true`, ≥ 1 line, ≥ 1 marker per line, unknown keys rejected on import; import stores it normalized with duplicate lines collapsed), `checkinOpenMethod` (`mailto` / `eml`), `checkinTaskScope` (`all` / `due-soon` / `hot` / `list:<id>`; a list id the data lacks is accepted — it reads as `all`), `activeLayoutId` (plus the structured `color.<theme>.<key>` rows, not enumerated). `ALL_SETTING_KEYS` is the import allowlist |
| createRepository, reorderBySortOrder, nextSortOrder, insertLast | data/create-repository.ts | Factory for shared CRUD operations (getAll, getById, insert, update, remove); extended per-repo. `reorderBySortOrder(table, ids)` gives each id its position as `sortOrder` in one transaction (status and list-definition `reorder`). `nextSortOrder(table, floor)` — one past the highest stored `sortOrder` (at least `floor + 1`), read inside the caller's insert transaction; `insertLast(table, row, floor)` inserts with it in one transaction and returns `{ id, sortOrder }` — so two adds that start together never share a sort order |
| createJoinOps, buildAssignmentMap, captureJoinRows, JoinCapture | data/join-helpers.ts | `createJoinOps`: join table assign/unassign with dedup check. `buildAssignmentMap`: generic join table → entity map builder (Map\<linkId, Entity[]\>); a UI snapshot read under `Dexie.ignoreTransaction`, so a load started by a React effect inside an open transaction's zone (store writes inside a transaction re-render synchronously) never joins that transaction. `captureJoinRows`: snapshot of join rows before an entity delete, restored by the person / tag repositories' `restoreWithJoins` on undo |
| todoRepository | data/todo-repository.ts | Full CRUD + queries for TodoItem, bulkUpdate (batched transaction), bulkDelete (atomic multi-delete). `delete` / `bulkDelete` clear the todo's `todoPeople` / `todoTags` / `todoEvents` rows and its `listOrders` ranks in the same transaction as the row drop, and return the deleted `todoEvents` rows (undo puts them back). `insert` without a `sortOrder` (and `insertManyWithAssignments`, always) places tasks last with `nextSortOrder` inside the insert transaction. `update(id, changes, now?)` / `complete(id, completed, completedAt?, now?)` / `bulkUpdate(mutations, now?)` stamp `modifiedAt` with the caller's `now` (so the store's copy matches; a mutation carrying its own `modifiedAt` — an undo — keeps it), and events with the same time. `update(id, changes)` writes only the given fields (a field set to `undefined` is removed; a missing row is left alone — nothing is recreated) — the single-row `bulkUpdate`, which also skips missing rows. **Recurrence-orphan invariant:** `update` and `bulkUpdate(mutations)` merge the change against the existing row and run a private `dropOrphanedRule` helper — when the merged row has `recurrenceRule` but no `dueDate`, the rule is dropped before the write, so every caller converges on `TaskEditPopup`'s silent-clear semantic. **Completion clock:** `insert` / `update` / `complete(id, completed, completedAt?)` / `bulkUpdate` keep `completedAt` in step with `isCompleted` via `resolveCompletedAt` (utils/completed-at.ts): newly completed → now (or the explicit value — undo passes the original back), still completed → kept, reopened → removed. `insert` mints `uid`. `getByIds(ids)` / `getByUids(uids)` (DB reads for the purge prompt / `purgeCompleted`, which must not depend on what the store has loaded). Write paths emit `todoEvents` in the same transaction. `insertManyWithAssignments` (several tasks + `created` events + `todoPeople` / `todoTags` rows in one transaction) and `restoreManyWithAssignments` (undo of a delete / redo of a create: rows with their ids, joins not duplicated, and their `events` back with their own ids) back `todo-store` |
