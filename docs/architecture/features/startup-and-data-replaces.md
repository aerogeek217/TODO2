# Startup and data replaces

**Startup** (`services/app-startup.runAppStartup`): `App.tsx` first checks the database's version (below the floor → `DatabaseTooOldDialog`: nothing read or written — Download this data, or Import a file… that replaces it after asking, or Reload; saved by a newer build → `DatabaseTooNewDialog`: Reload only, nothing read or written). Then settings load (theme, colour overrides) → the sync file reconnects (`fileStorageService.initialize()`). When its handle needs permission again, launch **waits for the launch question** (Grant access… / Continue without the file) before anything else runs.

**Launch can't wait on the browser without end**: reading the stored handle and checking its permission each get 5 s (`FILE_LINK_TIMEOUT_MS`) — a handle not read in time, or not readable at all: launch goes on without the file and the storage pill says **Sync off** for the rest of the session — no Dismiss; until a reload reads it or the file is attached again — (the stored handle kept, edits tracked as unsynced for the next start's load decision); a permission check not answered, or that fails: the launch question, saying the link to the file could not be checked; neither reads or writes the file, and a late answer is dropped.

**The start screen** (`layout/StartScreen`, behind the version check and launch alike) says `Loading…`; once one part of launch has taken 6 s (`START_SCREEN_EXPLAIN_MS`) it names it — opening the database, checking the sync file, loading tasks — and offers what is safe there: **Reload** always, and at the sync file's step, while launch waits for the browser to hand over the handle, its permission or the file's text (`launchWait`; the read has no time limit), also **Continue without the file** (this browser's data, sync paused, nothing written, the handle kept) and **Forget the sync file…** (after a confirm: the stored handle cleared, the tasks and the file itself untouched). Nothing there deletes or changes a task. The load decision changes nothing on either side until the user resolves a disagreement (conflict / older file / unreadable → a dialog or a pause); a browser merely ahead of an unchanged file is written to it after a backup of the file's text. Then the stores load. Completed tasks past the retention are **never purged silently**, and launch opens no dialog about them: the storage pill shows a **purge notice** (`17 old completed` — after any sync or backup warning, which outranks it; the phone's sync sheet too) whose section offers **Review…** — the purge dialog (Export & delete / Delete / Not now; a backup snapshot first), the only way anything is deleted — and **Not now**. It is offered at most once every N days, counted from when the user was last asked (the dialog opened, or Not now) — a notice merely shown stamps nothing, so one left unanswered is there at the next launch —, also after a later sync-file load; a change that leaves none expired (deleted, reopened, retention off) removes it (`stores/purge-notice-store`, read by `overlays/PurgeNoticeHost`). `backupScheduler.start()` takes a daily automatic backup; each backup kind keeps its newest few within a byte budget.

**Data replaces** (`services/replace-data.replaceData`) — Settings import and backup restore, the audit's cleanup, the sync file's load, the append import: note saves held → safety snapshot → layout writes in flight settled → the write → the stores reload (`refresh-all`; an append import reloads the task stores only and keeps the undo history) → `onDataReplaced` listeners. From the write until the reload has opened the new data, a replace (not an append import) holds layout and list writes (`stores/replace-hold`): the stores still hold the replaced data and their writes put whole rows, so an edit then (a tab closed, a rename, an undo) changes nothing and says why rather than writing the old layout or list over the new data. A file (an import, a backup, the sync file) is read through the import pipeline first: one from below the schema floor (`OLDEST_SUPPORTED_DB_VERSION`, v68) or without a version is refused — nothing read, nothing written —, with a message naming the older build that still converts it. One whose layouts hold far more parts than the app keeps is refused too, with a message, before the schema upgrades run (`data/layout-size`); a layout row the check rejects is **repaired**, as the database read repairs it, and stored repaired with a warning — never the whole file refused.
