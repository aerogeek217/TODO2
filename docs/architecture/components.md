## Popover patterns

Every floating panel anchored to a click-coord or a trigger element routes positioning + dismissal through the shared `usePopoverAnchor` hook (`hooks/use-popover-anchor.ts` — see services-and-utils.md). The hook owns flip-on-clip + clamp + scroll/resize/Escape/outside-click; the caller owns the panel + its `createPortal` wrapper. Built ui-consistency P1; the seven popovers covered are `RuntimeFilterPicker`, `ListDefinitionPickerPopup`, `WidgetKindMenu`, `FilteredListPopup`, `SlotMenu`, `CanvasContextMenu`, and `ProjectPickerPopup`.

**When to add a new popover, do this and only this:**

1. Choose an anchor: `{kind:'ref', ref}` for an element-anchored popover (panel tracks the trigger on scroll); `{kind:'point', x, y}` for click-coord popovers (right-click / contextmenu).
2. Call `usePopoverAnchor({ anchor, open, onClose })`. Defaults handle scroll-close / resize-close / Escape / outside-click.
3. Render the panel inside `createPortal(<div ref={panelRef} style={style}>…</div>, document.body)` — the hook is the *only* place that should compute panel position; consumers should not also write a separate clamp / flip `useEffect`.
4. For nested flyouts whose drop target sits outside the panel (e.g. `WidgetKindMenu`'s Change-list submenu), pass `extraInsideRefs: [flyoutRef]` so outside-click ignores them.
5. To preserve a popover's "no behavior change" path during migration: ref-anchored popovers that previously *repositioned* on scroll (`RuntimeFilterPicker`) pass `closeOnScroll: false, closeOnResize: false` — the hook reposition-mode kicks in for `kind: 'ref'` anchors, while `kind: 'point'` anchors stay static.
6. Popovers that own special Escape logic (e.g. `WidgetKindMenu`'s "close flyout first, then menu") pass `closeOnEscape: false` and keep their own keyboard handler on the panel.

**What NOT to do:**

- Do not write per-component `useEffect` for `getBoundingClientRect()` math, scroll listeners, resize listeners, or document-level `mousedown` / `keydown` outside-click handlers. Every one of those is folded into the hook.
- Do not portalize a popover from the *call site* (`createPortal(<MyPopover/>, body)` at the consumer). All the popovers above portal *internally* — adding a wrapping portal at the call site double-portals harmlessly but obscures intent and leaves stale parallel `createPortal` patterns the audit explicitly retired (`CanvasContextMenu` / `ProjectPickerPopup` previously had split call-site portal patterns; ui-consistency P1 collapsed them).

## DnD diagnostic flag (`?debug-dnd=1`)

Append `?debug-dnd=1` to the URL to instrument every guard branch and resolution path across the rails / float / taskboard / calendar drag-drop subsystem. Built ui-consistency P5 in response to triage P5's forensic diagnosis effort: the next time a drag silently misses (no console error, no visible feedback, the gesture just appears to do nothing), the user or reviewer flips the flag, redoes the drag, and the console emits the full ladder — source slot/tab → collision rule chosen → resolved `over.id` → guard outcomes → final dispatch.

The flag is read once at module load via `utils/debug-flags.ts`; each call site uses the gated `dndLog(label, payload?)` helper so production console stays quiet when the flag is absent. This is **permanent diagnostic infrastructure** (promoted in code-review-tail-2026-05-09 P1) — DnD bugs in this surface area recur often enough that the small bundle cost (a few dozen no-op string literals) buys real diagnose value.

**Wrap sites:**
- `utils/task-dnd/dispatch.ts` — every `return false` / `return true` branch (no-active-todo, calendar reschedule, taskboard reorder / move-to-end / remove-on-drop-off, taskboard add, unhandled).
- `utils/task-dnd/collision.ts` — `buildTaskCollision` rule selection (no-active fallback, rule matched with index + algorithm + droppable counts, no-rule-matched fallback).
- `utils/rail-dnd.ts` — `resolveFloatDockTarget` resolution (miss / empty-side / tab-strip / collapsed-side center-merge / collapsed-side no-stub / canvas-fallthrough / slot.no-orientation / slot).
- `hooks/use-rails-drag-monitor.ts` — `useRailsDragMonitor` `onDragStart` + `onDragEnd` (non-rails-drag bail, no-over, unknown-drop-id, resolved zone, all five canvas-branch silent aborts — no-pointer / no-canvas-el / no-src-slot / no-src-tab / no-canvas-id — and the slot-drag fallback).

**Not wrapped:** the stats widget (`FloatingStatusNode`) consumes the shared `useFloatingWidget` hook and docks via the dock-button click path, NOT dnd-kit drag events. It participates in the rails-monitor float-dock flow when the user drags it, but doesn't initiate any new DnD entry-points — no new wrap points needed for it.
