# Components

Detail reference for `src/components/` (workspace, task, overlays, shared, layout, settings) and `src/views/`. Load when touching UI, workspace widgets, overlays, editors, or view-level wiring.

## Views

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| ROUTE_WORKSPACE, ROUTE_SETTINGS, LEGACY_ROUTES, AppRoute, SettingsRouteState | routes.ts | Route paths for the hash router. `App.tsx` renders `WorkspacePage` at `/` (`ROUTE_WORKSPACE`, inside an `ErrorBoundary` scoped "Workspace"); `/settings` renders the mobile `SettingsPage` on a phone and, on desktop, opens the Settings modal and redirects to `/` (a deep link); every former page route in `LEGACY_ROUTES` (`/workspace`, `/list`, `/calendar`, `/dashboard`) and any unknown path redirects (`<Navigate replace>`) to `/`. | Section / buildListSections / listSortComparator | services/list-sections.ts | The section builder behind every list widget. See the `architecture/services-and-utils.md` row for the full surface |
| WorkspacePage, useWorkspaceData, useWorkspaceDragState, PanelGhost, UnsavedNavigationGuard | views/WorkspacePage.tsx | `/` — the app's main page. Renders `WorkspaceView` on desktop and `MobileWorkspaceView` on mobile (`useIsMobile`; its top bar gets the storage `SyncStatusButton`); on mobile the `DndContext`'s pointer sensor is swapped for `NoDragSensor` (no activators — the sensor list keeps its length, which dnd-kit uses as effect deps), so nothing drags. Calls `useWorkspaceStore.init()` on mount when not hydrated (pages mount after App's startup chain, so after the sync-file load). `useWorkspaceData` loads **all** tasks (`loadAll`), people, tags, statuses and list definitions, plus `useEntityAssignmentsForLoadedTodos()` — so chips and person / tag groups render on a cold load; the page subscribes to no task data, so a task edit doesn't re-render it (`src/test/views/workspace-page-renders.test.tsx` counts its renders). Owns the page `DndContext` (`buildTaskCollision`: tab and panel drags match no droppables, everything else `pointerWithin`): tab drags (`active.data.type === 'workspace-tab'`) and panel drags (`'workspace-panel'`, from a header's empty space) — on drag start the page measures the workspace (`measureWorkspace`), a window `pointermove` listener runs `hitTestWorkspace` → `dropTargetForHit` → `dropChangesLayout` (no-ops stay plain) into `WorkspaceDragContext` (`WorkspaceDragState`: the source, the tabs that move, hit, target, accepts), and drop calls `moveTab` / `movePanel`; Esc cancels. Task drags go through `dispatchTaskDrop` (calendar day; which date it sets: see `resolveCalendarDropType`; the write is `buildRescheduleUpdate` → `useTodoStore.update`) — its `chooseType` opens `CalendarDropChooser` (`useCalendarDropChoice`; the dropped-on day stays highlighted through `PendingCalendarDropContext`). Auto-scroll only scrolls a container while the pointer is inside it (`useAutoScrollUnderPointer`: dnd-kit otherwise scrolls the dragged row's list from another column). `DragOverlay` shows the tab ghost or, for a panel drag, `PanelGhost` (a 180px card: the panel's tabs, three placeholder lines, an `N tabs` badge, rotated −1.2°) — +12/+10 from the pointer via a modifier, placed above / left of the pointer where it would leave the window — plus a label pill for an accepted target the zones don't label ("New column", "New band above / below all columns", a panel's "Insert N tabs"), a lifted calendar entry (`calendarEntry` drag data) or the task row (a ghost `TaskRow`, styled by `components/workspace/DragOverlayTask.module.css`). Hosts `TaskDialog`, `CheckinDialog` (after it, so it opens over the task dialog), `TaskEditPopupHost`, `EntityActionHost`, `EditListHost`. On mount it also calls `list-draft-store.restore()` (unsaved list edits kept from before a reload). `UnsavedNavigationGuard`: `useBlocker` (pathname changes while the layout is dirty or a list has unsaved edits) → `UnsavedPrompt` (Save → then proceed; Discard → then proceed; Cancel → reset); a reload or a closed tab loses nothing (the unsaved changes are kept in the browser, `data/draft-storage`), so its `beforeunload` prompt fires only when they couldn't be kept (`unsavedDraftsKept()` false) |
| SettingsPage | views/SettingsPage.tsx | Mobile Settings (`/settings`, the bottom tab bar's Settings tab): the sections with a part flagged `mobile` in `settings-sections.ts` (`MOBILE_SETTINGS_SECTIONS`: Appearance, People statuses & tags, Database, About) as a list; tapping one slides to it — only its phone parts (People statuses & tags: only the Unused people & tags row; Database: Import / Export, File storage) — with a back arrow; navigated to with route state `{ section, part? }` (`SettingsRouteState` — the storage status sheet's File storage settings) it opens on that section, scrolled to the part (`scrollToSettingsPart`). Desktop shows the same sections in `SettingsModal` |

## Popover patterns

Floating panels anchored to a click-coord or a trigger element route positioning + dismissal through the shared `usePopoverAnchor` hook (`hooks/use-popover-anchor.ts` — see services-and-utils.md). The hook owns flip-on-clip + clamp + scroll/resize/Escape/outside-click; the caller owns the panel + its `createPortal` wrapper. Every popover is on it: `MenuPopover` (and with it `WidgetKindMenu`, `TaskMenu`, the layout picker, …; its submenus and panels too), `AnchoredPicker` (the row / mobile row / tag chip / bulk-bar pickers), `RuntimeFilterPicker`, `FollowupPopover`, the desktop `FilterChipBar` pickers and Filters menu, `StoragePill`, `CalendarDayPopover`, `EditListPopover` (rect anchor: its list's cell), `PredicateFieldPicker`, `SwitchToManualPopover`, `StatusEditor`, `TaskNotePopover`, `TooltipBubble` (`bottom-center`) and the `@ # /` popups of `QuickAddBar` and the notes (`NotesNlpPopup`) — both `rect` anchors at the caret. The one exception is the Eisenhower refusal tooltip, which follows the pointer and is kept inside its widget, not the viewport.

**When to add a new popover, do this and only this:**

1. Choose an anchor: `{kind:'ref', ref}` for an element-anchored popover (panel tracks the trigger on scroll); `{kind:'point', x, y}` for click-coord popovers (right-click / contextmenu).
2. Call `usePopoverAnchor({ anchor, open, onClose })`. Defaults handle scroll-close / resize-close / Escape / outside-click.
3. Render the panel inside `createPortal(<div ref={panelRef} style={style}>…</div>, document.body)` — the hook is the *only* place that should compute panel position; consumers should not also write a separate clamp / flip `useEffect`.
4. For nested flyouts that sit outside the panel (e.g. `MenuPopover`'s submenus and panels), pass `extraInsideRefs: [flyoutRef]` so outside-click ignores them.
5. Ref-anchored popovers that should *reposition* on scroll instead of closing (`RuntimeFilterPicker`) pass `closeOnScroll: false, closeOnResize: false` — the hook's reposition mode kicks in for `kind: 'ref'` anchors, while `kind: 'point'` anchors stay static.
6. Popovers that own special Escape logic (e.g. `MenuPopover`'s "close the submenu first, then the menu") pass `closeOnEscape: false` and keep their own keyboard handler. `consumeEscape: true` stops the Escape that closes a popover there (a row picker in the task dialog doesn't also close the dialog).
7. A panel whose size changes while open (a picker's list narrowing as you type, an editor growing) passes `observeSize: true`; an anchor that isn't the trigger (a whole row) passes `anchorIsInside: false` so a click on it closes the popover.
8. Make the panel's root a `PopoverRoot` (`components/shared/PopoverRoot.tsx`, a `div` taking every prop) instead of a plain `div`, and give its surface the popover tokens (`background: var(--color-popover-bg)`, `box-shadow: var(--shadow-dropdown)` — the ring is inside it, no border; D21). The root carries `data-popover-level` (`1` over the page, `2` on a popover or in a dialog — `popover-level.usePopoverLevel`) and provides its level to what it renders, so a popover opened from it — portaled or not — steps up; `tokens.css` swaps the tokens under `[data-popover-level='2']`. A popover whose sub-popovers render beside it rather than inside (`MenuPopover`'s submenus and panels, the folded Filters menu's pickers) wraps them in `PopoverLevelContext.Provider value={usePopoverLevel()}` itself.
9. To point at the anchor (D21), pass `caret: true` to the hook and its `caret` to the root (`<PopoverRoot caret={caret}>`): the hook keeps the gap at `CARET_GAP_PX` and returns `null` for a point anchor (nothing to point at) or before the panel is placed. The trigger shows the open look while the popover is open (`--trigger-open-ring`, `--color-trigger-open-fill`, `--color-accent-text`; with `:focus-visible`, `box-shadow: var(--trigger-open-ring), var(--focus-ring)`) — replacing any open tint of its own.
10. Nothing to do for layers opened over a popover: a press or an Esc in a layer stacked above it — a portal root later in `<body>` (`utils/dom-layers.isInLayerAbove`): a menu, a dialog or a confirm opened while it is open — isn't outside it, and an Esc with nothing focused while a modal is open above it (`hasModalAbove`) is that modal's. So a picker stays open behind the person / tag menu, editor or confirm it opened, and each Esc closes one layer (`e2e/picker-entity-menu.spec.ts`).

**What NOT to do:**

- Do not write per-component `useEffect` for `getBoundingClientRect()` math, scroll listeners, resize listeners, or document-level `mousedown` / `keydown` outside-click handlers. Every one of those is folded into the hook.
- Do not portalize a popover from the *call site* (`createPortal(<MyPopover/>, body)` at the consumer). The popovers above portal *internally* — adding a wrapping portal at the call site double-portals harmlessly but obscures intent.

## DnD diagnostic flag (`?debug-dnd=1`)

Append `?debug-dnd=1` to the URL to log every guard branch and resolution path of the task drag-and-drop path (list widget, Eisenhower and dashboard rows and calendar entries dropped on calendar days and quadrants). When a drag silently misses (no console error, no visible feedback), flip the flag, redo the drag, and the console emits the ladder — collision rule chosen → resolved `over.id` → guard outcomes → final dispatch.

The flag is read once at module load via `utils/debug-flags.ts`; each call site uses the gated `dndLog(label, payload?)` helper so production console stays quiet when the flag is absent. This is **permanent diagnostic infrastructure** — the small bundle cost (a few dozen no-op string literals) buys real diagnose value.

**Wrap sites:**
- `utils/task-dnd/dispatch.ts` — every branch of `dispatchTaskDrop` (no-active-todo, calendar-day reschedule, calendar-day choice cancelled, Eisenhower drop with its result, unhandled).
- `utils/task-dnd/collision.ts` — `buildTaskCollision` rule selection (no-active fallback, rule matched with index + algorithm + droppable counts, no-rule-matched fallback).

Workspace tab drags and list-row reorders don't go through these (they hit-test measured geometry) and are not logged.
