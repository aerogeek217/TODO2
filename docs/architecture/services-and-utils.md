# Services, Hooks & Utils

Detail reference for `src/services/` (non-UI logic), `src/hooks/` (custom React hooks), and `src/utils/` (pure utilities). Load when touching NLP, recurrence, file storage, list interpretation, drag-and-drop logic, keyboard shortcuts, or date helpers.

## Services

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| Section, ListSectionsSpec, ListSectionsContext, buildListSections, listSortComparator, isUngroupedSectionKey, truncateSections | services/list-sections.ts | The one section builder for list widgets (`buildList` → `useBuiltList` → `ListWidget`), so the same definition yields the same sections in every widget. `buildListSections(members, {groupBy, sortBy, restrictToPersonIds?, restrictToTagIds?}, ctx)` sorts with `listSortComparator(sortBy)` first (so every section comes out sorted; grouping keeps input order), then partitions through `utils/task-grouping.partitionByGroup`. Sections: due / follow-up → Overdue (`--color-overdue`) / Today (`--color-accent`) / This Week (`--color-text-secondary`) / Later (`--color-text-muted`), then "No Due Date" / "No Follow-up" (key `none`; every trailing "No …" / Unassigned section is `--color-text-muted`); people → person name, accent `person.color` (undefined when unset), alphabetical, then "Unassigned"; status → registry `sortOrder`, status color, then "No Status"; tag → `#name`, tag color, alphabetical, then "No Tag"; `none` → one `all` section (none when empty). A stored grouping this build doesn't know reads as `none`. Restrict mode (the effective filter's person / tag picks): only those sections, in pick order; the trailing sentinel is dropped unless the person picks include `0` (Unassigned). A task with several people / tags appears in each of their sections. `listSortComparator(sortBy, manualRanks?)`: `manual` → the list's ranks when `ctx.manualRanks` is given (`utils/list-order.manualOrderComparator`: ranked by rank, then unranked oldest first — list widgets via `ListBuildContext.ranks`), else `sortOrder` then id; `name` → `title.localeCompare` then `sortOrder`; `deadline` / `followup` → `compareTodosByDate` (undated last); `created` → `createdAt` oldest first, then `sortOrder`; `people` / `status` have no order of their own and fall back to `sortOrder`. `isUngroupedSectionKey(groupBy, key)` recognises the trailing "No …" / Unassigned section (cross-group drops map it to `UNGROUPED_GROUP_KEY`). `truncateSections(sections, maxTasks)` slices the tail when the total task count exceeds `maxTasks` (a list's hard cap) |

| buildList, matchesMembership, applyRuntimeFilter, ListContents, ListBuildContext, PredicateEvaluator | services/build-list.ts | Runs one `ListDefinition` over the tasks (called by `useBuiltList` and the task dialog's list source). Returns `ListContents { id, key, label, todos (members once, in sort order), sections, runtimeFilterUnset? }`. `applyRuntimeFilter(predicate, spec, values)` narrows the declared field (`person` / `status` / `tag`) to the picks (OR), replacing any prior id filter on that field; an empty array is a no-op. | buildEntries, CalendarEntry, BuildEntriesOptions, compareCalendarEntries, isEntryOverdue, dayOverdueWash, calendarEntryState, dayDots | services/calendar-entries.ts | Bucket-and-enrich helper for the workspace calendar widget. `buildEntries(todos, days, options)` places one entry per shown date type (`options.dateTypes`, required): on the due date's day and on the next follow-up's day (`kind: 'due' \| 'followup'`, `day` = midnight), generates virtual recurring due entries within the window via `generateRecurringInstances` (only while due dates are shown), and enriches every entry with people / status. | fileStorageService | services/file-storage.ts | File System Access API sync (file ↔ IndexedDB). **The user decides before anything changes:** a load (startup / Grant Access / attach / `retry()`) reads + `prepareImport`s the file without touching either side, then: any failure (too large, read error, invalid JSON/rows, too new, upgrade failed) → **paused** (`status.paused = {reason, message}`, no restore, never writes; a file `getFile()` can't find still forgets the handle). Reads go through private `readFileText` (50 MB cap before reading; a `File` snapshot that a save replaced mid-read — `NotFoundError` / `NotReadableError` from `text()` — is read again, up to 3 times, then `read-error`) and wait for `whenIdle()` first; below floor → `onConfirmMigration` (cancel → paused); unsynced browser changes (`dirtySince`), or no sync record while the browser has tasks → `onConflict` → `'file'` (browser backup via `takeSafetySnapshot` → restore; a failed backup asks, Cancel pauses with `backup-failed`) / `'browser'` (file text → `backupScheduler.snapshotFileBeforeOverwrite` → overwrite) / `'cancel'` (paused) — skipped when `browserMatchesFile` says both sides already hold identical data (an older file is compared after its upgrade, so a browser that came from a build without a sync record and was upgraded at open matches its in-sync file and gets the upgrade prompt instead); clean browser synced with an earlier version of the file → loads it (multi-machine); older-but-supported file → `onConfirmFileUpgrade` first (cancel → paused), then restore + restamp. **Events:** `onStatusChange` / `onBeforeImport` / `onAfterImport` add a subscriber and return its unsubscribe — every subscriber gets every event (a status subscriber that throws is logged; before-import holds are all taken, in turn, and released together after the reload — a hold that fails releases the ones taken; after-import subscribers all run in turn and the first failure is rethrown after). The questions (`onConfirmMigration` / `onConflict` / `onConfirmFileUpgrade`) have one answerer: a later handler replaces an earlier one, and each returns a removal that is a no-op once replaced. Missing handlers resolve to the safe answer (stay paused). Change-tracking Dexie hooks stay installed whenever a file is attached (also while paused / needing permission) and mark the browser dirty; writes only happen while `syncEnabled`. `overwriteFileWithBrowser()` (banner "Keep browser data…") backs up the file text then overwrites and resumes (a file over 50 MB isn't read: `backup-failed`, untouched). **Writes never overlap** (`saveInFlight`): a debounced save asked for during one is rescheduled after it; a forced write (create / overwrite / upgrade / empty-file seed) waits for it and then writes — never dropped; a save writes only the handle it started on and sets the sync record only if that file is still attached. `whenIdle()` resolves once no write is running or scheduled (the load path, and the e2e `readSyncFile` fixture, wait on it). Failures are logged (`console.warn`) and surfaced in `status.error` / the paused message. **Every write of existing file content** (confirmed upgrade, below-floor confirm, either conflict choice that rewrites the file, keep-browser overwrite) first backs up the raw file text (private `backupFileText` → `backupScheduler.snapshotFileBeforeOverwrite`); a failed backup or unreadable file pauses with `backup-failed` and nothing is written — any new write path must do the same. `openFile`/`createFile`/`disconnect` reset the sync record. `createFile` suggests `todo2-data-YYYY-MM-DD.json` (`newSyncFileName`, local day): the browser empties an existing file picked in the save dialog before `showSaveFilePicker` resolves, so its text can't be backed up — the dated default keeps the suggestion off an older sync file, and Settings › File storage says so. `isConnected` = actively syncing. Every load that replaces browser data goes through `takeSafetySnapshot` (a failed browser backup asks "Continue without a backup?"; Cancel pauses with `backup-failed`, nothing changed) — except when the browser already holds exactly this file's data (identical — after the file's upgrade, if any — or clean and synced with this file version), where a failed backup is only logged since the load loses nothing. The backup and the restore run between two hooks `file-storage-store` wires: `onBeforeImport` (the note store's `holdForDataReplace` — typed note text is saved before the backup; released after the reload, or on Cancel) and `onAfterImport` (`refreshAllStores`). `clearFileHandle` failures are logged with `console.warn`. `reset()` (tests sharing one module instance) puts the service back as at module load — no file, no sync, no timers or Dexie hooks, idle — and keeps its subscribers |

| parseInput, removeSpans, ParsedInput, CommandProblem | services/natural-language-parser.ts | Parses task text. Flags `/urgent` `/important` `/focus`; `/due <date>` and `/followup <date\|interval\|none>` read the longest run of up to 4 words that parses (`parseCommandDate`), stopping at the next `@` / `#` / `/` token; `/repeat <frequency>` one word; `/status <name>` one word or a quoted `"Multi word"`. The first `/due` `/followup` `/repeat` `/status` wins. Nothing else is read: plain dates, `by fri`, `every week`, `:status` stay in the title. `ParsedInput` = `text`, `title` (tokens removed), `tokens` (with spans; commands carry `command` + argument `value`), `persons`, `tags`, `status?`, `dueDate?`, `recurrence?`, `urgent` / `important` / `focus`, `nextFollowupAt?`, `followupNone`, and `problems` (`CommandProblem` with span: `unknown` `/urgnt` and `unreadable` (bad / missing argument) and `duplicate` stay in the title; `ignored` = `/repeat` without `/due` — dropped from the title, `recurrence` kept so a due date picked in the editor can anchor it; `unmatched` is the resolver's unknown status). `parseInput(text, today = new Date())`. `removeSpans` rebuilds a title without given spans |
