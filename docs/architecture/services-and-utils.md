# Services, Hooks & Utils

Detail reference for `src/services/` (non-UI logic), `src/hooks/` (custom React hooks), and `src/utils/` (pure utilities). Load when touching NLP, recurrence, file storage, list interpretation, drag-and-drop logic, keyboard shortcuts, or date helpers.

## Services

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| Section, ListSectionsSpec, ListSectionsContext, buildListSections, listSortComparator, isUngroupedSectionKey, truncateSections | services/list-sections.ts | The one section builder for list widgets (`buildDashboardLists` → `useBuiltList` → `ListWidget`), so the same definition yields the same sections in every widget. `buildListSections(members, {groupBy, sortBy, restrictToPersonIds?, restrictToTagIds?}, ctx)` sorts with `listSortComparator(sortBy)` first (so every section comes out sorted; grouping keeps input order), then partitions through `utils/task-grouping.partitionByGroup`. Sections: due / follow-up → Overdue (`--color-overdue`) / Today (`--color-accent`) / This Week (`--color-text-secondary`) / Later (`--color-text-muted`), then "No Due Date" / "No Follow-up" (key `none`; every trailing "No …" / Unassigned section is `--color-text-muted`); people → person name, accent `person.color` (undefined when unset), alphabetical, then "Unassigned"; status → registry `sortOrder`, status color, then "No Status"; tag → `#name`, tag color, alphabetical, then "No Tag"; `none` → one `all` section (none when empty). A stored grouping this build doesn't know reads as `none`. Restrict mode (the effective filter's person / tag picks): only those sections, in pick order; the trailing sentinel is dropped unless the person picks include `0` (Unassigned). A task with several people / tags appears in each of their sections. `listSortComparator(sortBy, manualRanks?)`: `manual` → the list's ranks when `ctx.manualRanks` is given (`utils/list-order.manualOrderComparator`: ranked by rank, then unranked oldest first — list widgets via `DashboardListsContext.listRanks`), else `sortOrder` then id; `name` → `title.localeCompare` then `sortOrder`; `deadline` / `followup` → `compareTodosByDate` (undated last); `created` / `people` / `status` have no order of their own and fall back to `sortOrder`. `isUngroupedSectionKey(groupBy, key)` recognises the trailing "No …" / Unassigned section (cross-group drops map it to `UNGROUPED_GROUP_KEY`). `truncateSections(sections, maxTasks)` slices the tail when the total task count exceeds `maxTasks` (a list's hard cap) |
| buildDashboardLists, interpretMembership, applyRuntimeFilter, DashboardList, DashboardListsContext | services/dashboard-lists.ts | Interpreter over `ListDefinition`s for list widgets (called by `useBuiltList`). Per definition (in `sortOrder`): merges the runtime prompt's picks (`ctx.runtimeFilterValues: ReadonlyMap<defId, number[]>`) into the predicate with `applyRuntimeFilter`, evaluates membership through the injected `ctx.evalPredicate` (the app passes `filter-store.createPredicateEvaluator` or `createScreenComposedEvaluator`; without one a custom list matches nothing, with a once-per-build warning), then builds sections with `services/list-sections.buildListSections` using the effective predicate's `personIds` / `tags` as the restrict picks. Returns `DashboardList { id, key, label, todos (members once, in sort order), sections, runtimeFilterUnset? }`. `applyRuntimeFilter(predicate, spec, values)` narrows the declared field (`person` / `status` / `tag`) to the picks (OR), replacing any prior id filter on that field; an empty array is a no-op. A missing pick → `{ todos: [], sections: [], runtimeFilterUnset: true }` so the widget shows its "pick a value" placeholder. `App.tsx`'s Quick Add submit also calls `applyRuntimeFilter` (for `filter-store`'s runtime filter state) |
| buildEntries, dayKey, CalendarEntry, BuildEntriesOptions, compareCalendarEntries, isEntryOverdue, dayOverdueWash, calendarEntryState, dayDots | services/calendar-entries.ts | Bucket-and-enrich helper for the workspace calendar widget. `buildEntries(todos, days, options)` places one entry per shown date type (`options.dateTypes`, default due only): on the due date's day and on the next follow-up's day (`kind: 'due' \| 'followup'`, `day` = midnight), generates virtual recurring due entries within the window via `generateRecurringInstances` (only while due dates are shown), and enriches every entry with people / status. Within a day: due before follow-up, then `sortOrder`. `isEntryOverdue` (own date before today, open; occurrences never), `dayOverdueWash` (a past day: `'due'` over `'followup'`), `calendarEntryState` (`due` / `due-today` / `due-overdue` / `followup` / `followup-overdue`), `dayDots` (≤ 3 compact-month dots, a follow-up always among them). `dayKey(d)` is the canonical bucket key (UTC midnight ISO) |
| buildExportData, selfCheckExportJson, ExportData | services/export-import.ts | Reads every `ALL_DATA_TABLES` table inside one read-only Dexie transaction (consistent snapshot). `selfCheckExportJson(json)` runs a serialized export back through `prepareImportText` and returns the failing table/row/field message or `null` — used by Settings Export JSON (persistent warning, file still saved) and `backupRepository.createSnapshot`. Shared by file-storage, settings export, and backup snapshots. Stamps every export with `__schemaVersion = CURRENT_DB_VERSION` so `detectUnsupportedImport` and the upgrade pipeline work off the embedded marker |
| buildMarkdownExport | services/export-import.ts | Markdown of all tasks (Settings → Export Markdown), from `buildExportData`: `# TODOs`, then one flat `- [ ] title [Status] (due …) (follow-up …)` line per task in manual (`sortOrder`) order (`[Status]` only for statuses with an icon), then a `# Task Details` section with a `### title` block (`**People:**`, `**Tags:**`, `**Notes:**`) for each task that has any of them |
| fileStorageService | services/file-storage.ts | File System Access API sync (file ↔ IndexedDB). **The user decides before anything changes:** a load (startup / Grant Access / attach / `retry()`) reads + `prepareImport`s the file without touching either side, then: any failure (too large, read error, invalid JSON/rows, too new, upgrade failed) → **paused** (`status.paused = {reason, message}`, no restore, never writes; NotFound still forgets the handle); below floor → `onConfirmMigration` (cancel → paused); unsynced browser changes (`dirtySince`), or no sync record while the browser has tasks → `onConflict` → `'file'` (browser snapshot → restore) / `'browser'` (file text → `backupScheduler.snapshotFileBeforeOverwrite` → overwrite) / `'cancel'` (paused) — skipped when `browserMatchesFile` says both sides already hold identical data; clean browser synced with an earlier version of the file → loads it (multi-machine); older-but-supported file → `onConfirmFileUpgrade` first (cancel → paused), then restore + restamp. Missing listeners resolve to the safe answer (stay paused). Change-tracking Dexie hooks stay installed whenever a file is attached (also while paused / needing permission) and mark the browser dirty; writes only happen while `syncEnabled`. `overwriteFileWithBrowser()` (banner "Keep browser data…") backs up the file text then overwrites and resumes. **Every write of existing file content** (confirmed upgrade, below-floor confirm, either conflict choice that rewrites the file, keep-browser overwrite) first backs up the raw file text (private `backupFileText` → `backupScheduler.snapshotFileBeforeOverwrite`); a failed backup or unreadable file pauses with `backup-failed` and nothing is written — any new write path must do the same. `openFile`/`createFile`/`disconnect` reset the sync record. `isConnected` = actively syncing. Failures of the pre-destructive snapshot and of `clearFileHandle` are logged with `console.warn` |
| backupScheduler | services/backup-scheduler.ts | Auto-snapshot every 24h, pre-destructive snapshots (`snapshotBeforeDestructive`), sync-file text snapshots (`snapshotFileBeforeOverwrite`), prune to 10 max; started in App.tsx. The interval body skips while `document.visibilityState !== 'visible'` so a backgrounded tab doesn't accumulate snapshots; an `import.meta.hot?.dispose(() => backupScheduler.stop())` guard tears the timer down on Vite HMR |

| planClearUrgent, clearUrgent, setUrgent, askClearUrgent, ClearUrgentPlan, ClearUrgentPrompt | services/clear-urgent.ts | Turning Urgent off when Urgent is effective (flag OR due within the range). Pure `planClearUrgent(targets, today, range)` → `{ clearFlag, dueSoon, prompt }` over the case table: one task urgent only by date → nothing clears, `Remove the due date?` (Cancel · Remove due date); one flagged + due within the range → flag clears, `Still urgent: due today / Tue 13 / overdue` (Keep due date · Remove due date); flagged with the date outside / none → flag clears, no prompt; several → flags clear, one prompt `k of n tasks stay urgent because of their due dates.` (Keep due dates · Remove their due dates). `clearUrgent(ids)` applies it to stored tasks (`bulkSetUrgent(…, false)` = one undo step, then the prompt through `ui-store.showBulkConfirmation('custom')` — the nested confirm dialog, so it stacks over the task editor; Remove → `bulkClearDueDate`, its own undo step). `setUrgent(ids, on)` = flag all / `clearUrgent`. | parseInput, removeSpans, ParsedInput, CommandProblem | services/natural-language-parser.ts | Parses task text. Only explicit tokens set metadata: `@name` / `@"First Last"` (`MENTION_PATTERN` — `'person'` tokens; `nlp-resolver` looks the names up), `#tag` (whitespace-anchored; deduped by `normalizeTag` slug, first-seen case kept) and **slash commands** (`services/slash-commands`): `/` counts only at the start or after whitespace and a command name runs to whitespace or the end (so `a/b`, `1/2`, URLs, `/etc/hosts` are plain text). Flags `/urgent` `/important` `/focus`; `/due <date>` and `/followup <date\|interval\|none>` read the longest run of up to 4 words that parses (`parseCommandDate`), stopping at the next `@` / `#` / `/` token; `/repeat <frequency>` one word; `/status <name>` one word or a quoted `"Multi word"`. The first `/due` `/followup` `/repeat` `/status` wins. Nothing else is read: plain dates, `by fri`, `every week`, `:status` stay in the title. `ParsedInput` = `text`, `title` (tokens removed), `tokens` (with spans; commands carry `command` + argument `value`), `persons`, `tags`, `status?`, `dueDate?`, `recurrence?`, `urgent` / `important` / `focus`, `nextFollowupAt?`, `followupNone`, and `problems` (`CommandProblem` with span: `unknown` `/urgnt` and `unreadable` (bad / missing argument) and `duplicate` stay in the title; `ignored` = `/repeat` without `/due` — dropped from the title, `recurrence` kept so a due date picked in the editor can anchor it; `unmatched` is the resolver's unknown status). `parseInput(text, today = new Date())`. `removeSpans` rebuilds a title without given spans |
| SLASH_COMMANDS, lookupSlashCommand, takesArgument, parseCommandDate, parseRepeatArgument, REPEAT_FREQUENCIES, DATE_ARGUMENT_HINT | services/slash-commands.ts | The command table (menu order: urgent, important, focus, due, followup (alias `follow-up`), repeat, status; description; argument label). `parseCommandDate` = `utils/followup.parseFollowupInput(text, today, 'future')` — an interval `Nd/Nw/Nm/Ny`, a relative date (`utils/date-phrase`), `MM/DD[/YY[YY]]`, `24 Oct`, ISO — one date grammar for `/due`, `/followup` and the follow-up inputs |
| computeAutocomplete, applyAutocompletePick, isVisible, isSelectable, isPartialDateArgument, AutocompleteView, AutocompleteRow, AutocompleteItem | services/nlp-autocomplete.ts | The task-text autocomplete as pure functions over (text, cursor) — shared by `useNlpAutocomplete` (React inputs) and any other editor. Triggers at token start: `@` (people: substring or exact initials, `"` ignored; create row when nothing matches, not while a quote is open), `#` (tags: prefix; create row), `/` when `commands` is on (command list filtered by prefix, unfiltered list has the footer; no match → no popup). After an argument command and a space the view switches to its argument (`mode: 'argument'`, `anchor` stays on the `/`): `/due` / `/followup` suggestions (`today tomorrow mon fri 1w` / the quick intervals with the Settings default marked + `none`), the live parse of a valid argument, suggestions filtered by a half-typed word, the grammar hint alone while a longer date is in progress (`next`, `in 3`, `24`, `wed`…), else an error row; `/status` statuses by prefix (multi-word names inserted quoted, followed across an open quote); `/repeat` frequencies (`from Mon 12` / `every Mon` when the text has a `/due`). A space after a complete argument closes it. `applyAutocompletePick` replaces `[from, to)` with the token + a space; `reopen` when a command takes an argument |
| tokenTints, TokenTint, TintSpan | services/nlp-token-tints.ts | Tint spans for typed task text (Quick Add's field mirror): `chip` (tags, known people, `/status`, a token being typed), `new` (`@name` matching nobody), `due` / `urgent` / `followup` (`/important`, `/followup`) / `accent` (`/focus`, `/repeat`), `error` (unreadable argument, unknown status), `ignored` (`/repeat` without `/due`, a repeated command); unknown commands are untinted |
| makeRecurrenceRule | services/recurrence.ts | Build a RecurrenceRule, capturing originalDayOfMonth for monthly/quarterly/yearly |
| computeNextDueDate | services/recurrence.ts | Advances a due date by one recurrence interval, skipping past dates |
| recurrenceAnchor, advanceRecurring | services/recurrence.ts | `recurrenceAnchor(todo)` returns the `dueDate` (null without one). `advanceRecurring(todo)` computes the next occurrence's `{dueDate}` — used by `todo-store.toggleComplete` / `bulkSetCompleted`. **Day-of-month integrity:** monthly/quarterly/yearly read `originalDayOfMonth` from the rule (captured at `makeRecurrenceRule`), so a Jan-31 monthly that lands on Feb-28 elevates back to Mar-31; a Feb-29 yearly that lands on Feb-28 in year N+1 elevates back to Feb-29 in the next leap year. **DST:** `next.setHours(0, 0, 0, 0)` re-anchors to local midnight after every interval bump so spring-forward / fall-back can't leak a 23:00 / 01:00 timestamp into stored rows. **Repository-level mirror:** `data/recurrence-anchor.ts` exports `hasRecurrenceAnchor` — a pure predicate over `Pick<TodoItem, 'dueDate'>` that returns true iff this same anchor would be non-null. `todoRepository.update` / `bulkUpdate` use it to drop orphaned `recurrenceRule` from changes before persistence, and the `auditData` orphan-recurrence-rule pass uses it to detect legacy rows, so the runtime "rule never fires" condition and the persisted-shape "rule has no anchor" condition stay aligned in one predicate |
| generateRecurringInstances | services/recurrence.ts | Generates all recurring dates within a date range for calendar display (`buildEntries`' virtual occurrences) |
| resolveInput, ResolvedInput | services/nlp-resolver.ts | `resolveInput(parsed, people, statuses?)` matches parsed names against known entities (people: case-insensitive exact/prefix/initials/first-name; `/status`: exact-then-prefix); unmatched people land in `unmatchedPersons` (created on submit by `resolveUnmatchedPeople`); a status matching nothing stays in the title, lands in `unmatchedStatuses` and adds an `unmatched` problem. Returns `title`, `textWithoutCommands` (the text minus command tokens, `@` / `#` kept — the editor's title after a Quick Add handoff), dueDate, recurrence, personIds[], statusId, `urgent` / `important` / `focus` (only when set), `nextFollowupAt` / `followupNone`, `problems`, plus the pass-through `tags: string[]` (converted to ids by `resolveTags`) |
| resolveTags, TagStoreLike | services/nlp-resolver.ts | Async resolve-or-create: for each `#foo` name, look up the existing tag case-insensitively in `ctx.tagStore.tags` and return its id; on a miss, `tagStore.add(name, DEFAULT_ENTITY_COLOR)` and use the new id. Returns ids in input order, deduped. A local `createdByLower` cache coalesces duplicate new names within the same call so `#Foo #foo` creates one tag, not two; a `TagLimitError` (registry at `settings.maxTags`) stops further creates and returns what resolved. Repository-level concurrency (two near-simultaneous NLP calls racing to create the same name) is handled by `tagRepository.getOrCreate` — the single-transaction upsert serialises the check-and-insert so only one row lands, and `tagStore.add` is idempotent on a case-insensitive match |
| resolveUnmatchedPeople, PersonStoreLike | services/nlp-resolver.ts | Async lookup-or-create for `@name` tokens that matched nobody: each name (deduped case-insensitively, blanks skipped) goes through `ctx.personStore.getOrCreate` — case-insensitive name match first, otherwise a new person with `generateInitials` initials and no color. Returns ids in input order. The people counterpart of `resolveTags` |
