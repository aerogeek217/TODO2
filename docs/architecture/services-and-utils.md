# Services, Hooks & Utils

Detail reference for `src/services/` (non-UI logic), `src/hooks/` (custom React hooks), and `src/utils/` (pure utilities). Load when touching NLP, recurrence, file storage, dashboard list interpretation, drag-and-drop logic, keyboard shortcuts, or date helpers.

| Section, ListSectionsSpec, ListSectionsContext, buildListSections, listSortComparator, truncateSections | services/list-sections.ts | The one section builder for every list surface — the list page (`ListView`) and list widgets (`buildDashboardLists` → `ListDefinitionBody`) — so the same definition yields the same sections everywhere. `buildListSections(members, {groupBy, sortBy, restrictToPersonIds?, restrictToTagIds?}, ctx)` sorts with `listSortComparator(sortBy)` first (so every section comes out sorted; grouping keeps input order), then partitions through `utils/task-grouping.partitionByGroup`. Sections: due / follow-up → Overdue (`--color-overdue`) / Today (`--color-accent`) / This Week (`--color-text-secondary`) / Later (`--color-text-muted`), then "No Due Date" / "No Follow-up" (key `none`; every trailing "No …" / Unassigned section is `--color-text-muted`); people → person name, accent `person.color` (undefined when unset), alphabetical, then "Unassigned"; status → registry `sortOrder`, status color, then "No Status"; project → registry `sortOrder`, accent `--color-accent`, then "No Project"; tag → `#name`, tag color, alphabetical, then "No Tag"; `none` → one `all` section (none when empty). Restrict mode (the effective filter's person / tag picks): only those sections, in pick order; the trailing sentinel is dropped unless the person picks include `0` (Unassigned). A task with several people / tags appears in each of their sections. `listSortComparator`: `manual` → `sortOrder` then id; `name` → `title.localeCompare` then `sortOrder`; `deadline` / `followup` → `compareTodosByDate` (undated last); `created` / `people` / `project` / `status` have no order of their own and fall back to manual. `truncateSections(sections, maxTasks)` slices the tail when the total task count exceeds `maxTasks` (the list page's hard limit) |
| buildDashboardLists, interpretMembership, applyRuntimeFilter, DashboardList, DashboardListsContext | services/dashboard-lists.ts | Interpreter over `ListDefinition`s for list widgets. Per definition (in `sortOrder`): merges the runtime prompt's picks (`ctx.runtimeFilterValues: ReadonlyMap<defId, number[]>`) into the predicate with `applyRuntimeFilter`, evaluates membership through the injected `ctx.evalPredicate` (the app passes `filter-store.createPredicateEvaluator`; without one a custom list matches nothing, with a once-per-build warning), then builds sections with `services/list-sections.buildListSections` using the effective predicate's `personIds` / `tags` as the restrict picks. Returns `DashboardList { id, key, label, todos (members once, in sort order), sections, runtimeFilterUnset? }`. `applyRuntimeFilter(predicate, spec, values)` narrows the declared field (`person` / `project` / `status` / `tag`) to the picks (OR), replacing any prior id filter on that field; an empty array is a no-op. A missing pick → `{ todos: [], sections: [], runtimeFilterUnset: true }` so the surface shows a "Pick a {label}…" placeholder. `ListView` calls `applyRuntimeFilter` directly (round-tripping its filter-store criteria through `criteriaToPredicate` / `predicateToCriteria`) |

| fileStorageService | services/file-storage.ts | File System Access API sync (file ↔ IndexedDB). **The user decides before anything changes:** a load (startup / Grant Access / attach / `retry()`) reads + `prepareImport`s the file without touching either side, then: any failure (too large, read error, invalid JSON/rows, too new, upgrade failed) → **paused** (`status.paused = {reason, message}`, no restore, never writes; NotFound still forgets the handle); below floor → `onConfirmMigration` (cancel → paused); unsynced browser changes (`dirtySince`), or no sync record while the browser has tasks → `onConflict` → `'file'` (browser snapshot → restore) / `'browser'` (file text → `backupScheduler.snapshotFileBeforeOverwrite` → overwrite) / `'cancel'` (paused) — skipped when `browserMatchesFile` says both sides already hold identical data; clean browser synced with an earlier version of the file → loads it (multi-machine); older-but-supported file → `onConfirmFileUpgrade` first (cancel → paused), then restore + restamp. Missing listeners resolve to the safe answer (stay paused). Change-tracking Dexie hooks stay installed whenever a file is attached (also while paused / needing permission) and mark the browser dirty; writes only happen while `syncEnabled`. `overwriteFileWithBrowser()` (banner "Keep browser data…") backs up the file text then overwrites and resumes. **Every write of existing file content** (confirmed upgrade, below-floor confirm, either conflict choice that rewrites the file, keep-browser overwrite) first backs up the raw file text (private `backupFileText` → `backupScheduler.snapshotFileBeforeOverwrite`); a failed backup or unreadable file pauses with `backup-failed` and nothing is written — any new write path must do the same. `openFile`/`createFile`/`disconnect` reset the sync record. `isConnected` = actively syncing.
