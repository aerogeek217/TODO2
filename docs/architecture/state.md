# State (Zustand Stores)

Detail reference for `src/stores/`. Load when touching store APIs, filter semantics, undo, selection, or cross-store helpers.

## Stores

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| useTodoStore | stores/todo-store.ts | All tasks (`loadAll` / memoized `ensureAllLoaded`), CRUD and bulk operations: `addMany(items, { description, snackbar? })` (every create — Quick Add, the editor, notes, Make a task, through `services/create-task` / `note-tasks`, which stamp Settings' default status and next follow-up: tasks with their people / tag ids in one transaction, last in order — the repository picks `sortOrder` in its insert transaction, so creates that start together never share one; the rows come back from the insert itself; reloads the assignment caches; one undo step — undo takes them out, redo puts them back as they were when undone), `update(id, changes)` (`TodoChanges`: just the fields the caller changed — never a whole row, so a caller holding an old copy can't write it back; fields already holding the value are skipped; written as a patch via `todoRepository.update(id, changes)`; undo / redo / a failed write's rollback touch only those fields; no change → no write, no undo step; **never rejects** — a failed write is rolled back, the snackbar says `Couldn't save your change to "<title>".` and it resolves `false` (else `true`), so fire-and-forget callers leave no unhandled rejection; `checkin-reply/apply` stops on `false`), `toggleComplete` (advances recurring tasks via `advanceRecurring`), `remove`, `bulkSetCompleted` (one `bulkUpdate` transaction for the completions and the recurring advances, its undo too; a failed write rolls back and re-reads the tasks — `loadAll`), `bulkSetStatus`, `bulkSetDeadline`, `bulkSetFollowup`, `bulkSetLastFollowup`, `bulkSetFocus` (on → `focus: true`, off → key removed; one undo step), `bulkSetUrgent` / `bulkSetImportant` (same shape on `urgent` / `important`), `setMarkerFlags(changes, description)` (per-task Urgent / Important / Focus writes — an Eisenhower drop, `services/eisenhower-drop`; one undo step with the snackbar), `bulkClearDueDate(ids)` (removes due dates — the clearing-Urgent prompt's action; one undo step with the snackbar `Removed the due date` / `Removed N due dates`), `markFollowedUp(ids, { next?, description?, detail? })` ("Mark followed up" — every path: the task menu, the bulk bar, the follow-up popover, the editor, a check-in sent or its reply applied: last = now, next = the given `next` (the popover's edited field; `null` = none) on every task, else **per task** (cr25 P6, `utils/followup.nextAfterFollowup`): a next follow-up after today is kept — not written, so undo / a failed write's rollback leave it as it is then — and one today / past / none gets `settings-store.autoNextFollowup(now)` — today + the interval, none while the automatic next follow-up is off; one timestamp shared by store + DB; one undo step with snackbar — default `followedUpName`: `Followed up · next follow-up <date>` / `Followed up · no next follow-up` / `Followed up · next follow-up kept` (`… follow-ups kept` for several) / mixed `Followed up · next follow-up <date> · 2 kept`; `description` names it, e.g. a check-in send's `Check-in for <name> opened · N tasks followed up`; undo restores the last follow-up everywhere and the next follow-up only where it was written; redo sets the same given `next`, else the rule again per task from the redo's now), `remove` / `bulkRemove` (undo puts back the tasks with their people, tags, dependent rows and **event history** — the repository's delete returns the deleted `todoEvents` rows; a redo captures afresh, so the next undo brings back what the tasks had then; more than `BULK_DELETE_SNAPSHOT_MIN` (5) tasks → `takeSafetySnapshot` first, outside the tracked write; cancelled → nothing deleted; without a backup the snackbar says `Delete N tasks — no backup was taken`; a redo skips the gate; `opts.beforeDelete` runs only once the delete goes ahead — the bulk confirm clears the selection and closes the editor there, so a cancel keeps them), `duplicate(id)` (copies title / notes / dates incl. next follow-up / status / recurrence / the urgent and important flags (not focus), with the source's people and tags in one insert transaction, then its status updates — same days and texts, a fresh `createdAt`, best effort through `status-update-store.addRows`; undo / redo as a create's), `purgeCompleted(ids)` → `PurgeOutcome` (`done` with `deleted` + `noBackup`, or `cancelled` when the backup failed and the user cancelled; deletes only the given ids still completed **in the DB**, re-read after the backup gate (`takeSafetySnapshot`); called only after the launch prompt / Settings cleanup confirm; expiry keyed on `completedAt`), **One take / put-back for "a task goes / comes back"** (cr31 A1): every delete, a delete's redo and a create's undo run through the store's `takeTasks(ids)` — it reads each row as it is now (the store's copy, the database's for a task not loaded), its people and tags and its dependent rows (`stores/task-dependents.captureDependents`: list ranks, status updates, subtasks), deletes them (`todoRepository.bulkDelete`, which returns the events), and drops them from the stores (`forgetDependents`, the assignment maps' entries too); `putBackTasks` restores rows, joins and events in one transaction (`restoreManyWithAssignments`), reloads the assignment caches and restores the dependent rows (`restoreDependents`). So a change made after a create or between an undo and a redo without an undo step of its own (a manual-order move, a sync-file load) survives the round trip, and the redo of an undone create puts the task back with its `created` event, so the dashboard trend reads the same. A new kind of task-owned row is one edit in `task-dependents` (and `data/tables.TASK_CHILD_TABLE_NAMES`, which `bulkDelete` walks). **One `modifiedAt` per write:** each write mints its timestamp once and passes it to the repository (`update` / `complete` / `bulkUpdate` take a `Stamp`), so the store and the database hold the same value. **Undo puts back the task's earlier `modifiedAt`, redo the one the step wrote** (cr32, `utils/task-stamps`): each step keeps its `StampChanges` (each task's stamp before → after) and its undo / redo write them — inverted / as they are — as a guarded `Stamp`, only where the task still holds the stamp the other left (a task touched since keeps its newer one), in the database (in the write's transaction) and the store alike (`stampAfter`). The same for every undoable task write: a field edit (`patchTodo`'s `stamp`), a completion (`writeCompletion`), a recurring advance, `bulkSetCompleted` (its undo restores every task it wrote, a no-op completion's too), `bulkUpdateField`, `setMarkerFlags`, `markFollowedUp` (a redo still counts the rule from its own now, the stamp the original's), a status deleted from Settings (`status-store`), and the entry stores' and the assignments' writes; a delete's undo puts the row back with its stored stamp. `purgeCompleted` only deletes and forgets (no undo). Optimistic completion state mirrors the repository's `completedAt` rule (`resolveCompletedAt`). `todosVersion: number` monotonic counter — bumped on every mutation that changes the id-set (addMany / duplicate / remove / bulkRemove / their undo and redo / purgeCompleted / load); **not** bumped on field edits (update / toggleComplete / bulkSet*). Surfaces that only care about membership changes use `${todos.length}:${todosVersion}` as an O(1) cache key — as `useEntityAssignmentsForLoadedTodos` (the workspace) does, subscribing to the count and `todosVersion` separately to gate the assignment-join-load effect. `toggleComplete` shows the undo snackbar for every completion (D19: a completed row may fold out of its list), one undo step as before; reopening a task stays quiet, a recurring task's advance keeps its own. |

| useNoteStore | stores/note-store.ts | The single global "outside-tasks" note shown by every notes widget: `notes` map + `activeId`, debounced `setContent(id, content)` (`SAVE_DEBOUNCE_MS` 500; the page hidden or closed saves the pending text at once — `utils/page-hide`) + `flush`, `lastSavedAt`. `load()` seeds the row if missing (`noteRepository.getOrSeedGlobal`, one transaction); concurrent loads share one (`loadInFlight`); text still unsaved stays what the store shows. | createAssignmentActions | stores/assignment-helpers.ts | Factory for assign/unassign/bulk/load actions shared by person + tag stores; a bulk assign / unassign is one transaction (the repository's `bulkAssign*` / `bulkUnassign*`); **an assignment is activity on its task** (cr32): each write stamps the tasks whose people / tags it changed (`modifiedAt`, in the join write's transaction — a `TaskTouch`) and tells the todo store (`task-hooks.notifyTasksStamped`), so the stale fade and the Modified filter / sort follow; its undo puts back each task's earlier stamp, its redo the one it wrote, each only where the task still holds the other (`utils/task-stamps`). | makeEnsureLoaded | stores/store-helpers.ts | `makeEnsureLoaded(load, isLoaded)` → an `ensureLoaded()` callers can fire on every mount without re-hitting IndexedDB. Concurrent callers share the in-flight load; once `isLoaded()` — the store's `loaded` flag, set only by a load whose read succeeded — is true, calls are a no-op. A failed load (reported by `loadFresh`) leaves the flag false, so the next `ensureLoaded()` reads again; the promise never rejects. The flag is store state, so it resets with the store. Used by `useTodoStore.ensureAllLoaded`, `usePersonStore.ensureLoaded`, `useStatusStore.ensureLoaded`, `useTagStore.ensureLoaded`, `useListDefinitionStore.ensureLoaded` (`useListOrderStore.ensureLoaded` and `useStatusUpdateStore.ensureLoaded` follow the same rule on their own `loaded`). | trackWrite, readFresh | stores/store-helpers.ts | Keep a `load()` from putting back rows an edit changed while its read was in flight. Loads read through `readFresh`: it waits until no tracked write is in flight, reads, and reads again if a write started meanwhile (gives up after 5 reads with a warning).
