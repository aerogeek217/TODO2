# State (Zustand Stores)

Detail reference for `src/stores/`. Load when touching store APIs, filter semantics, undo, selection, or cross-store helpers.

## Stores

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| useTodoStore | stores/todo-store.ts | All tasks (`loadAll` / memoized `ensureAllLoaded`), CRUD and bulk operations: `add(title)` (stamps Settings' default status and `nextFollowupAt` = `settings-store.newTaskDefaultFollowup(now)` (today + `followupDefaultInterval`, none while `autoFollowup` is off); goes last — the repository picks `sortOrder` in its insert transaction, so adds that start together never share one; the row comes back from the insert itself; undo deletes it, redo puts it back as it was when undone — row, people, tags, list ranks and events read then, as a delete's undo does), `addMany(items, { description, snackbar? })` (tasks with their people / tag ids in one transaction, last in order; one undo step — undo deletes them, redo puts the same rows and joins back; reloads the assignment caches), `update(id, changes)` (`TodoChanges`: just the fields the caller changed — never a whole row, so a caller holding an old copy can't write it back; fields already holding the value are skipped; written as a patch via `todoRepository.update(id, changes)`; undo / redo / a failed write's rollback touch only those fields; no change → no write, no undo step; **never rejects** — a failed write is rolled back, the snackbar says `Couldn't save your change to "<title>".` and it resolves `false` (else `true`), so fire-and-forget callers leave no unhandled rejection; `checkin-reply/apply` stops on `false`), `toggleComplete` (advances recurring tasks via `advanceRecurring`), `remove`, `bulkSetCompleted` (one `bulkUpdate` transaction for the completions and the recurring advances, its undo too; a failed write rolls back and re-reads the tasks — `loadAll`), `bulkSetStatus`, `bulkSetDeadline`, `bulkSetFollowup`, `bulkSetLastFollowup`, `bulkSetFocus` (on → `focus: true`, off → key removed; one undo step), `bulkSetUrgent` / `bulkSetImportant` (same shape on `urgent` / `important`), `setMarkerFlags(changes, description)` (per-task Urgent / Important / Focus writes — an Eisenhower drop, `services/eisenhower-drop`; one undo step with the snackbar), `bulkClearDueDate(ids)` (removes due dates — the clearing-Urgent prompt's action; one undo step with the snackbar `Removed the due date` / `Removed N due dates`), `markFollowedUp(ids, { next?, description?, detail? })` ("Mark followed up" — every path: the task menu, the bulk bar, the follow-up popover, the editor, a check-in sent or its reply applied: last = now, next = the given `next` (the popover's field; `null` = none) else `settings-store.autoNextFollowup(now)` — today + the interval, none while the automatic next follow-up is off; one timestamp shared by store + DB; one undo step with snackbar — default `Followed up · next follow-up <date>` / `Followed up · no next follow-up`, `description` names it, e.g. a check-in send's `Check-in for <name> opened · N tasks followed up`; redo sets the same given `next`, else the rule again), `remove` / `bulkRemove` (undo puts back the tasks with their people, tags, list ranks and **event history** — the repository's delete returns the deleted `todoEvents` rows; more than `BULK_DELETE_SNAPSHOT_MIN` (5) tasks → `takeSafetySnapshot` first, outside the tracked write; cancelled → nothing deleted; without a backup the snackbar says `Delete N tasks — no backup was taken`; a redo skips the gate; `opts.beforeDelete` runs only once the delete goes ahead — the bulk confirm clears the selection and closes the editor there, so a cancel keeps them), `duplicate(id)` (copies title / notes / progress / dates incl. next follow-up / status / recurrence / the urgent and important flags (not focus), with the source's people and tags in one insert transaction; undo / redo as `add`'s), `purgeCompleted(ids)` → `PurgeOutcome` (`done` with `deleted` + `noBackup`, or `cancelled` when the backup failed and the user cancelled; deletes only the given ids still completed **in the DB**, re-read after the backup gate (`takeSafetySnapshot`); called only after the launch prompt / Settings cleanup confirm; expiry keyed on `completedAt`), internal `_restore` (task + people / tags + events) / `_removeNoUndo` (returns the deleted events) for undo / redo — the redo of an undone `add` / `addMany` / `duplicate` puts the task back with its `created` event, so the dashboard trend reads the same. **One `modifiedAt` per write:** each write mints its timestamp once and passes it to the repository (`update` / `complete` / `bulkUpdate` take `now`), so the store and the database hold the same value; an undo that restores an earlier `modifiedAt` writes that value to both. Deletes also drop the tasks' manual-order ranks from `list-order-store` (`forgetTodos`). Optimistic completion state mirrors the repository's `completedAt` rule (`resolveCompletedAt`). `todosVersion: number` monotonic counter — bumped on every mutation that changes the id-set (add / duplicate / remove / bulkRemove / _restore / _removeNoUndo / purgeCompleted / load); **not** bumped on field edits (update / toggleComplete / bulkSet*). Surfaces that only care about membership changes use `${todos.length}:${todosVersion}` as an O(1) cache key — consumed by `useEntityAssignmentsForTodos` (the workspace) to gate the assignment-join-load effect |
| usePersonStore | stores/person-store.ts | People list, CRUD (`add(name, initials, color?)` — the color key is written only when a color is given; `getOrCreate(name)` — lookup-or-create by trimmed name, case-insensitive, in memory then `personRepository.getOrCreate`; new people get `generateInitials` initials and no color; used by every person picker's Create and by NLP `@name`; `update(person)` writes the whole row, so a cleared color drops the key; `remove` is undoable — `captureJoinRows` + `personRepository.restoreWithJoins`, folding a same-named person created meanwhile into the restored one), `ensureLoaded`, `assignedPeopleMap`, todo-person assignments (`loadAssignments`, assign / unassign / bulk with undo via `createAssignmentActions`). A failed `update` rolls back only that person (and only while it still holds this edit), in `people` and the map. `countTasks(personId)` — how many tasks (loaded or not) the person is on, read from the database (the delete confirm). `forgetPeople(ids)` drops people the database no longer has from `people` and the map (Settings' Unused people & tags removal, `services/remove-entities`) |
| useStatusStore | stores/status-store.ts | Status definitions: load / `ensureLoaded`, add (goes last — `statusRepository.insertLast` picks the sort order and refuses a name already stored, ignoring case, in its transaction), update (a failure rolls back only that status), remove (cascade delete clears todos + the default-status setting, with undo), reorder (drag sort with persisted sortOrder). `selectTodoCountByStatusId(statusId)` — store-derived count for StatusEditor's delete confirmation, read from `useTodoStore.todos`; StatusEditor calls `useTodoStore.ensureAllLoaded()` so the cache is populated |
| useTagStore | stores/tag-store.ts | Normalized tag registry (mirrors `usePersonStore` shape): `tags: Tag[]`, `assignedTagsMap: Map<number, Tag[]>`, `load` / `ensureLoaded`, `loadAssignments(todoIds)`, `add(name, color?)` (defaults to `DEFAULT_ENTITY_COLOR`; idempotent on a case-insensitive name match via `tagRepository.getOrCreate`; no cap on the number of tags), `update` (a failure rolls back only that tag, in `tags` and the map), `remove` (with undo — re-adds the cascaded `todoTags` joins via `captureJoinRows` + `tagRepository.restoreWithJoins`, folding a same-named tag created meanwhile into the restored one), `countTasks(tagId)` — how many tasks (loaded or not) carry the tag, read from the database (the delete confirm), `forgetTags(ids)` (as `forgetPeople`), `assignTag` / `unassignTag` / `bulkAssignTag` / `bulkUnassignTag`. Uniqueness is enforced case-insensitively at the repository layer; `#Foo` / `#foo` resolve to the same registry row. Task counts per tag: `assignment-helpers.countTodosByEntity(assignedTagsMap)` (callers load assignments for every task first, as `TagEditor` does). A former project is a `Project: <name>` tag (schema v60) |
| useNoteStore | stores/note-store.ts | The single global "outside-tasks" note shown by every notes widget: `notes` map + `activeId`, debounced `setContent(id, content)` (`SAVE_DEBOUNCE_MS` 500; the page hidden or closed saves the pending text at once — `utils/page-hide`) + `flush`, `lastSavedAt`. `load()` seeds the row if missing (`noteRepository.getOrSeedGlobal`, one transaction); concurrent loads share one (`loadInFlight`); text still unsaved stays what the store shows. The latest edit is `pending` (sequenced) until a save of it or newer text succeeds: saves run one at a time, each writes the latest text (`saveContent` — content + `modifiedAt` only) and never puts older text back into the store. A failed save keeps the text, sets `saveFailed`, shows `Couldn't save your notes. They'll be saved with your next change.` once (undo snackbar notice) and is retried by the next change or `flush`; `flush` never rejects. `discardPending()` drops unsaved text and its scheduled save (`refreshAllStores` calls it). `holdForDataReplace()` — called before every data replace takes its backup (`services/replace-data` — every replace goes through it; a sync file load holds from before its load decision, `withDataReplaceHold`): holds nest (only the outermost saves and drops — text typed during an outer hold stays pending); saves the text typed so far (`flush`, which also waits for a save already started — so the pre-op backup holds it; if that save fails the text is dropped and the replace goes ahead), then holds every later save (`replaceHolds > 0`; text typed meanwhile is dropped by the reload) until the returned release — called after the stores reload, or when the replace was cancelled or failed (text typed meanwhile is then saved). So no save can land after a replace, and text typed just before one is recoverable from Settings › Backups. It waits only on note saves (untracked, never on a load), so it can't deadlock with the replace `resetNoteSaves()` (tests sharing one module instance) clears the save timer and the save chain. |
| useWorkspaceStore | stores/workspace-store.ts | Workspace layouts: `layouts` (saved, in the tabs' and the picker's order: `sortOrder`, then oldest first; `reorderLayouts(orderedIds, description?)` shows and saves a new order at once — not a layout change, nothing becomes unsaved — as one undo step (`Reordered layouts`, shown in the snackbar; undo / redo re-save the order and throw on a failed write, so the entry stays); `moveLayout(id, toIndex)` = one layout moved (the tabs' drag, Move left / right, the picker's drag; `Moved layout “<name>”`; no move = no step); layouts it leaves out keep their order after the named ones; a failed write puts the order back with a notice, resolves `false` and leaves no undo step; Save as and New layout put the new layout last), `activeLayoutId`, `working` (in-memory working copy of the open layout), `saved` (its stored version; `null` for a kept new layout not saved yet), `previousLayoutId` (while such a layout is open: the layout Discard goes back to), `isDirty`, `repairedIds`, `hydrated`. **The lens pick** (D15): `setLens(lensId | null)` is view state on the open layout (`lensId`, written at once like the active tab, never unsaved; `null` removes the key — `utils/workspace-layout-ops.setLayoutLens`); `setLayoutsLens(layoutIds, lensId)` sets it on any layouts (the open one through the view-state path, the others in `layouts` and as stored) — a deleted lens's layouts going to No lens and its undo. A change of `activeLayoutId` (a layout switch) puts a lifted lens back (`ui-store.setLensLifted(false)`). **Kept for a reload:** after every change (but a `live` resize — see below) the store writes what is unsaved — the working copy when its structure differs from `saved` (with `saved`'s body as its base), or a new layout an older build kept — to `data/draft-storage` (`localStorage`, never Dexie), or forgets it. The page load's first `init()` (concurrent first calls share it) reads it before opening and takes it back unsaved only while the stored layout is the open one with the same structure as the base — after repointing the draft at the lists the stored layout now shows at the same tabs (`utils/workspace-layout-ops.listIdChanges`: a layout given copies of the lists it shared by the v68 upgrade) — and the draft shows no other layout's list (else dropped with the notice `Unsaved changes to layout “<name>” were dropped: they showed another layout’s list.`); a kept new layout only while it shows no list (every list belongs to a stored layout; else dropped with `The unsaved new layout “<name>” was dropped: a layout shows only its own lists, and it wasn’t stored yet.`); anything else is forgotten. **Writes land before the screen says so:** `save` (→ `true` / `false`), `saveAs` (→ id / `null`) and `rename` (→ `false`) change state only after the write succeeds; a failed one keeps the layout unsaved / the old name and says so in the snackbar (`Couldn't save layout "…".`), never rejects; the unsaved-changes prompt stays open when its Save fails. A failed view-state write is logged and kept for the session. **Repaired on read:** a layout `layoutRepository` repaired (`ReadLayout.fixes` — e.g. a retired widget kind dropped) opens without the bad parts but unsaved (`repairedIds` keeps `isDirty` true, also after `discard`), and the snackbar says `Repaired layout "<name>" — <fixes>. Save it to keep the repair.` (logged too). Nothing writes the repair back but `save()` (or Data integrity cleanup): its view-state edits stay in memory, `load` writes only `lastUsedAt` and `rename` only the name. `init()` (idempotent: `layoutRepository.ensureDefault`, then opens the `activeLayoutId` layout, falling back to the most recently used; drops any working copy — call after startup has loaded the sync file; the first call of a page load reopens the kept draft, see above), `createLayout(name)` (stores an empty layout under the name, last, and opens it — callers ask about unsaved changes first; `null` for a blank name or a failed write, with `Couldn't create layout "…".`). Only an unsaved new layout an older build kept (draft `kind: 'new'`) still opens unstored — id `UNSAVED_LAYOUT_ID`, `saved` null, dirty; `save()` inserts it under its name (as `saveAs`) and opens it, `discard()` goes back to `previousLayoutId`, `rename(UNSAVED_LAYOUT_ID, name)` renames it in memory, `load(id)` (switches unconditionally — callers resolve unsaved changes first; stamps `lastUsedAt` with a field patch), `save()`, `saveAs(name)` (the new layout becomes current and saved; the source keeps its last saved state), `discard()`, `rename(id, name)` (never dirty), `delete(id)` (refuses the last; deleting the open layout opens the most recently used). **A layout's lists** (`owner: { layoutId }` — every list but the Eisenhower's) follow their layout: after `save` writes the layout, the lists it owns that neither it nor an edit made meanwhile shows are deleted with their ranks and drafts (`layoutRepository.pruneOwnedLists` → `forgetDeletedLists`; a failure only leaves them for the next Save), as one undo step with the snackbar `Removed the list “<name>”` / `Removed N lists` (Undo brings them back as the layout's lists with their ranks — `restoreLists` — and a tab for each in the layout's first cell, an unsaved edit, so the next Save or page load keeps them; it runs only while that layout is open, else it throws `UndoRefused` `Open layout “<layout>” to bring back “<name>”.` and stays to try again; once the layout is gone nothing comes back and it notifies `“<name>” can’t come back: its layout is gone.`; Redo closes those tabs and removes the lists again unless the layout shows them otherwise by then — `pruneOwnedLists` restricted to those ids); a list another layout's stored row names is handed to that layout instead (`OwnedListsRemoved.handedOver`, the list store reloaded) — closing a list's last tab or Change list away is a layout edit, so `discard` keeps a list the stored layout shows; `discard` (and the page load's first open when it drops the edits: no kept draft, or one not taken back — also a kept draft of another layout) deletes the layout's own lists only the dropped edits showed. Every removal reads the stored rows in its transaction: a list the stored row names stays (a part the layout repair dropped still counts until a Save writes the repair — then such lists go, as part of that Save's undo step); `saveAs` copies the ones the working copy shows for the new layout (each as edited — its draft, a blank draft name keeping the saved name —, with its ranks; `layoutRepository.insertWithListCopies`, one transaction, the new layout's tabs repointed), reloads the list / rank stores, then drops the source layout's own lists its saved body doesn't show (the ones only its edits showed — now copied); `delete` deletes the layout's lists, ranks and drafts with it (`deleteUnlessLast`, one transaction; not undoable — the confirm says so). The Eisenhower's list belongs to no layout: none of these touch it. **Structural edits** change only `working` and recompute `isDirty = repaired || !layoutStructureEqual(working, saved)`: `addWidget(kind, target, seed?)`, `moveTab(tabId, target)`, `movePanel(panelId, target)` (a whole cell or band), `closeTab`, `closeCell` (a cell or band), `splitCell(cellId, 'right'\|'below')`, `patchTabConfig(tabId, kind, patch)`, `changeTabKind(tabId, kind, seed?)`; one that brings the structure back to `saved`'s takes `saved`'s sizes too (`copySizes(…, 'all')`: a column added and closed again leaves its neighbours as they were). A structural edit that would make the layout show a list it doesn't own — a list tab's list or a dashboard's list tile naming another layout's list, the Eisenhower's or one with no owner (`foreignListRefs`: only lists the edit adds; a list that no longer exists is no one's) — is refused: nothing changes, `addWidget` returns `null`. **View-state edits** — `setActiveTab(tabId)`, `setCellCollapsed(panelId, collapsed)` (a cell or band), `patchTabViewState(tabId, kind, patch)` — apply to `working` and to `saved` (where the target exists there) and write `saved` to Dexie at once (`layoutRepository.updateView`; last write wins; `modifiedAt` untouched; never dirty; Discard keeps them; no undo). While a Save's write runs, each also goes onto the layout it writes (`viewEditsDuringSave`) and to its stored row after it, even when the layout saved before had nothing for it (a tab or size only the Save brings). **Sizes are view state:** `setColumnWeights` / `setCellWeights` (batched, by id) and `setBandHeight(edge, px)` change `working` and go onto `saved` through the same path, per size group (`copySizes`) and only where `saved` has the same parts — the same columns, that column with the same cells, that band; among parts an unsaved edit changed (a new column / cell / band) the size stays in `working` (and its kept draft) for Save to write. They take `{ live: true }` for the frames of a divider drag — only `working` changes, no write per frame — and `endResize()`, which the divider calls once when the drag ends, saves what the frames changed (a keyboard step or double-click saves at once). A kept draft taken back on a page load puts its sizes onto `saved` the same way (a draft an older build kept for a resize alone ends up saved, with no unsaved change). A repaired-and-unsaved layout keeps them in memory until Save, as the rest of its view state. New column / cell / tab ids are random and checked against the layout (`layoutIds`, which includes the bands). A layout's bands (`top` / `bottom`) are part of its body: made, merged into or closed they make the layout unsaved (resized: view state, above) (the dirty check and the kept draft compare the whole body — columns and bands); `save` / `saveAs` / `discard` carry them as the columns. `refreshAllStores` re-runs `init()` once the store is hydrated |
