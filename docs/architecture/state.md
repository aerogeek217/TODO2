# State (Zustand Stores)

Detail reference for `src/stores/`. Load when touching store APIs, filter semantics, undo, selection, or cross-store helpers.

## Stores

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| useTodoStore | stores/todo-store.ts | All tasks (`loadAll` / memoized `ensureAllLoaded`), CRUD and bulk operations: `add(title)` (stamps Settings' default status and `nextFollowupAt` = `settings-store.defaultNextFollowup(now)` (today + `followupDefaultInterval`); goes last — the repository picks `sortOrder` in its insert transaction, so adds that start together never share one), `addMany(items, { description, snackbar? })` (tasks with their people / tag ids in one transaction, last in order; one undo step — undo deletes them, redo puts the same rows and joins back; reloads the assignment caches), `update(id, changes)` (`TodoChanges`: just the fields the caller changed — never a whole row, so a caller holding an old copy can't write it back; fields already holding the value are skipped; written as a patch via `todoRepository.update(id, changes)`; undo / redo / a failed write's rollback touch only those fields; no change → no write, no undo step; **never rejects** — a failed write is rolled back, the snackbar says `Couldn't save your change to "<title>".` and it resolves `false` (else `true`), so fire-and-forget callers leave no unhandled rejection; `checkin-reply/apply` stops on `false`), `toggleComplete` (advances recurring tasks via `advanceRecurring`), `remove`, `bulkSetCompleted`, `bulkSetStatus`, `bulkSetDeadline`, `bulkSetFollowup`, `bulkSetLastFollowup`, `bulkSetFocus` (on → `focus: true`, off → key removed; one undo step), `bulkSetUrgent` / `bulkSetImportant` (same shape on `urgent` / `important`), `setMarkerFlags(changes, description)` (per-task Urgent / Important writes — an Eisenhower drop; one undo step with the snackbar), `bulkClearDueDate(ids)` (removes due dates — the clearing-Urgent prompt's action; one undo step with the snackbar `Removed the due date` / `Removed N due dates`), `markFollowedUp(ids, description?)` ("Mark followed up": last = now, next = today + default interval; one timestamp shared by store + DB; one undo step with snackbar — `description` names it, e.g. a check-in send's `Check-in for <name> opened · N tasks followed up`), `remove` / `bulkRemove` (undo puts back the tasks with their people, tags, list ranks and **event history** — the repository's delete returns the deleted `todoEvents` rows; more than `BULK_DELETE_SNAPSHOT_MIN` (5) tasks → `takeSafetySnapshot` first, outside the tracked write; cancelled → nothing deleted; without a backup the snackbar says `Delete N tasks — no backup was taken`; a redo skips the gate; `opts.beforeDelete` runs only once the delete goes ahead — the bulk confirm clears the selection and closes the editor there, so a cancel keeps them), `duplicate(id)` (copies title / notes / progress / dates incl. next follow-up / status / recurrence / the urgent and important flags (not focus), then the source's people and tags at repository level; undoable), `purgeCompleted(ids)` → `PurgeOutcome` (`done` with `deleted` + `noBackup`, or `cancelled` when the backup failed and the user cancelled; deletes only the given ids still completed **in the DB**, re-read after the backup gate (`takeSafetySnapshot`); called only after the launch prompt / Settings cleanup confirm; expiry keyed on `completedAt`), internal `_restore` (task + people / tags + events) / `_removeNoUndo` (returns the deleted events) for undo / redo — the redo of an undone `add` / `addMany` / `duplicate` puts the task back with its `created` event, so the dashboard trend reads the same. **One `modifiedAt` per write:** each write mints its timestamp once and passes it to the repository (`update` / `complete` / `bulkUpdate` take `now`), so the store and the database hold the same value; an undo that restores an earlier `modifiedAt` writes that value to both. Deletes also drop the tasks' manual-order ranks from `list-order-store` (`forgetTodos`). Optimistic completion state mirrors the repository's `completedAt` rule (`resolveCompletedAt`). `todosVersion: number` monotonic counter — bumped on every mutation that changes the id-set (add / duplicate / remove / bulkRemove / _restore / _removeNoUndo / purgeCompleted / load); **not** bumped on field edits (update / toggleComplete / bulkSet*). Surfaces that only care about membership changes use `${todos.length}:${todosVersion}` as an O(1) cache key — consumed by `useEntityAssignmentsForTodos` (the workspace) to gate the assignment-join-load effect |
| usePersonStore | stores/person-store.ts | People list, CRUD (`add(name, initials, color?)` — the color key is written only when a color is given; `getOrCreate(name)` — lookup-or-create by trimmed name, case-insensitive, in memory then `personRepository.getOrCreate`; new people get `generateInitials` initials and no color; used by every person picker's Create and by NLP `@name`; `update(person)` writes the whole row, so a cleared color drops the key; `remove` is undoable — `captureJoinRows` + `personRepository.restoreWithJoins`, folding a same-named person created meanwhile into the restored one), `ensureLoaded`, `assignedPeopleMap`, todo-person assignments (`loadAssignments`, assign / unassign / bulk with undo via `createAssignmentActions`). A failed `update` rolls back only that person (and only while it still holds this edit), in `people` and the map. `countTasks(personId)` — how many tasks (loaded or not) the person is on, read from the database (the delete confirm) |
| useStatusStore | stores/status-store.ts | Status definitions: load / `ensureLoaded`, add (goes last — `statusRepository.insertLast` picks the sort order and refuses a name already stored, ignoring case, in its transaction), update (a failure rolls back only that status), remove (cascade delete clears todos + the default-status setting, with undo), reorder (drag sort with persisted sortOrder). `selectTodoCountByStatusId(statusId)` — store-derived count for StatusEditor's delete confirmation, read from `useTodoStore.todos`; StatusEditor calls `useTodoStore.ensureAllLoaded()` so the cache is populated |
| useTagStore | stores/tag-store.ts | Normalized tag registry (mirrors `usePersonStore` shape): `tags: Tag[]`, `assignedTagsMap: Map<number, Tag[]>`, `load` / `ensureLoaded`, `loadAssignments(todoIds)`, `add(name, color?)` (defaults to `DEFAULT_ENTITY_COLOR`; idempotent on a case-insensitive name match via `tagRepository.getOrCreate`; no cap on the number of tags), `update` (a failure rolls back only that tag, in `tags` and the map), `remove` (with undo — re-adds the cascaded `todoTags` joins via `captureJoinRows` + `tagRepository.restoreWithJoins`, folding a same-named tag created meanwhile into the restored one), `countTasks(tagId)` — how many tasks (loaded or not) carry the tag, read from the database (the delete confirm), `assignTag` / `unassignTag` / `bulkAssignTag` / `bulkUnassignTag`. Uniqueness is enforced case-insensitively at the repository layer; `#Foo` / `#foo` resolve to the same registry row. `countTodosByTag(map)` — counts read from `assignedTagsMap` (callers load assignments for every task first, as `TagEditor` does). A former project is a `Project: <name>` tag (schema v60) |
| useNoteStore | stores/note-store.ts | The single global "outside-tasks" note shown by every notes widget: `notes` map + `activeId`, debounced `setContent(id, content)` (`SAVE_DEBOUNCE_MS` 500) + `flush`, `lastSavedAt`. `load()` seeds the row if missing (`noteRepository.getOrSeedGlobal`, one transaction); concurrent loads share one (`loadInFlight`); text still unsaved stays what the store shows. The latest edit is `pending` (sequenced) until a save of it or newer text succeeds: saves run one at a time, each writes the latest text (`saveContent` — content + `modifiedAt` only) and never puts older text back into the store. A failed save keeps the text, sets `saveFailed`, shows `Couldn't save your notes. They'll be saved with your next change.` once (undo snackbar notice) and is retried by the next change or `flush`; `flush` never rejects. `discardPending()` drops unsaved text and its scheduled save (`refreshAllStores` calls it). `holdForDataReplace()` — called before every data replace takes its backup (import / backup restore / audit cleanup via `file-ops-store`, a sync file load via `fileStorageService.onBeforeImport` wired by `file-storage-store`): saves the text typed so far (`flush`, which also waits for a save already started — so the pre-op backup holds it; if that save fails the text is dropped and the replace goes ahead), then holds every later save (`replaceHolds > 0`; text typed meanwhile is dropped by the reload) until the returned release — called after the stores reload, or when the replace was cancelled or failed (text typed meanwhile is then saved). So no save can land after a replace, and text typed just before one is recoverable from Settings › Backups. It waits only on note saves (untracked, never on a load), so it can't deadlock with the replace `resetNoteSaves()` (tests sharing one module instance) clears the save timer and the save chain. |
| useWorkspaceStore | stores/workspace-store.ts | Workspace layouts: `layouts` (saved, oldest first), `activeLayoutId`, `working` (in-memory working copy of the open layout), `saved` (its stored version; `null` for a new layout), `previousLayoutId` (while a new layout is open: the layout Discard goes back to), `isDirty`, `repairedIds`, `hydrated`. **Kept for a reload:** after every change (but a `live` resize — see below) the store writes what is unsaved — the working copy when its structure differs from `saved` (with `saved`'s body as its base), or a new layout (with its lists' names) — to `data/draft-storage` (`localStorage`, never Dexie), or forgets it. The page load's first `init()` (concurrent first calls share it) reads it before opening and takes it back unsaved only while the stored layout is the open one with the same structure as the base / every list a new layout shows has the same id and name; anything else is forgotten. **Writes land before the screen says so:** `save` (→ `true` / `false`), `saveAs` (→ id / `null`) and `rename` (→ `false`) change state only after the write succeeds; a failed one keeps the layout unsaved / the old name and says so in the snackbar (`Couldn't save layout "…".`), never rejects; the unsaved-changes prompt stays open when its Save fails. A failed view-state write is logged and kept for the session. **Repaired on read:** a layout `layoutRepository` repaired (`ReadLayout.fixes` — e.g. a retired widget kind dropped) opens without the bad parts but unsaved (`repairedIds` keeps `isDirty` true, also after `discard`), and the snackbar says `Repaired layout "<name>" — <fixes>. Save it to keep the repair.` (logged too). Nothing writes the repair back but `save()` (or Data integrity cleanup): its view-state edits stay in memory, `load` writes only `lastUsedAt` and `rename` only the name. `init()` (idempotent: `layoutRepository.ensureDefault`, then opens the `activeLayoutId` layout, falling back to the most recently used; drops any working copy — call after startup has loaded the sync file; the first call of a page load reopens the kept draft, see above), `newLayout()` (an empty `Untitled layout` with id `UNSAVED_LAYOUT_ID`, `saved` null, dirty; nothing stored until `save()` inserts it under its name — as `saveAs` — and opens it; `discard()` goes back to `previousLayoutId`; `rename(UNSAVED_LAYOUT_ID, name)` renames it in memory), `load(id)` (switches unconditionally — callers resolve unsaved changes first; stamps `lastUsedAt` with a field patch), `save()`, `saveAs(name)` (the new layout becomes current and saved; the source keeps its last saved state), `discard()`, `rename(id, name)` (never dirty), `delete(id)` (refuses the last; deleting the open layout opens the most recently used). **Structural edits** change only `working` and recompute `isDirty = repaired || !layoutStructureEqual(working, saved)`: `addWidget(kind, target, seed?)`, `moveTab(tabId, target)`, `movePanel(panelId, target)` (a whole cell or band), `closeTab`, `closeCell` (a cell or band), `setBandHeight(edge, px)`, `splitCell(cellId, 'right'\|'below')`, `setColumnWeights` / `setCellWeights` (batched, by id; these and `setBandHeight` take `{ live: true }` for the frames of a divider drag — applied but not kept in the browser until `keepLayoutDraft()`, which the divider calls once when the drag ends), `patchTabConfig(tabId, kind, patch)`, `changeTabKind(tabId, kind, seed?)`. **View-state edits** — `setActiveTab(tabId)`, `setCellCollapsed(panelId, collapsed)` (a cell or band), `patchTabViewState(tabId, kind, patch)` — apply to `working` and to `saved` (where the target exists there) and write `saved` to Dexie at once (last write wins; `modifiedAt` untouched; never dirty). New column / cell / tab ids are random and checked against the layout (`layoutIds`, which includes the bands). A layout's bands (`top` / `bottom`) are part of its body: made, merged into, resized or closed they make the layout unsaved (the dirty check and the kept draft compare the whole body — columns and bands); `save` / `saveAs` / `discard` / `newLayout` carry them as the columns. `refreshAllStores` re-runs `init()` once the store is hydrated |
| useListDefinitionStore | stores/list-definition-store.ts | Saved list definitions: load / `ensureLoaded`, add (goes last — `listDefinitionRepository.insertLast` picks the sort order in its transaction; accepts membership / sort / grouping), update (a failure rolls back only that list), remove (with undo + snackbar; drops the list from the lists as they are when its delete finishes, so a list added or edited meanwhile stays; drops the list's ranks — `list-order-store.forgetList`; a check-in scope on the list goes back to `all`, and undo restores it unless the scope was changed since), reorder. New custom lists start from `emptyPredicate()` (`models/filter-predicate`). Backs every list widget, the Lists manager and the Edit list dialog. `ListDefinition.runtimeFilter?: RuntimeFilterSpec` declares a per-render picker field (`person` / `status` / `tag`); the *value* is *not* stored on the def — workspace list tabs keep their picks in `list-widget-store` (never saved) and feed them to `buildList` via `ctx.runtimeFilterValue` (through `useBuiltList`). Picks are OR-combined arrays; an empty array means no narrowing. Unsaved edits to a definition live in `list-draft-store`, not here |
| useListDraftStore, getUnsavedListIds, draftListIds | stores/list-draft-store.ts | Unsaved edits to list definitions, keyed by list id and shared by every widget showing the list. Kept in the browser too (`data/draft-storage`, each with the saved list it was made against): `restore()` (the workspace calls it on mount; concurrent calls share one run) takes back each kept draft whose saved list still `defsEqual`s its base and forgets the rest — drafts on screen win; nothing is written before a restore ran, so an edit can't overwrite what's kept. `edit(id, fn)` applies `fn` to the draft (else the saved def) and drops the draft when the result `defsEqual`s the saved def; `save(id)` writes it through `useListDefinitionStore.update` (blank name → the saved name; restored as a draft if the write fails); `discard(id)`; `revert(id)` = `discard` as an undo step (`undoable`, snackbar `List changes reverted` — Undo puts the draft back through `edit`). | useListOrderStore, useListRanks | stores/list-order-store.ts | Manual list order: `ranks` (list id → todo id → rank), loaded once (`ensureLoaded`, from `useBuiltList`; reloaded by `refreshAllStores`). `setRanks` (a move) and `replaceList` (switch to manual) update memory then save at once — order changes are never part of a list's unsaved draft. `forgetTodos` / `forgetList` drop deleted rows from memory (todo-store / list-definition-store call them after the repository cascades); `restoreRows` is their undo `resetListOrderLoad()` (tests) forgets the load in flight. |
| useListWidgetStore, ListFilterField, PopoverPoint | stores/list-widget-store.ts | Never-saved list widget state: prompt picks (`picks[tabId]`, `setPicks`; empty = nothing picked) and collapsed group keys per layout tab (`toggleGroup`); also the filter-picker types (`ListFilterField`, `PopoverPoint`). ## Filter Semantics

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| useFilterStore | stores/filter-store.ts | The screen (top-bar) filter: `filters` (a `FilterCriteria`), `setShowCompleted` / `setPersonIds` / `setStatusIds` / `setSearchText` / `setDateRange` (wraps Dates as fixed anchors) / `setTags` (OR semantics via `assignedTagsMap`), `setAllFilters` / `clearAll`, and a derived `isActive` (`countActiveFilters > 0`). Edited by the TopBar `FilterChipBar` / mobile `FilterSheet`; cleared by `App.tsx` on every pathname change. The criteria type, converters and evaluators are pure modules in `utils/` |
| FilterCriteria, fixedAnchor, countActiveFilters, composeScreenFilter, criteriaToPredicate / predicateToCriteria | utils/filter-criteria.ts | `FilterCriteria`: personIds, statusIds, tags as null\|Set of number ids; showCompleted, searchText, dates (`DateFilters`: a clause per date type — `deadline` = due date / `followup` = next follow-up / `created` / `modified` — each a range of `DateAnchor`s (with `includeNoDate` on the due date / follow-up), Has a date or No date; every clause must pass, `utils/filter-match.matchesDateMatch`; the screen filter's `setDateRange` sets the due-date range), markers — the Priority filter (`MarkersFilter \| null`: `'hot'` = hot by `settings.hotRule`, or every ticked marker required, Urgent = effective urgent against `settings.urgentDueWithinDays`; `utils/markers.matchesMarkers`). `countActiveFilters` — one per control (people, status, tags, dates — however many types filter, they count once —, markers, show completed, search); drives the mobile Filters badge. `composeScreenFilter(screen, list)` — the two stages a task must both pass: narrowing clauses AND strictly (even on the same field — screen `@Alice` + list `@Bob` = tasks assigned to both), `showCompleted` ORs into both. Converters between runtime `FilterCriteria` (Sets) and serializable `TodoPredicate` (arrays); `predicateToCriteria` reads the date clauses through `utils/date-filters.readDateFilters` (anchors via `readDateAnchor`; clauses that filter nothing left out), builds an id Set only from an array (anything else = no filter) and normalizes markers (`{}` → null) |
| FilterSettings, matchesFilter / matchesFilterWithLookups / applyFilter / createPredicateEvaluator / matchesComposedFilter / createScreenComposedEvaluator | utils/filter-match.ts | The evaluators — pure: every one takes `FilterSettings` (`MarkerSettings` + `weekStartsOn`, from `useFilterSettings` or `settings-store.currentFilterSettings`) and `today`. `matchesFilter(filters, todo, personIds, today, searchCtx, tagIds, settings)` is the core: person filter is plain set membership over the todo's assigned people (`0` = unassigned sentinel); statuses never hide tasks by themselves; `today` and `settings.weekStartsOn` resolve relative date-range tokens; a non-null tag clause excludes tasks with no tag assignments. `matchesFilterWithLookups` resolves people / tag ids and the search context (`utils/filter.textMatchContextFor`) from `TodoNameLookups` — the one path behind both `applyFilter` (calendar, Eisenhower, dashboard) and `createPredicateEvaluator(lookups, today, settings)` (list widgets' `evalPredicate` for stored `TodoPredicate`s; converts each predicate to criteria once), so search hits person / status / tag names on every surface. `createScreenComposedEvaluator(screen, lookups, today, settings)` is the `evalPredicate` list widgets pass to `buildList` (via `composeScreenFilter`) |

## Store Helpers

| Abstraction | Location | Purpose |
|-------------|----------|---------|
| createAssignmentActions | stores/assignment-helpers.ts | Factory for assign/unassign/bulk/load actions shared by person + tag stores; a failed write takes back only its own entries (other tasks' changes made meanwhile stay). `loadAssignments(todoIds, {refetch?})` fetches only ids missing from the map (the map ends up holding exactly `todoIds`; entries written optimistically during the fetch win); `refetch: true` re-reads every id — `refreshAllStores` uses it after a restore / import, where a todo can keep its id while its people / tags change |
| makeEnsureLoaded | stores/store-helpers.ts | `makeEnsureLoaded(load, isLoaded)` → an `ensureLoaded()` callers can fire on every mount without re-hitting IndexedDB. Concurrent callers share the in-flight load; once `isLoaded()` — the store's `loaded` flag, set only by a load whose read succeeded — is true, calls are a no-op. A failed load (reported by `loadFresh`) leaves the flag false, so the next `ensureLoaded()` reads again; the promise never rejects. The flag is store state, so it resets with the store. Used by `useTodoStore.ensureAllLoaded`, `usePersonStore.ensureLoaded`, `useStatusStore.ensureLoaded`, `useTagStore.ensureLoaded`, `useListDefinitionStore.ensureLoaded` (`useListOrderStore.ensureLoaded` follows the same rule on its own `loaded`). A restore / import reloads through `refreshAllStores`, which calls each `load()` directly. The load in flight is module state: `resetModuleState` (tests) forgets it, and a forgotten load finishing never clears its successor |
| trackWrite, readFresh | stores/store-helpers.ts | Keep a `load()` from putting back rows an edit changed while its read was in flight. Every store write (state change + database write) runs through `trackWrite` — `mutate` / `optimistic` do it for their callers; the other writes of the todo / person / tag / status / list / list-order / settings stores wrap themselves. Loads read through `readFresh`: it waits until no tracked write is in flight, reads, and reads again if a write started meanwhile (gives up after 5 reads with a warning). One app-wide tracker, so e.g. a todo load also waits for a status delete that clears `statusId`s. Rule: a tracked write never awaits a `readFresh` load (deadlock); `loadAssignments` doesn't use it (it merges with the latest map instead), so writes may call it. Not covered: the workspace store (`init` / `load(id)` open a layout — no edit can be pending) and the note store (its load runs at startup / after an import; a typed note saves on a debounce). `resetWriteTracking` is the shared vitest setup's file-boundary reset |
| loadFresh, reportLoadFailure | stores/store-helpers.ts | A store load's `readFresh` read; returns undefined on failure. `reportLoadFailure(label, error)` logs a failed load and shows `Couldn't load <label>. Reload the page to try again.` as the undo snackbar's notice (also used by the list-order and note stores). Stores keep no `loading` / `error` fields: a failed load is a notice, a failed write is logged and rejects to its caller (or, for `todo-store.update`, a notice) |
| mutate | stores/store-helpers.ts | Tracked wrapper for store mutation actions: logs a failure and re-throws it |
| optimistic | stores/store-helpers.ts | Tracked optimistic mutation: applies state synchronously, persists async, rolls back on failure; undo registered only after successful persist. Rollbacks are **item-level**: each caller puts back only what its own write changed (the task's fields, the one person / tag / status / list — and only while it still holds this edit —, the assignment entries it added or removed, at their old positions), so a concurrent edit that landed meanwhile keeps its value |
| updateEntityInMap | stores/store-helpers.ts | Refresh entity references in assignment maps when entity is edited |
| captureAssignments, captureAssignmentsBulk | stores/store-helpers.ts | Capture person assignment IDs for todo undo (delete / duplicate) |
| bulkUpdateField | stores/store-helpers.ts | Generic bulk field update with undo for todo store (one `modifiedAt` for the store and the DB; undo restores the changed rows' value and `modifiedAt` in both) |
