# Architecture Overview

This file is the always-loaded orientation: what lives where and how data moves. Every module's detail — its functions, rules and edge cases — is in the reference files under [Detail References](#detail-references); load the one you need.

## Tech Stack
- **Frontend**: React 19 + TypeScript, built with Vite
- **State**: Zustand stores
- **Database**: Dexie.js over IndexedDB (local-first, no backend)
- **Drag-and-Drop**: dnd-kit
- **Routing**: React Router v7 data router (`createHashRouter` + `RouterProvider`; one splat route renders the shell's `<Routes>`, so `useBlocker` is available)
- **Builds + CSP** (a `<meta>` in `index.html`, first in its head, `base-uri 'none'; form-action 'none'` everywhere): the online build (`vite.config.ts`; `dist/index.html`) loads scripts from `./assets` only, so its `cdnFonts` plugin drops `script-src 'unsafe-inline'` (and adds Google Fonts) and `noInlineScripts` fails the build on any inline script. The offline single file (`vite.config.offline.ts`; `dist/todo2.html`) **makes no network request**: its own policy (`offlineCsp`) denies by default and names no `'self'` (on `file://` it would admit any `file:` URL, a UNC share's among them) — inline styles, `data:` images and fonts, no connect / frame / object / worker / media / manifest (the check-in preview is a sandboxed `srcdoc` frame, which fetches nothing) — and allows its one inline script by its sha256 (`offlineScriptHash`, the build's last step, over the final text; the build fails on a second script or a mismatch); it sends no Referer and turns DNS prefetch off. The build then runs the **egress check** on the finished file (`offlineEgressCheck` → `scripts/offline-file.checkOfflineFile`): it fails on anything that loads, a `<!--` in its script text (after it a `<script` would make the browser read past the first `</script` the check stops at), a looser policy (a CSP directive named twice too: browsers enforce its first copy), no `no-referrer` / DNS-prefetch-off meta, a network API in the code (a reference to `window.open`, called or not; a resource hint's rel value, quoted anywhere in the script — the library hint code the app never calls is on its inert list) or a URL off its inert list (protocol-relative ones too, a dotless UNC `//host/share` among them) — each inert entry with its reason; ESLint bans the network APIs in `src/` (and the HTML-parsing sinks — `innerHTML` / `outerHTML` writes, `insertAdjacentHTML`, `document.write`, `dangerouslySetInnerHTML`: nodes are built, never parsed from a string), and `e2e/built-csp.spec.ts` audits the file's requests through its main flows. The sync file, imports and exports go through the File System Access API, file inputs and downloads, which no fetch directive governs. Its icons are `data:` URLs too (SVG, the .ico's 16–64 px bitmaps, the 192 px PNG — `offlineIcons`) and it has no manifest link, so the file works alone from disk. Dev keeps `'unsafe-inline'` for the React refresh preamble

## Data Flow

1. **Startup** (`services/app-startup.runAppStartup`): `App.tsx` first checks the database's version (below the floor → `DatabaseTooOldDialog`: nothing read or written — Download this data, or Import a file… that replaces it after asking, or Reload; saved by a newer build → `DatabaseTooNewDialog`: Reload only, nothing read or written). Then settings load (theme, colour overrides) → the sync file reconnects (`fileStorageService.initialize()`). When its handle needs permission again, launch **waits for the launch question** (Grant access… / Continue without the file) before anything else runs. The load decision changes nothing on either side until the user resolves a disagreement (conflict / older file / unreadable → a dialog or a pause); a browser merely ahead of an unchanged file is written to it after a backup of the file's text. Then the stores load. Completed tasks past the retention are **never purged silently**: the purge prompt asks (Export & delete / Delete / Not now), at most once every N days, also after a later sync-file load. `backupScheduler.start()` takes a daily automatic backup; each backup kind keeps its newest few within a byte budget.
2. **Normal use**: UI → Zustand stores → repositories → Dexie. While a sync file is syncing, Dexie hooks debounce-save to it; while paused or waiting for permission they only mark the browser dirty, which the next load resolves (written to an unchanged file, else asked about). Every task write stamps the task's `modifiedAt` (the stale fade, the Modified filter and sort read it), in the store and the database alike; **an undo puts back the stamp the task had before the step, a redo the one the step wrote** — each only where the task still holds the stamp the other left, so a task touched since keeps its newer one (`utils/task-stamps`, cr32; the same rule for field edits, completions, follow-ups, priority flags, status updates, subtasks and assignments; a delete's undo puts the row back with its stored stamp). Destructive operations — a data replace, a purge, a bulk delete of more than five tasks, removing unused people and tags — back up first (`takeSafetySnapshot`; a failed backup asks before going on). New tasks come through `QuickAddBar` (its Details hands off to `TaskEditPopup`'s create mode).
3. **Data replaces** (`services/replace-data.replaceData`) — Settings import and backup restore, the audit's cleanup, the sync file's load, the append import: note saves held → safety snapshot → the write → the stores reload (`refresh-all`; an append import reloads the task stores only and keeps the undo history) → `onDataReplaced` listeners. A file (an import, a backup, the sync file) is read through the import pipeline first: one from below the schema floor (`OLDEST_SUPPORTED_DB_VERSION`, v68) or without a version is refused — nothing read, nothing written —, with a message naming the older build that still converts it.
4. **Workspace**: a layout is one **table** (D26, schema v78, `models/workspace-layout`): grid lines across and down — `grid.columns` and `grid.rows`, each a list of `GridTrack`s (`{ id, weight?, px?, collapsed? }`: a weighted track, its share of the axis, or a fixed `px` track, a former band) — and `cells`, each covering a rectangle of tracks (`area { col, row, colSpan, rowSpan }`, track indices) and holding a strip of widget tabs. A full-height column is a cell spanning every row track, a strip a cell spanning every column track; nothing nests. The cells tile the grid exactly (no gap, no overlap) and every grid line is the edge of some cell (`utils/workspace-grid`: the queries — neighbours along an edge, whether two cells merge into a rectangle, reading order, edge stretches —, `normalizeGrid`, which merges the two tracks beside a line no cell's edge lies on, and `validateTiling`); a cell with no tabs is an **empty cell** (a split's new cell, or a close with no taker). **The ops** (`utils/workspace-layout-ops`; each returns a normalized table, or the same layout when there is nothing to do, which `dropChangesLayout` relies on): `splitCell` (a new empty cell on a side, taking half — an even span splits on its middle line, an odd one splits its middle track, the cells crossing it then spanning both halves; the new cell never comes out collapsed — split below / above a collapsed cell, the old half keeps its collapse, while beside it in a collapsed row the row expands), `insertTrack` (a row at the top / bottom or a column at the left / right, full width / height, holding one new empty cell, half the nearest weighted track's size; a new column across collapsed rows expands them), `mergeCells` (two cells whose union is a rectangle: the first grows over the second, whose tabs join its strip after its own), `closeCell` (**the absorb rule**: the neighbour sharing its whole edge — left, above, right, below, the first there is — grows over it; else the neighbours along one side that together cover that whole edge all grow across it; else, the centre of a pinwheel, it stays as an empty cell), `moveTab` / `movePanel` onto a target `{ kind: 'cell', cellId, index? } | { kind: 'split', cellId, side } | { kind: 'insert', edge } | { kind: 'layout' }` (a cell the move empties closes by the same rule; a whole cell's move closes its old place first or places first, whichever leaves no empty cell), `moveEdge` (a divider, below) and `setTrackCollapsed` (**Collapse row** collapses every row track the cell covers, so its side-by-side neighbours fold with it: the cells lying only in a collapsed track show their top lines, a cell spanning through it gets shorter; column tracks don't collapse). **Rendering** (`WorkspaceView`, `utils/workspace-table`): one CSS grid, `grid-template-*` from the tracks — a weighted track `minmax(<its cells' minimum>px, <share>fr)` (the table scrolls when the minimums don't fit: `CELL_MIN_PX` high and 120px wide, a glance cell 64px / 72px — `utils/workspace-rows`), a fixed track its px, a fit row `auto`, a collapsed row a header's 32px —, each cell placed by `grid-area`. **Dividers** (`WorkspaceDivider`, one per stretch of grid line between two cells' edges — `edgeStretches`: a line parts at each "+" crossing, where the perpendicular line is an edge on both sides, but runs on at a "T"; none beside a collapsed row): a stretch that holds every edge on its line moves live and reweights its two tracks (view state, saved once at the drag's end); a stretch that is part of a line leaves it — onto another line (a piece snapped back onto a line re-joins it), or a new line and track where it stops (the cells crossing that track gaining a span) — a structural edit, unsaved until Save; the drag snaps onto any line of its axis within 8px (`EDGE_SNAP_PX`) — one only other columns' or rows' cells lie on too — a faint accent guide along that whole line while it holds (`SnapGuide`), and keeps every cell its minimum, and the arrow keys step it, the focus staying on it (a double-click evens a whole line's two weighted tracks, or moves part of a line midway between its own cells — `evenStretchDelta`, an unsaved edit). **Crossing handles** (`WorkspaceCrossing`, one per "+" — `lineCrossings`): a drag moves both whole lines through it, the level one with the pointer's y and the upright one with its x, each a whole-line resize (view state, saved at the end) that snaps back onto its own place within 8px (a mostly vertical drag leaves the column line put); ↑↓ / ←→ step the row / column line 16px, a double-click evens both. A Numbers-only (fit) row's line has a divider too: its drag gives the row a fixed height, its track's `px` (view state, saved at once; px wins over `auto`), a double-click clears it and the row fits again. **Drops** (`utils/workspace-drop`, on the geometry `measureWorkspace` takes when a tab or cell drag starts — again while the table scrolls under it): the layout's left / right edge (24px inside) inserts a column, its top / bottom edge (24px inside, reaching 16px past) a row; a cell's strip takes a tab at an index; a cell body splits on its outer 20 % (at most 120px) on each of its four sides — a cell with one widget has no strip, its whole card is its body — and joins as a tab in its middle; an empty cell takes the drop as a tab. **One ghost** (D26 board T, `dropGhost`, drawn by `DragOverlayLayer`) shows the result: the move run on a probe copy of the layout and the cell that ends up holding what is dragged placed from the drag-start geometry, labelled `Split Late · above`, `Insert row · full width`, `Insert column · full height`, `Add as tab` (`Add N tabs`); it fades in at each new spot (reduced motion: at once). **The cell's ⋯** (`cell-menu`, named **Cell options**) is one merged menu in two headed sections: the active widget's own entries first, under its kind's name (Edit list… / Change list, Review these N tasks, Zoom, the lens switch, Copy, a Number's or a chart's Edit …, its settings, then **Change widget ›** — the current kind beside it, a submenu of every kind under Tasks and Numbers & charts), then the cell's, under **Cell** — **Add widget…** (`AddWidgetFlow`: where first, as a picture of the cell — its middle Tab, its inner sides Split above / below / left / right, bars outside it Insert row at the top / bottom and Insert column at the left / right, the hovered or focused one named under it in the drag ghost's words, the arrow keys moving between them, default Tab — then the kind), **Split cell ▸** Right / Below, **Merge with ▸** Right / Below (off, saying why, unless the two make a rectangle), **Insert ▸** Row at the top / bottom, Column at the left / right, Collapse / Expand row, Close tab “…” (two or more widgets) and Close cell (`(N tabs)`). A right-click on a tab (that tab's menu) or on a lone widget's top line, and Shift+F10 / the Menu key there, open it; there is no arrange mode. **Tabs on demand** (D26 AA1): a cell holding one widget has no tab strip — the widget's own top line (`WidgetTopLine`) names it and stands for its tab (`data-ws-tab`): a list's name, unsaved dot and badge capsule (`list/ListTopLine`) then its filter line (chips, lens switch, count, group · sort), the calendar's month header, a Number's label, a chart's title, a name line for Notes, the Eisenhower (with its count) and the Neglect map (with Slipping N); it ends with the cell's controls slot (`CellControls`, lent through `CellControlsContext`: the grip, which drags the whole cell, and the ⋯ — shown on the cell's hover and focus-within and always on touch; while collapsed an Expand row button that always shows); a face with no top line (a small face, a Number whose label is inside its button) gets the slot floating over the cell's top-right corner. With two or more widgets the cell's header shows as before: the tab strip (`CellTabStrip`), the grip, Collapse row and the same ⋯. A drop joining a one-widget cell previews the strip it will have. **Fit rows**: a row track whose cells lying only in it each hold one Number fits its content (`auto`, ~64–76px; derived, never stored — `workspace-rows.isFitTrack`; a cell spanning through it doesn't count) — unless its divider gave it a height (the track's `px`, which wins; a Number taller than its small face shows its medium face). **Faces** (D25 R, `utils/widget-face` + `hooks/use-widget-face`): a widget draws its small, medium or large face by its cell body's measured size — small at most 90px tall or 180px wide, medium at most 160px tall, else large; never stored, never a setting. The List, Calendar, Eisenhower (D26: small the 2×2 of pane counts — the old Eisenhower summary —, medium those counts with each pane's first two titles, `EisenhowerFace`), Neglect map and every glance widget have faces (Notes is always whole; a fit row's cell is at its small face); a click on a small face (or its focus-only `Open …` button) opens the whole widget in a popover anchored to the cell (`min(720, 100vw − 16) × min(520, 100vh − 16)`; Esc, × or a press outside closes it, and so does the face growing). Stored layouts are read through the layout repair (`data/layout-shape`: a part this build can't use is dropped, a tiling that doesn't hold is rebuilt as the cells in their reading order stacked in one column; the layout opens unsaved). A layout's optional **hue** (D19) colours its tab, its cells' top lines and headers and the focus ring inside it; it is set with the name in Edit… (the layout tab's menu; the Edit layout dialog) and saved at once. Layout edits — anything that changes a track's id or a cell's area, a tab's place or its config — make the working copy unsaved until Save (kept in the browser across a reload, never in the database); an edit that brings the arrangement back to the saved one takes its track ids and sizes (`withTrackIdsOf`, so Insert row then Close cell reads saved). The layouts' order and view state — track sizes (a weighted track's weight, a fixed one's px) from the dividers, collapsed row tracks, each cell's active tab, calendar view, row details width — save at once; a size among tracks an unsaved edit added stays with that edit until Save — and so do a fixed track's px and a row's collapse on a track the edit changed (split — a split's first half keeps the old id — or spanned anew: `workspace-layout-sizes.sameTrackIn`), so the stored row, a neighbour's too, keeps its own. On a **phone** (`MobileWorkspaceView`) every cell shows in reading order (by its top track, then its left) in one vertical scroll, a run of Number cells two up while each gets 140px; the same tabs-on-demand rule (one widget: no tab row, its top line holds the ⋯; a face with no top line has none), no layout editing. **v78** (`data/upgrades/v78/layout-table`) made every v77 layout (columns → rows → cells, and the bands) a table: its lines from v77's geometry — the column weights give the x positions, inside a column each row's cells' weights, a band's cells across the whole width; down, each column's row weights between the bands, which become fixed tracks at the top and bottom (a fit row counts as a nominal 76px of an 800px column area, for the ordering only, and then fits again) — every distinct position a line, the weights scaled to whole numbers summing to 1000 per axis, a row track collapsed when every cell over it came from a collapsed row or band; each cell keeps its id, tabs and active tab, while `stripShown` and the phone's `activeColumnId` go.
   **Lenses** (D15) are named screen filters defined once (Settings › Tasks › Lenses, the `lenses` settings row; four presets seeded on its first open; a lens's filter edits are saved or reverted — a draft until Save, the top bar keeping the saved lens, and leaving it with a draft asks Save / Discard / Keep editing, cr25) and **picked in the top bar** — one pick for every layout, no part of any layout (`settings-store.activeLensId`, the `activeLensId` settings row: saved at once, no unsaved state, no undo step; a layout switch keeps it). The lens control sits between the layout tabs and the screen-filter tray, its own part of the bar (never folds; outside the tray, never lifted with it), and while a lens is on the whole control takes the accent as the tray takes red for a chip. A person's envelope (a People group header, a Breakdown's person row with check-ins, the person task dialog), its right-click menu and the top bar's People filter offer Review with X…, Email check-in to X and Paste reply from X… (`shared/person-menu-entries`, one source). A reply comes back by paste (the import dialog, which reads the person from the reply): `checkin-reply` parses it, diffs it against the tasks, and applies the ticked changes as one undo group (a changed Status — read without its `(MM/DD)` — adds a status update dated today; a reply never removes one).
10. **Status updates** (cr27, schema v72): a task's dated lines of text — what happened, as of a day — in their own table (`statusUpdates`, `status-update-repository` → `status-update-store`; not on the task row, but each write — add, edit, remove — stamps the task's `modifiedAt` in the same transaction, so updates keep a task from going stale, and its undo / redo puts the earlier / its own stamp back), newest first by day, then by when written. They replaced the one-line Progress field (the v72 upgrade made each task's Progress its first entry, dated its `modifiedAt`); the Status picker (`statusId`) is a separate field. Added / edited / removed in the task layout's Status updates section — the editor's and the review card's (D26 BB / BG: **every entry oldest first**, like a log, the list scrolling inside and opening at the bottom, then the **add line**: ⏎ adds the entry dated today with `addStatusUpdate`'s rules — in the deck, ⏎ there is Mark followed up with that update; a past day is set by editing the entry) — each its own undo step; the places that show only the newest (the row's tooltip, the phone chip, the check-in email, the follow-up popover) stay newest; added from the notes popover's Status line (today) and from the follow-up popover's optional **Status update** line — with text, Mark followed up adds the entry dated today (`followedUp`) in the same undo step (`services/mark-followed-up`; from the bulk bar, to every selected task). **Entering one on an open task counts as following up on its day** (`addStatusUpdate`): a day after the task's last follow-up is Mark followed up for that day — the last follow-up moves to it, the next follow-up by the rule counted from it, entry `followedUp`, one undo step with the snackbar; an older or same day only adds the entry, and so does any entry on a **completed** task (nothing is chased on it any more: its follow-up dates stay, the entry isn't `followedUp`); a new task's entries set its Last follow-up to the newest's day (a new task is always created open). The follow-up popover's Mark followed up (and the bulk bar's, and a check-in reply's Record a follow-up) is the user's explicit choice and records the follow-up on a completed task too. Editing an entry's day doesn't, nor does a check-in reply without Record a follow-up. The newest shows on the row's notes tooltip and the phone row's chip (`MM/DD text`); the text search reads every entry. A task delete takes its entries, and its undo brings them back; Duplicate copies them. They travel with exports, backups, the sync file, task archives and the append import; the audit deletes orphans
11. **Subtasks** (cr28, schema v73): a task's checklist — each line a title and whether it is done, nothing else, one level — in its own table (`subtasks`, `subtask-repository` → `subtask-store`, ordered by `sortOrder`). A subtask is never a list row, never counted, filtered, grouped or sorted, and never a search result of its own; **the text search finds the task by its subtasks' words** (a Subtasks group in the top bar, the line as the snippet; the screen filter, lists, lenses, panes and counts keep the task likewise). Every task row shows a `2/5` count after its title — a 12px pie before it filling by the share done, the accent once all are (D25 D2) — that opens the checklist as a popover (check, rename, add, ⋯: Rename · Make a task · Move to another task… · Delete); the phone's chip opens it as a bottom sheet; the task layout has a Subtasks section beside Notes (drag to reorder; **+ Add subtask** its last line) — the editor's in create mode too, written with the task, and the review card's. The task menu offers **Add subtask…** and **Make subtask of…** (a task picker; the task keeps only its title and done state — a prompt lists what goes unless it holds only its title — its own subtasks move to the parent; one undo step brings it back whole; `services/subtask-convert`); **Make a task** gives a subtask the parent's people, tags, status, due date, next follow-up and markers (not its notes, status updates or repeat). Every subtask write stamps the task's `modifiedAt` as status updates do (`stores/task-hooks`); checking the last open one offers **Complete task** in the undo snackbar (never automatic); completing a task with open subtasks asks nothing; a recurring completion unchecks the checklist in the same undo step; a delete takes the checklist and its undo brings it back; Duplicate copies it unchecked; purge removes it. Notes → tasks (the toolbar's Convert, Alt+T, or the convert icon in the editor's left margin beside the line under the pointer; one line opens Quick Add on its text, Details handing off to the editor; two or more open a preview that shows drafts on task rows edited in place, nothing stored until it is confirmed; a draft checked off makes no task and its line goes on confirm, in the one note edit that a Ctrl+Z undoes; Settings › Task defaults' Remove note lines after converting (off by default) makes every converted line go that way too, asking nothing, instead of `✓ <title>`; × leaves the line) makes the indented list lines under a bullet its task's subtasks (plain titles), and Tab / ⇧Tab — or the toolbar's Indent / Outdent — indent list lines in every notes editor. **A task's own notes** (the editor's, the notes popover's) convert to that task's subtasks instead, the same three ways and with no dialog (`services/note-subtasks`): each line a plain title, the lines under it beside it (one level), a done box done; the lines turn `✓` or go as above, all one undo step with the snackbar; in create mode they join the pending subtasks. Check-in emails list a task's open subtasks under it for context (never read back); the Markdown export and Copy write indented `- [ ]` / `- [x]` lines under the task. It travels with exports, backups, the sync file, task archives and the append import; the audit deletes orphans
12. **Ambience** (desktop only; Settings › Appearance › Ambience — on by default): quiet signs of the time of day and the season in the chrome, never over a task's text and never in a colour that means something. `hooks/use-ambience` computes the `utils/sky` scene once a minute from the clock and the place (a typed latitude / longitude, else the time zone's main city — `utils/sun`; no location prompt, no network, so the offline file stays clean). `components/ambience` draws it: in the top bar, the sky over the glass at the share the glass lets through, the sun and moon as soft discs, stars, cumulus, the winter aurora, morning mist, the season's weather (snow, leaves, petals, seeds, fireflies — CSS-animated) and the sun's point on the hairline; in the workspace, the sunbeam and weather behind the cells and lamplight over them; a task completed on screen sends a ripple along the hairline and a burst from its box. Sky strength scales the sky, clouds, aurora, mist and sunbeam; Header motion everything that moves in the bar; Seasons the weather, the burst and the aurora. Reduced motion keeps a still sky. Its colours are `--ambience-*` tokens in `tokens.css` (each theme's own there), which the scene mixes by the time of day with `color-mix()` — no ambience file writes a colour or picks one by theme. One JSON settings row (`ambience`), no schema step
13. **Review deck** (desktop only; D26): a dialog over the workspace (`overlays/ReviewDeck`, state in `stores/review`, opened through `services/review.openReview`) that steps through a frozen queue of tasks one card at a time — a list tab's tasks as shown (its ⋯ menu › Review these N tasks, the editable `R` shortcut, the palette's Review List; its groups as dividers, each task once, collapsed groups too), a person's or a tag's open tasks (their right-click menu, the envelope), or several people's (the top bar's People filter), or a Breakdown row's (D26 P8: **Review ▸** at the end of a row's name on hover or keyboard focus — its tasks — and a click on its Due or Follow-up count — just those; kinds `person`, `tag`, `status`, `priority` or `chart`; not on the phone, nor while a deck is open). The rail reads like list rows (priority ring, dates in words and their colours; ✓ while followed up today in this review, – skipped); the card is **the task editor's layout** (D26 BB, `task/TaskDetailsBody`): the box and title; the status pill and Focus · Urgent · Important; Due + repeat, People, Tags; Subtasks | Notes (the notes flushed before any other write); Status updates oldest first, the deck's update line last (focused and in view as each card opens); the Follow-up group last (Next with 1w 2w 1m 3m and None; Last as its date only) — every edit in place, each its own undo step, one task only (never the selection); there is no Open in editor; its Next field and **Mark followed up ›** in the footer (⏎ in the update line) are the follow-up popover's rules — the typed update and the follow-up as one undo step — then the next card. ## Dismissing a popover

A change a popover shows either sticks or the user is warned. Esc or a click off saves what was typed (`FollowupPopover`, `SubtaskChecklist` in every host, `TaskNotePopover`; in the task editor the Status updates add line and + Add subtask line, which Esc leaves and the editor's close adds): each writes it in an unmount cleanup, so every way of closing is covered, and only a Cancel button drops it. Esc inside an inline edit — a subtask rename, a status entry — cancels that edit and leaves the popover or editor open. Text that can't be stored holds the close once, saying so; closing again drops it (a filter expression that doesn't read too: the first press outside its field, `ExpressionField`). Nothing exists yet behind Quick Add, the new-task editor and the convert preview's edited drafts, so they ask instead (Create task / Discard / Keep editing, or Discard / Keep editing with no title), and only when the form differs from how it opened; the editor's Cancel button discards without asking. Filter and picker popovers write on every change; a date panel's pending Is not, which no clause can hold yet, is kept per filter (`filters/date-pending-not`).

## Testing

Two layers, picked by what's being verified (setup, fixtures and helpers: [architecture/testing.md](architecture/testing.md)):

- **vitest (`npm test`)** — unit + JSDOM under `src/test/**`: pure logic, models, repositories, stores, services, utilities, and rendering / event dispatch that doesn't depend on real layout, focus or async DOM timing. Two projects (`isolated` for files that mock modules, `shared` for the rest); every store and every registered module state is reset before each test.
- **Playwright (`npm run test:e2e`)** — Chromium-only real-browser flows under `e2e/**`, on its own dev server (port 5173, or `PW_PORT`). Specs wait on app state, never on timers. CI (the deploy workflow) runs only vitest.

**JSDOM is not authoritative** for focus handoffs, `ResizeObserver`-driven layout, drag-and-drop hit-testing, popover placement and viewport flips, and async-store-driven re-render timing — those need a Playwright spec.

**Diagnosis vs. regression.** The Chrome DevTools MCP server (`mcp__chrome-devtools__*`) is a *spike* tool — drive an interaction live in real Chromium, then codify the regression in Playwright. See CLAUDE.md "Tools — Chrome DevTools MCP".

**Manual-testing seed.** `npm run seed:dev` writes a realistic export in the current schema to `dev-data/seed-v78.json` (gitignored) for Settings → Import / Export → Import JSON.
