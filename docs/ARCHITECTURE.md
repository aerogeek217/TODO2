# Architecture Overview

This file is the always-loaded orientation. For per-abstraction detail, load the relevant reference file under [Detail References](#detail-references).

## Tech Stack
- **Frontend**: React 19 + TypeScript, built with Vite
- **State**: Zustand stores
- **Database**: Dexie.js over IndexedDB (local-first)
- **Drag-and-Drop**: dnd-kit
- **Routing**: React Router v7 data router (`createHashRouter` + `RouterProvider`; one splat route renders the shell's `<Routes>`, so `useBlocker` is available)
- **Builds + CSP** (a `<meta>` in `index.html`, `base-uri 'none'; form-action 'none'` everywhere): the online build (`vite.config.ts`; `dist/index.html`) loads scripts from `./assets` only, so its `cdnFonts` plugin drops `script-src 'unsafe-inline'` (and adds Google Fonts) and `noInlineScripts` fails the build on any inline script; the offline single file (`vite.config.offline.ts`; `dist/todo2.html`) keeps `'unsafe-inline'` for its one inline script and allows its embedded `data:` fonts (`offlineCsp`); its icons are `data:` URLs too (SVG, the .ico's 16–64 px bitmaps, the 192 px PNG — `offlineIcons`) and it has no manifest link, so the file works alone from disk. Dev keeps `'unsafe-inline'` for the React refresh preamble

## Data Flow

1. **Startup** (`services/app-startup.runAppStartup`, in order; before it `App.tsx` checks the database's version — below the floor → `MigrationDialog`, above this build's (a newer build saved it) → only `DatabaseTooNewDialog`, nothing read or written): Dexie opens IndexedDB → settings load (theme + `data-theme` on `<html>`; user color overrides applied as inline styles) → `fileStorageService.initialize()` reconnects the file handle (concurrent calls share one run). When the handle needs permission again (after a browser restart) launch **waits for the launch question** (`LaunchPermissionDialog` over the start screen, asked at every launch while that holds): **Grant access…** → the browser's prompt → the load decision below (its prompts over the start screen; refused → the question says so and stays); **Continue without the file** / Esc → this browser's data, permission still needed (the storage pill says so), nothing written to the file. Nothing below — store loads, the purge check, persistent storage, automatic backups — runs before the answer. The load decision: nothing on either side changes until the user resolves any disagreement (conflict / older file / unreadable file → `SyncConflictDialog` / `FileUpgradeDialog` / paused (the storage pill); state in `services/file-sync-state.ts`; sides that match once an older file is upgraded are not a conflict — e.g. a browser DB upgraded at open, with no sync record, and its in-sync older file → `FileUpgradeDialog`) → people / statuses / tags load. If `completedRetentionDays` is set, completed tasks past it (keyed on `TodoItem.completedAt`, `utils/completed-at.ts`) are **never purged silently**: launch's check records their uids after the sync-file load (or the launch question's answer) — and `App.tsx` checks again after any load that applied file data once that check began (Grant access, Attach / Open file, a retry, a resolved conflict: `fileStorageService.onAfterImport`; only uids the prompt hasn't already asked about this launch) — and `StartupPurgePrompt` → `PurgeCompletedDialog` asks (Export & delete → task archive via `services/purge-completed` + `services/task-archive`; Delete; Not now = this launch, unless a later file load brings other expired tasks). `backupScheduler.start()` takes an automatic backup when the last one is a day old (or there is none), then checks hourly; each backup kind (auto / pre-op / manual / sync file) keeps its own newest few.
2. **Normal use**: UI → Zustand stores → repository methods → Dexie. If file storage is syncing, Dexie hooks debounce-save to the JSON file; while paused or awaiting permission the same hooks only mark the browser dirty (`dirtySince`), which forces a conflict prompt on the next load. Cross-cutting capture rides `QuickAddBar` (`Ctrl+Space` / the top bar's New task / mobile FAB / `command-registry.openQuickAdd`); the `TaskEditPopup` create modal is reachable via QuickAdd's Details handoff.
3. **Workspace**: a layout is columns of cells plus at most one full-width band above and one below the columns (not a recursive split tree — the bands are the only rows); a band is a cell spanning the workspace, its height in px. `WorkspacePage` opens the active layout (`useWorkspaceStore.init()`; a fresh database gets an empty "Default" layout). Stored layouts are read through the layout repair (`layoutRepository` → `ReadLayout`; a band is checked like a cell): a part this build can't use is dropped in memory, and the layout opens unsaved with a notice until it is saved. Layout edits (add / move / close / split / resize widgets, drag a tab or a whole panel by its header's empty space, make / merge into / close a band, band height, layout config) make the working copy unsaved until Save (kept in the browser across a reload, never in the database — `data/draft-storage`; a data replace after the workspace opened forgets it); New layout asks a name and stores the empty layout at once (an unsaved new layout an older build kept still opens, and its Save asks a name); the layouts' order (`sortOrder`, the top bar's tabs and the picker) is saved at once, as one undo step, never a layout change; view state (active tab, collapse — cells and bands —, calendar view / offset, the task rows' details width) is written straight away. On a phone the same layout shows one column (or band) at a time: the top band first, the bottom band last.
4. **Navigation**: desktop has one page — the workspace — under one top bar; the layout tabs (or, folded, the layout picker) are the "you are here" mark. Settings is a modal over it (gear, `G S`, palette "Open Settings", the storage pill — Database at its File storage part —, or the `#/settings` deep link), so it never changes the route and never prompts about unsaved layouts. On mobile the BottomTabBar routes between `/` and `/settings` (the workspace's `useBlocker` prompts when leaving with unsaved work). The old page routes (`/workspace`, `/list`, `/calendar`, `/dashboard`) redirect to `/`.
5. **People / tags**: many-to-many via `todoPeople` / `todoTags` joins; `usePersonStore.assignedPeopleMap` / `useTagStore.assignedTagsMap` cache them. A person's optional `color` fills their avatar / chip / group swatch (`NEUTRAL_PERSON_COLOR` when unset). An optional `email` (Settings → People; people created on the fly have none) is what email check-ins send to. `Org: <name>` people and `Project: <name>` tags (from the org / project migrations) are naming conventions only — no special handling.
6. **List widgets**: a list shows every task it matches (its panel scrolls). A list tab runs its definition through `useBuiltList` with the top-bar (screen) filter composed in — narrowing clauses AND (strict, even on the same field; each side keeps its own "is not" switches), `showCompleted` ORs (`utils/filter-criteria.composeScreenFilter`). An "is not" field seeds nothing on Add task; a prompt pick replaces its field as "is". Edits to the definition from a widget (filter chips, Edit list, switch to manual) go to `list-draft-store`: every widget showing the list renders the draft and shows it unsaved — tab dot, Revert · Save on its filter line — until Save writes it or Revert drops it (Undo brings it back); kept across a reload while the saved list is unchanged. Settings › Lists edits the saved list in its own modal, and its Save drops the workspace draft; `UnsavedPrompt` asks before a layout switch, leaving the workspace or closing the list's last widget would drop it. Prompt picks live in `list-widget-store` and are never saved. Manual order is per list (`listOrders`) and saves at once. The Eisenhower has its own list (a hidden list owned by the Eisenhower, named by the `eisenhowerSource` setting — made at app startup or after a data replace when missing, `ensureEisenhowerList`; no filter = every task — every Eisenhower tab and the dashboard section): each Eisenhower tab is a widget showing the list for all of the above (`tabListId`), with the list's filter line; Settings › Tasks › Eisenhower edits the same draft. **Layout-only lists**: a list owned by one layout (`owner: { layoutId }`, made from the list picker's This layout only, while the open layout is saved) is a list like any other but offered only in that layout's list picker / Change list; a layout Save deletes its own lists no saved tab shows (their manual order and drafts too; Discard keeps them), Save as copies the ones it shows for the new layout (as edited, with their manual order — `layoutRepository.insertWithListCopies`), Delete layout deletes them (`deleteUnlessLast`, one transaction; the confirm says so), the tab menu's Save to my lists makes one a saved list. The Eisenhower's list belongs to no layout: none of these touch it.
7. **Dashboard**: a dashboard tab computes every number with the pure `services/stats/*` functions over the tasks passing the screen filter (completed included, for the trend; `statsFilter`) and over all tasks, so counts read `shown of total`; list tiles run each list's predicate AND the screen filter (unsaved list drafts included). The trend reads `todoEvents` once per (range, day) through `trend-events-store`. What shows (tiles, list tiles, sections, their order and options) is the tab's `config`, saved with the layout. The Eisenhower section counts with the app-wide Eisenhower panes over the Eisenhower's own list (as every Eisenhower tab), its drills and Copy summary line named by the panes.
8. **Email check-ins** (offline, no mail API): an entry that names one person sends at once (`checkin-email/person-checkin.sendPersonCheckin`, the saved task scope and open method); `CheckinDialog` picks several people and a task scope (`utils/checkin-settings`, remembered) — and opens for one person when the one-click send can't send. Either way `services/checkin-email` selects each person's open tasks and builds the email (HTML + plain text, a `Ref <token>` per task from its uid, a `Your update` box per task, the footer `Check-in for <name> · sent <date>`) → per person either the rich clipboard + a `mailto:` link (To + Subject — an empty To without a valid address, the recipient then typed in the mail app; the user pastes the body) or a downloaded `.eml` draft (no To header without an address), then `markFollowedUp` on the emailed tasks as one undo entry. The status line (the dialog's, and the one-click send's snackbar line — `checkinSentStatus`) names the address it went to, or says to add the recipient, and how to finish. Nothing about the send is stored. The reply comes back by paste: `CheckinImportDialog` → `checkin-reply/parse` (HTML in an inert document, else plain text; tasks found by Ref, the newest email in a thread only) → `diff` against current values (a task modified on a later day than the footer's send date is flagged and unticked) → `apply` writes the ticked changes through the todo store as one undo group.

## Testing

Two layers, picked by what's being verified:

- **vitest (`npm test`)** — unit + JSDOM under `src/test/**`. Authoritative for pure logic, models, repositories, store reducers, services, utilities, and rendering / event-handler dispatch that doesn't depend on real layout, focus, or async DOM timing. `e2e/**` is excluded from the vitest sweep. `vitest.config.ts` splits two projects: `isolated` — any test file calling `vi.mock` / `vi.doMock` (detected at config load), one fresh worker per file so module fakes can't leak; `shared` — every other file, `isolate: false` (one jsdom + module cache per worker, the bulk of the speed-up). **Before every test, in both projects**, `src/test/setup.ts` puts every zustand store back to `getInitialState()` (its `vi.mock('zustand')` wrapper, `src/test/store-tracking.ts`, registers each store as it is created) and runs `utils/module-reset.resetModuleState()`: every module with state outside a store registers its own reset when it loads (`registerModuleReset` — writes and loads in flight in `store-helpers`, `fileStorageService`, `backupScheduler`, the file-handle cache, the file-storage prompts, the note store's save timer / queue, the settings store's OS-theme listener, the list-order load), so a new singleton is covered by registering, not by a list in the setup. **At each file boundary of the shared project**, `src/test/setup-shared.ts` restores the rest of what a fresh worker would give: the Dexie db deleted, Testing Library `cleanup()`, `<body>` / `<html>` attributes / storage / URL cleared, real timers, global + env stubs undone (and clipboard stubs a file defined straight on `navigator` / `globalThis`), `vi.spyOn` spies restored. `src/test/**` is type-checked by `tsc -b` (`tsconfig.test.json`: the app's options plus Node's types) and linted with type information like the rest. The test / hook timeout is 30 s (a heavy test can take several times its ~1 s on a loaded machine); "stays fast on huge input" checks go through `src/test/timing.expectWithin(ms, run)` — the best of up to three runs against the bound (a super-linear regression slows every run, load slows one).
- **Playwright (`npm run test:e2e`)** — Chromium-only real-browser flows under `e2e/**`. Starts its own `npm run dev` on port 5173, or `PW_PORT` when set (the everyday dev server is 5180; with `reuseExistingServer` a second checkout must pick its own port or it tests the first one's code), `--strictPort`, `trace: 'retain-on-failure'`, `fullyParallel` (each test has its own browser context, so tests within one spec spread across workers). Fixtures live in `e2e/fixtures/` (`workspace.ts` seeds layouts / lists / tasks straight into IndexedDB — `seedWorkspace`, `seedTaskList` — and drives trusted-mouse drags — `drag(page, from, to, { lifted, during })` (behind `dragTab` / `dragRow` / `dragPanel`; locators `wsCell` / `wsTab` / `wsBand` / `wsBandTabs` / `wsPanelHandle` / `wsListWidget`) crosses the 5 px activation distance and ends in `releaseDrag`, which waits out dnd-kit's 50 ms post-drag click block so the next click isn't swallowed; `gotoSettingsDeepLink` / `openSettings` open the Settings modal without racing the `#/settings` deep link's effect; `seed.ts` holds the task-row locators and `rowTitles`; `db.ts` reads and writes the app's IndexedDB straight (`readStore` / `readStores` / `writeStores` / `assignedNames`, and `afterTransactionsOn` — resolves once the app's transactions on given stores have finished); `geometry.ts` has `box`, `pointIn`, `expectInsideViewport`, `clickOutside`; `render-count.ts` counts named components' renders through a stand-in React DevTools hook installed before the app loads (dev server names; for "this interaction renders no row" checks without timing — it leans on React's fiber internals, so `expectCounterLive` first proves it still sees renders and a React change fails loudly); `sync-file.ts`'s `readSyncFile` reads an OPFS sync file only once `fileStorageService.whenIdle()` resolves — a `File` read while a save swaps the file in throws `NotFoundError`; `attachSyncHandle` stores a sync file's handle as an earlier session would, and `stubFilePermission` / `setPermissionAnswer` / `answerPermission` script the browser's permission answers for the launch question). `built-csp.spec.ts` builds both targets into a temp folder and runs them (online served over http, offline from `file://`) with no CSP violations. The app is hash-routed (`/#/`, `/#/settings`). Specs wait on app state (a locator, a stored row, `whenIdle`, a database turn), never on timers (`waitForTimeout`). CI (the deploy workflow) runs only the vitest suite (`npm test`, before the build) — Playwright stays local.

**Folder cycles.** `src/test/architecture/folder-cycles.test.ts` scans every relative import in `src/` (static, dynamic, CSS, `composes … from`) into a graph of folders (`components/<area>`, the other top-level folders, each top-level file) and fails on any cycle. Its allow-list of edges is empty; an entry would fail once its edge is gone. The layers it holds in place, lowest first: `models` / `utils` → `data` → `stores` → `services` → `hooks` → `components` → `views` (each imports only from layers before it; services orchestrate stores, never the reverse).

**JSDOM is not authoritative** for: focus handoffs, `ResizeObserver`-driven layout, drag-and-drop hit-testing (workspace tab drags, list row drags, calendar day drops), popover anchor placement and viewport flips, and async-store-driven re-render timing. Those categories require a Playwright spec — JSDOM passing is not enough signal.

**Diagnosis vs. regression.** The Chrome DevTools MCP server (`mcp__chrome-devtools__*`) is a *spike* tool — drive an interaction live in real Chromium, capture state, then codify the regression in Playwright. See CLAUDE.md "Tools — Chrome DevTools MCP".

**Manual-testing seed.** `npm run seed:dev` (`scripts/dev-seed.ts`) writes a realistic v49 export (with orgs, projects, a taskboard and a canvas, so the whole upgrade path runs) with dates relative to the run day to `dev-data/seed-v49.json` (gitignored); Settings → Import / Export → Import JSON in the dev server then runs the full v49 → current upgrade. `src/test/data/dev-seed.test.ts` keeps it importable.
