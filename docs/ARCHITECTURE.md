# Architecture Overview

This file is the always-loaded orientation: what lives where and how data moves. Every module's detail — its functions, rules and edge cases — is in the reference files under [Detail References](#detail-references); load the one you need.

## Tech Stack
- **Frontend**: React 19 + TypeScript, built with Vite
- **State**: Zustand stores
- **Database**: Dexie.js over IndexedDB (local-first, no backend)
- **Drag-and-Drop**: dnd-kit
- **Routing**: React Router v7 data router (`createHashRouter` + `RouterProvider`; one splat route renders the shell's `<Routes>`, so `useBlocker` is available)
- **Builds + CSP** (a `<meta>` in `index.html`, `base-uri 'none'; form-action 'none'` everywhere): the online build (`vite.config.ts`; `dist/index.html`) loads scripts from `./assets` only, so its `cdnFonts` plugin drops `script-src 'unsafe-inline'` (and adds Google Fonts) and `noInlineScripts` fails the build on any inline script; the offline single file (`vite.config.offline.ts`; `dist/todo2.html`) keeps `'unsafe-inline'` for its one inline script and allows its embedded `data:` fonts (`offlineCsp`); its icons are `data:` URLs too (SVG, the .ico's 16–64 px bitmaps, the 192 px PNG — `offlineIcons`) and it has no manifest link, so the file works alone from disk. Dev keeps `'unsafe-inline'` for the React refresh preamble

## Data Flow

1. **Startup** (`services/app-startup.runAppStartup`): `App.tsx` first checks the database's version (below the floor → `DatabaseTooOldDialog`, saved by a newer build → `DatabaseTooNewDialog`: Reload only, nothing read or written). Then settings load (theme, colour overrides) → the sync file reconnects (`fileStorageService.initialize()`). When its handle needs permission again, launch **waits for the launch question** (Grant access… / Continue without the file) before anything else runs. The load decision changes nothing on either side until the user resolves a disagreement (conflict / older file / unreadable → a dialog or a pause); a browser merely ahead of an unchanged file is written to it after a backup of the file's text. Then the stores load. Completed tasks past the retention are **never purged silently**: the purge prompt asks (Export & delete / Delete / Not now), at most once every N days, also after a later sync-file load. `backupScheduler.start()` takes a daily automatic backup; each backup kind keeps its newest few within a byte budget.
2. **Normal use**: UI → Zustand stores → repositories → Dexie. While a sync file is syncing, Dexie hooks debounce-save to it; while paused or waiting for permission they only mark the browser dirty, which the next load resolves (written to an unchanged file, else asked about). Destructive operations — a data replace, a purge, a bulk delete of more than five tasks, removing unused people and tags — back up first (`takeSafetySnapshot`; a failed backup asks before going on). New tasks come through `QuickAddBar` (its Details hands off to `TaskEditPopup`'s create mode).
3. **Data replaces** (`services/replace-data.replaceData`) — Settings import and backup restore, the audit's cleanup, the sync file's load, the append import: note saves held → safety snapshot → the write → the stores reload (`refresh-all`; an append import reloads the task stores only and keeps the undo history) → `onDataReplaced` listeners. A file (an import, a backup, the sync file) is read through the import pipeline first: one from below the schema floor (`OLDEST_SUPPORTED_DB_VERSION`, v68) or without a version is refused — nothing read, nothing written —, with a message naming the older build that still converts it.
4. **Workspace**: a layout is columns of cells plus an optional full-width band above and below (a band is a cell spanning the workspace). Stored layouts are read through the layout repair (a part this build can't use is dropped; the layout opens unsaved). Layout edits make the working copy unsaved until Save (kept in the browser across a reload, never in the database); the layouts' order and view state (pane sizes from the dividers, active tab, collapse, calendar view, row details width, the lens) save at once — a size among parts an unsaved edit added stays with that edit until Save. On a phone one column or band shows at a time.
   **Lenses** (D15) are named screen filters defined once (Settings › Tasks › Lenses, the `lenses` settings row; four presets seeded on its first open) and **picked per layout** (`lensId`, view state; Save as copies it, a new layout has none). Wherever the screen filter applies — lists, the Eisenhower, the dashboard, the calendar, the filtered-tasks panel and its counts — the open layout's lens composes under the top bar's chips (`stores/screen-filter`: `FilterCriteria.lens`, its own clauses and "is not" switches ANDed, completion left to the chips). The chips stay ad hoc on top: Clear all clears them only; the tray turns red for chips only. **Search tokens** (D16): what is typed in the top bar's search (or the phone sheet's) — `@person`, `#tag`, `/status …`, `/urgent` · `/hot`, `overdue`, `due ⟨phrase⟩`, `followup ⟨phrase⟩`, `no due`, `done` — becomes those chips as each token completes (`services/search-tokens` over Quick Add's parser → `filter-store.applySearchTokens`); the words left are the text search; Backspace in the empty box takes the last box-made chip back. The lens control's glasses lift the lens for now (`ui-store.lensLifted`) until a second click, a layout switch or a reload; the counter `61 of 109` says what the lens and chips keep of every open task. Deleting a lens a layout uses asks first and puts those layouts on No lens (one undo step).
5. **Navigation**: desktop is one page — the workspace under one top bar; Settings is a modal over it (gear, `G S`, the palette, the storage pill, `#/settings`), so it never changes the route. On a phone the bottom tab bar routes between `/` and `/settings`, and the workspace's `useBlocker` asks before unsaved work is left.
6. **Lists**: a list tab runs its definition through `useBuiltList` with the top-bar (screen) filter — the chips with the layout's lens — composed in (narrowing clauses AND, Show completed ORs). Its desktop rows are quiet (D17): a set date is its `MM/DD` alone, colour goes only to what needs action now (an overdue or due-soon due date, a follow-up today or late; avatars, tags and the status glyph are muted until the row is hovered), a hot task's title is semibold, a task untouched for Settings' `staleAfterDays` (default 30) is faded, and Settings › Appearance's row density lets titles wrap (`comfortable`). Group headers stick to the top of the body while their group scrolls; a list tab's menu collapses or expands every group. Edits from a widget go to `list-draft-store` — every widget showing the list shows the draft unsaved until Save or Revert; kept across a reload. Manual order is per list and saves at once. **Every list belongs to one layout** (`owner: { layoutId }`) and is offered only there: a layout's Save deletes its lists no saved tab shows, Save as copies the ones it shows, Delete takes them with it. The Eisenhower has its own hidden list (`owner: { eisenhower: true }`), shown by every Eisenhower tab and the dashboard's Eisenhower section, under the app-wide panes (Settings › Tasks › Eisenhower).
7. **People / tags**: many-to-many via `todoPeople` / `todoTags`, cached in the person / tag stores' assignment maps. A person's optional email is where check-ins go. `Org: <name>` people and `Project: <name>` tags (from the old org / project migrations) are naming conventions only. Every People / Status / Tags filter has a "none" choice, id 0 (Unassigned, No status, No tags): `Tags is No tags` keeps untagged tasks (a triage list), `Tags is not No tags` reads "has a tag". Settings › People, statuses & tags › Find unused… (Unused people & tags, a dialog) lists the ones no task has (optionally ignoring completed tasks, noting the filters that name them) and removes the ticked ones with their assignments as one undo step; filters naming them keep the ids and stop matching, as after a single delete.
8. **Dashboard**: every number comes from the pure `services/stats/*` functions over the screen-filtered tasks and over all tasks (`shown of total`); the trend reads `todoEvents` through `trend-events-store`. What shows is the tab's `config`, saved with the layout. A tile takes its colour only when its number asks for action (D18, `litWhen`).
9. **Email check-ins** (no mail API): `services/checkin-email` builds each person's email from their open tasks under the saved check-in filter (a `Ref` per task), hands it to the mail app (clipboard + `mailto:`, or an `.eml` draft) and marks the tasks followed up as one undo entry. A reply comes back by paste: `checkin-reply` parses it, diffs it against the tasks, and applies the ticked changes as one undo group.

## Testing

Two layers, picked by what's being verified (setup, fixtures and helpers: [architecture/testing.md](architecture/testing.md)):

- **vitest (`npm test`)** — unit + JSDOM under `src/test/**`: pure logic, models, repositories, stores, services, utilities, and rendering / event dispatch that doesn't depend on real layout, focus or async DOM timing. Two projects (`isolated` for files that mock modules, `shared` for the rest); every store and every registered module state is reset before each test.
- **Playwright (`npm run test:e2e`)** — Chromium-only real-browser flows under `e2e/**`, on its own dev server (port 5173, or `PW_PORT`). Specs wait on app state, never on timers. CI (the deploy workflow) runs only vitest.

**JSDOM is not authoritative** for focus handoffs, `ResizeObserver`-driven layout, drag-and-drop hit-testing, popover placement and viewport flips, and async-store-driven re-render timing — those need a Playwright spec.

**Diagnosis vs. regression.** The Chrome DevTools MCP server (`mcp__chrome-devtools__*`) is a *spike* tool — drive an interaction live in real Chromium, then codify the regression in Playwright. See CLAUDE.md "Tools — Chrome DevTools MCP".

**Manual-testing seed.** `npm run seed:dev` writes a realistic export in the current schema to `dev-data/seed-v68.json` (gitignored) for Settings → Import / Export → Import JSON.
