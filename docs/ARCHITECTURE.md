# Architecture Overview

This file is the always-loaded orientation: what lives where and how data moves. Every module's detail — its functions, rules and edge cases — is in the reference files under [Detail References](#detail-references); load the one you need.

## Tech Stack
- **Frontend**: React 19 + TypeScript, built with Vite
- **State**: Zustand stores
- **Database**: Dexie.js over IndexedDB (local-first, no backend)
- **Drag-and-Drop**: dnd-kit
- **Routing**: React Router v7 data router (`createHashRouter` + `RouterProvider`; one splat route renders the shell's `<Routes>`, so `useBlocker` is available)
- **Builds + CSP** (a `<meta>` in `index.html`, first in its head, `base-uri 'none'; form-action 'none'` everywhere): the online build (`vite.config.ts`; `dist/index.html`) loads scripts from `./assets` only, so its `cdnFonts` plugin drops `script-src 'unsafe-inline'` (and adds Google Fonts) and `noInlineScripts` fails the build on any inline script. The offline single file (`vite.config.offline.ts`; `dist/todo2.html`) **makes no network request**: its own policy (`offlineCsp`) denies by default and names no `'self'` (on `file://` it would admit any `file:` URL, a UNC share's among them) — inline styles, `data:` images and fonts, no connect / frame / object / worker / media / manifest (the check-in dialog's message is a sandboxed `srcdoc` frame, which fetches nothing) — and allows its one inline script by its sha256 (`offlineScriptHash`, the build's last step, over the final text; the build fails on a second script or a mismatch); it sends no Referer and turns DNS prefetch off. The build then runs the **egress check** on the finished file (`offlineEgressCheck` → `scripts/offline-file.checkOfflineFile`): it fails on anything that loads, a `<!--` in its script text (after it a `<script` would make the browser read past the first `</script` the check stops at), a looser policy (a CSP directive named twice too: browsers enforce its first copy), no `no-referrer` / DNS-prefetch-off meta, a network API in the code (a reference to `window.open`, called or not; a resource hint's rel value, quoted anywhere in the script — the library hint code the app never calls is on its inert list) or a URL off its inert list (protocol-relative ones too, a dotless UNC `//host/share` among them) — each inert entry with its reason; ESLint bans the network APIs in `src/` (and the HTML-parsing sinks — `innerHTML` / `outerHTML` writes, `insertAdjacentHTML`, `document.write`, `dangerouslySetInnerHTML`: nodes are built, never parsed from a string), and `e2e/built-csp.spec.ts` audits the file's requests through its main flows. The sync file, imports and exports go through the File System Access API, file inputs and downloads, which no fetch directive governs. Its icons are `data:` URLs too (SVG, the .ico's 16–64 px bitmaps, the 192 px PNG — `offlineIcons`) and it has no manifest link, so the file works alone from disk. Dev keeps `'unsafe-inline'` for the React refresh preamble

## Data Flow

1. **Startup** (`services/app-startup.runAppStartup`): `App.tsx` first checks the database's version (below the floor → `DatabaseTooOldDialog`: nothing read or written — Download this data, or Import a file… that replaces it after asking, or Reload; saved by a newer build → `DatabaseTooNewDialog`: Reload only, nothing read or written). Then settings load (theme, colour overrides) → the sync file reconnects (`fileStorageService.initialize()`). When its handle needs permission again, launch **waits for the launch question** (Grant access… / Continue without the file) before anything else runs. The load decision changes nothing on either side until the user resolves a disagreement (conflict / older file / unreadable → a dialog or a pause); a browser merely ahead of an unchanged file is written to it after a backup of the file's text. Then the stores load. Completed tasks past the retention are **never purged silently**, and launch opens no dialog about them: the storage pill shows a **purge notice** (`17 old completed` — after any sync or backup warning, which outranks it; the phone's sync sheet too) whose section offers **Review…** — the purge dialog (Export & delete / Delete / Not now; a backup snapshot first), the only way anything is deleted — and **Not now**. It is offered at most once every N days, counted from when the user was last asked (the dialog opened, or Not now) — a notice merely shown stamps nothing, so one left unanswered is there at the next launch —, also after a later sync-file load; a change that leaves none expired (deleted, reopened, retention off) removes it (`stores/purge-notice-store`, read by `overlays/PurgeNoticeHost`). `backupScheduler.start()` takes a daily automatic backup; each backup kind keeps its newest few within a byte budget.
2. **Normal use**: UI → Zustand stores → repositories → Dexie. While a sync file is syncing, Dexie hooks debounce-save to it; while paused or waiting for permission they only mark the browser dirty, which the next load resolves (written to an unchanged file, else asked about). Every task write stamps the task's `modifiedAt` (the stale fade, the Modified filter and sort read it), in the store and the database alike; **an undo puts back the stamp the task had before the step, a redo the one the step wrote** — each only where the task still holds the stamp the other left, so a task touched since keeps its newer one (`utils/task-stamps`, cr32; the same rule for field edits, completions, follow-ups, priority flags, status updates, subtasks and assignments; a delete's undo puts the row back with its stored stamp). Destructive operations — a data replace, a purge, a bulk delete of more than five tasks, removing unused people and tags — back up first (`takeSafetySnapshot`; a failed backup asks before going on). New tasks come through `QuickAddBar` (its Details hands off to `TaskEditPopup`'s create mode). **A new task flies home** (flair P4, `overlays/task-fly`): when a list row on screen shows it — drawn, its centre in view and the topmost thing there (or its list `.row`, whose `content-visibility: auto` skips a just-added row's contents until a frame finds it on screen), looking through the closing Quick Add / New task editor (`FLIGHT_SEE_THROUGH_ATTR`) and the pill itself — a ghost of its title flies there from Quick Add's place, the row held closed until it lands, then opening and glowing; otherwise (no such row, a phone, reduced motion) the recent-task pill shows as before.
3. **Data replaces** (`services/replace-data.replaceData`) — Settings import and backup restore, the audit's cleanup, the sync file's load, the append import: note saves held → safety snapshot → layout writes in flight settled → the write → the stores reload (`refresh-all`; an append import reloads the task stores only and keeps the undo history) → `onDataReplaced` listeners. From the write until the reload has opened the new data, a replace (not an append import) holds layout and list writes (`stores/replace-hold`): the stores still hold the replaced data and their writes put whole rows, so an edit then (a tab closed, a rename, an undo) changes nothing and says why rather than writing the old layout or list over the new data. A file (an import, a backup, the sync file) is read through the import pipeline first: one from below the schema floor (`OLDEST_SUPPORTED_DB_VERSION`, v68) or without a version is refused — nothing read, nothing written —, with a message naming the older build that still converts it. One whose layouts hold far more parts than the app keeps is refused too, with a message, before the schema upgrades run (`data/layout-size`); a layout row the check rejects is **repaired**, as the database read repairs it, and stored repaired with a warning — never the whole file refused.
4. **Workspace**: a layout is one **table** (D26, schema v78, `models/workspace-layout`): grid lines across and down — `grid.columns` and `grid.rows`, each a list of `GridTrack`s (`{ id, weight?, px?, collapsed? }`: a weighted track, its share of the axis, or a fixed `px` track, a former band) — and `cells`, each covering a rectangle of tracks (`area { col, row, colSpan, rowSpan }`, track indices) and holding a strip of widget tabs. A full-height column is a cell spanning every row track, a strip a cell spanning every column track; nothing nests. The cells tile the grid exactly (no gap, no overlap) and every grid line is the edge of some cell (`utils/workspace-grid`: the queries — neighbours along an edge, whether two cells merge into a rectangle, reading order, edge stretches —, `normalizeGrid`, which merges the two tracks beside a line no cell's edge lies on and expands a collapsed row nothing can expand (below), and `validateTiling`); a cell with no tabs is an **empty cell** (a split's new cell, a close with no taker, or a lone widget removed). **The rule** (layout edit mode E4, said in the UI too): **edit mode changes the grid; what's inside a cell changes in place** — cells, rows and columns (split, merge, insert, close, a cell or a tab moved to another cell) change only in the layout edit mode (below); a cell's tabs, a Numbers strip's Numbers, a widget's kind and settings, the row's collapse and the dividers change in place (a divider's Alt-drag, which breaks part of a line off into a new one, is the one grid change made outside the mode, an undo step like any other). **The ops** (`utils/workspace-layout-ops`; each returns a normalized table, or the same layout when there is nothing to do, which `dropChangesLayout` relies on): `splitCell` (a new empty cell on a side, taking half — an even span splits on its middle line, an odd one splits its middle track, the cells crossing it then spanning both halves; the new cell never comes out collapsed — split below / above a collapsed cell, the old half keeps its collapse, while beside it in a collapsed row the row expands), `insertTrack` (a row at the top / bottom or a column at the left / right, full width / height, holding one new empty cell, half the nearest weighted track's size; a new column across collapsed rows expands them), `insertTrackBeside` (a row above / below a cell's row or a column left / right of its column: on that inner line, half of the cell's track, the cells spanning across the line growing into it and the gaps beside them new empty cells; at an outer edge `insertTrack`), `insertTrackAt` (the edit mode's rulers, E2: a full row / column on any line of the table — the cells crossing it growing across, its other places new empty cells; the edges `insertTrack`; given a run of lines whose tracks between are slivers (`through`), it first merges the slivers into the major track beside them, so the new track goes on the one line left, sized from that major; `insertPreviewGaps` reads off the result where its new empty cells go, which a "+"'s guide draws), `removeTrack` (a ruler's Remove row / column, refused for an axis's last track: along the axis a cell spanning the track — through it, or starting or ending in it — shrinks; ## Dismissing a popover

A change a popover shows either sticks or the user is warned. Esc or a click off saves what was typed (`FollowupPopover`, `SubtaskChecklist` in every host, `TaskNotePopover`; in the task editor the Status updates add line and + Add subtask line, which Esc leaves and the editor's close adds): each writes it in an unmount cleanup, so every way of closing is covered, and only a Cancel button drops it. Esc inside an inline edit — a subtask rename, a status entry — cancels that edit and leaves the popover or editor open. Text that can't be stored holds the close once, saying so; closing again drops it (a filter expression that doesn't read too: the first press outside its field, `ExpressionField`). Edit list and the widget editors (a Number's, a chart's, Project pulse's, Created vs completed's) hold a copy until their Save, which writes it for good as one undo step (layouts and lists themselves have no Save: every other edit is stored at once): closing one with changes asks Save / Discard / Keep editing, and the press that asked goes no further; closing one with none just closes. The layout edit mode holds its draft the same way, as a layout-wide editor: only leaving the layout asks it (Save / Discard / Keep editing), never what is done inside it; its Cancel asks nothing and offers Restore instead. **Nothing leaves one with changes without that question** — one rule, `stores/editor-leave` (each registers through `hooks/use-editor-leave` while mounted): whatever would close it or take its subject off the screen from outside asks first and then carries on — Save or Discard, then it does what was asked; Keep editing, nothing changes: opening Settings (the gear, `G S`, the palette, the storage pill — `ui-store.openSettings`), opening another editor (`openListEditor` / `openNumberEditor` / a chart's or Project pulse's — another list's Edit list opens once this one was saved or discarded; `widget-hooks.openEditList` asks before it shows the tab; one editor at a time, whatever its kind: `editor-leave.openOneEditor` closes any other, and `closeOpenEditors` is the one roster Settings, the widget popup and a data replace close them through), adding a widget (`widget-hooks.addTabToCell` / `AddWidgetFlow`: a ⋯'s Add widget as tab ›, an empty cell's kinds, the strip's `+`, the palette's Add Widget ›), opening the layout edit mode (`workspace-store.enterEdit`, which then closes every editor), **whatever in a cell can take a widget off the screen** (`FilledCell`, `cell-menu`, the phone's cell: a tab switched — a click, Enter, the arrow keys, the `+N` menu — or closed, Collapse / Expand row, the menu's Remove widget and Change widget — from the keys or a menu, a press elsewhere having asked already; the one press that carries on is a tab's: held by the question, it is made again once the answer is Save or Discard (`use-editor-leave.carryOnAfterLeave`), so a click switches tabs as the keys do, with one question; after it the focus is on the new tab), opening an editor on a tab out of sight (`widget-hooks.openBeside`, every editor's way in), closing the widget popup over an editor opened from it (its ×, its scrim, Esc) and a Review jump that would close it, a layout switch from the tabs, the picker, the palette or a shortcut, New / Duplicate layout, deleting the open layout (`workspace-store.load` / `createLayout` / `duplicateLayout` / `delete`), and an in-app route change — the phone's tab bar, the browser's back / forward (`WorkspacePage`'s `useBlocker`). The task editor, Quick Add and the palette itself open over an editor without closing it; the widget popup (Open larger, the popup review) covers the workspace and asks first, as Settings does (item 4). A closed tab or a reload asks nothing (the widget editors never did; nothing is kept), and an editor closed anyway — its subject gone where nothing could ask: a data replace (the draft may name a list the new data lacks, so it is dropped), an undo, a hash typed in (the router can't hold a navigation it didn't make), a cell resized too small to draw its widget whole (a divider, the window) — says so (`Edit list closed: its changes to “X” weren’t saved.`). Nothing exists yet behind Quick Add, the new-task editor and the convert preview's edited drafts, so they ask instead (Create task / Discard / Keep editing, or Discard / Keep editing with no title) — on Esc, a press on the backdrop and the new-task editor's × —, and only when the form differs from how it opened; the editor's Cancel button discards without asking. Filter and picker popovers write on every change; a date panel's pending Is not, which no clause can hold yet, is kept per filter (`filters/date-pending-not`).

## Testing

Two layers, picked by what's being verified (setup, fixtures and helpers: [architecture/testing.md](architecture/testing.md)):

- **vitest (`npm test`)** — unit + JSDOM under `src/test/**`: pure logic, models, repositories, stores, services, utilities, and rendering / event dispatch that doesn't depend on real layout, focus or async DOM timing. Two projects (`isolated` for files that mock modules, `shared` for the rest); every store and every registered module state is reset before each test.
- **Playwright (`npm run test:e2e`)** — Chromium-only real-browser flows under `e2e/**`, on its own dev server (port 5173, or `PW_PORT`). Specs wait on app state, never on timers. CI (the deploy workflow) runs only vitest.

**JSDOM is not authoritative** for focus handoffs, `ResizeObserver`-driven layout, drag-and-drop hit-testing, popover placement and viewport flips, and async-store-driven re-render timing — those need a Playwright spec.

**Diagnosis vs. regression.** The Chrome DevTools MCP server (`mcp__chrome-devtools__*`) is a *spike* tool — drive an interaction live in real Chromium, then codify the regression in Playwright. See CLAUDE.md "Tools — Chrome DevTools MCP".

**Manual-testing seed.** `npm run seed:dev` writes a realistic export in the current schema to `dev-data/seed-v82.json` (gitignored) for Settings → Import / Export → Import JSON.
