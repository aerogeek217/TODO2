# Architecture Overview

This file is the always-loaded orientation: what lives where and how data moves. Every module's detail — its functions, rules and edge cases — is in the reference files under [Detail References](#detail-references); load the one you need.

## Tech Stack
- **Frontend**: React 19 + TypeScript, built with Vite
- **State**: Zustand stores
- **Database**: Dexie.js over IndexedDB (local-first, no backend)
- **Drag-and-Drop**: dnd-kit
- **Routing**: React Router v7 data router (`createHashRouter` + `RouterProvider`; one splat route renders the shell's `<Routes>`, so `useBlocker` is available)
- **Builds + CSP** (a `<meta>` in `index.html`, first in its head, `base-uri 'none'; form-action 'none'` everywhere): the online build (`vite.config.ts`; `dist/index.html`) loads scripts from `./assets` only, so its `cdnFonts` plugin drops `script-src 'unsafe-inline'` (and adds Google Fonts) and `noInlineScripts` fails the build on any inline script. The offline single file (`vite.config.offline.ts`; `dist/todo2.html`) **makes no network request**: its own policy (`offlineCsp`) denies by default and names no `'self'` (on `file://` it would admit any `file:` URL, a UNC share's among them) — inline styles, `data:` images and fonts, no connect / frame / object / worker / media / manifest (the check-in preview is a sandboxed `srcdoc` frame, which fetches nothing) — and allows its one inline script by its sha256 (`offlineScriptHash`, the build's last step, over the final text; the build fails on a second script or a mismatch); it sends no Referer and turns DNS prefetch off. The build then runs the **egress check** on the finished file (`offlineEgressCheck` → `scripts/offline-file.checkOfflineFile`): it fails on anything that loads, a `<!--` in its script text (after it a `<script` would make the browser read past the first `</script` the check stops at), a looser policy (a CSP directive named twice too: browsers enforce its first copy), no `no-referrer` / DNS-prefetch-off meta, a network API in the code (a reference to `window.open`, called or not; a resource hint's rel value, quoted anywhere in the script — the library hint code the app never calls is on its inert list) or a URL off its inert list (protocol-relative ones too, a dotless UNC `//host/share` among them) — each inert entry with its reason; ESLint bans the network APIs in `src/` (and the HTML-parsing sinks — `innerHTML` / `outerHTML` writes, `insertAdjacentHTML`, `document.write`, `dangerouslySetInnerHTML`: nodes are built, never parsed from a string), and `e2e/built-csp.spec.ts` audits the file's requests through its main flows. The sync file, imports and exports go through the File System Access API, file inputs and downloads, which no fetch directive governs. Its icons are `data:` URLs too (SVG, the .ico's 16–64 px bitmaps, the 192 px PNG — `offlineIcons`) and it has no manifest link, so the file works alone from disk. Dev keeps `'unsafe-inline'` for the React refresh preamble

## Data Flow

1. **Startup** (`services/app-startup.runAppStartup`): `App.tsx` first checks the database's version (below the floor → `DatabaseTooOldDialog`: nothing read or written — Download this data, or Import a file… that replaces it after asking, or Reload; saved by a newer build → `DatabaseTooNewDialog`: Reload only, nothing read or written). Then settings load (theme, colour overrides) → the sync file reconnects (`fileStorageService.initialize()`). When its handle needs permission again, launch **waits for the launch question** (Grant access… / Continue without the file) before anything else runs. The load decision changes nothing on either side until the user resolves a disagreement (conflict / older file / unreadable → a dialog or a pause); a browser merely ahead of an unchanged file is written to it after a backup of the file's text. Then the stores load. Completed tasks past the retention are **never purged silently**: the purge prompt asks (Export & delete / Delete / Not now), at most once every N days, also after a later sync-file load. `backupScheduler.start()` takes a daily automatic backup; each backup kind keeps its newest few within a byte budget.
2. **Normal use**: UI → Zustand stores → repositories → Dexie. While a sync file is syncing, Dexie hooks debounce-save to it; while paused or waiting for permission they only mark the browser dirty, which the next load resolves (written to an unchanged file, else asked about). Every task write stamps the task's `modifiedAt` (the stale fade, the Modified filter and sort read it), in the store and the database alike; **an undo puts back the stamp the task had before the step, a redo the one the step wrote** — each only where the task still holds the stamp the other left, so a task touched since keeps its newer one (`utils/task-stamps`, cr32; the same rule for field edits, completions, follow-ups, priority flags, status updates, subtasks and assignments; a delete's undo puts the row back with its stored stamp). Destructive operations — a data replace, a purge, a bulk delete of more than five tasks, removing unused people and tags — back up first (`takeSafetySnapshot`; a failed backup asks before going on). New tasks come through `QuickAddBar` (its Details hands off to `TaskEditPopup`'s create mode).
3. **Data replaces** (`services/replace-data.replaceData`) — Settings import and backup restore, the audit's cleanup, the sync file's load, the append import: note saves held → safety snapshot → the write → the stores reload (`refresh-all`; an append import reloads the task stores only and keeps the undo history) → `onDataReplaced` listeners. A file (an import, a backup, the sync file) is read through the import pipeline first: one from below the schema floor (`OLDEST_SUPPORTED_DB_VERSION`, v68) or without a version is refused — nothing read, nothing written —, with a message naming the older build that still converts it.
4. **Workspace**: a layout has three levels, **columns → rows → cells** (D25 O, schema v76, `models/workspace-layout`): the column area is a row of columns, each a stack of rows, each row one or more cells side by side, each cell a strip of widget tabs; an optional full-width band above and below is one fixed-height row of cells. No deeper: a cell in a row never splits again. Sizes are weights — a column's share of the width, a row's of its column's height, a cell's of its row's width — set by the dividers between them (Resize rows, Resize cells); collapse belongs to the row (and the band): a row collapses to its cells' headers, so a cell of a multi-cell row can't collapse alone (Collapse row). A tab or panel dropped on a cell body (`utils/workspace-drop`): its top / bottom zone makes a new row above / below that row, its left / right zone (the outer 20 %, at most 120px) a cell beside it in the row, its middle joins its tabs; a band body has left / middle / right only. The cell menu splits Right (in its row) · Below (a new row) · New column. **Headless cells** (`utils/workspace-rows`): a cell holding one tab of a glance widget — or of any widget at its small face — hides its tab strip, which slides in over the body's top on hover, keyboard focus or while its menu is open, and its right-click opens the tab menu; the cell menu's Show / Hide tab strip overrides it (`LayoutCell.stripShown`, layout config; choosing what the widget would do anyway clears it). **Fit rows**: a column row whose every cell holds one Number fits its content (~64–76px; `flex: none`, no weight — one added between rows takes none of theirs —, no divider resize, gaps beside it, the weighted rows on either side keeping a divider across it); a row (or band) of glance widgets only may shrink to 64px, any other to `CELL_MIN_PX`. **Faces** (D25 R, `utils/widget-face` + `hooks/use-widget-face`): a widget draws its small, medium or large face by its cell body's measured size — small at most 90px tall or 180px wide, medium at most 160px tall, else large; never stored, never a setting. The List, Calendar, Neglect map and every glance widget have faces (Notes and the Eisenhower are always whole); a click on a small face (or its focus-only `Open …` button) opens the whole widget in a popover anchored to the cell (`min(720, 100vw − 16) × min(520, 100vh − 16)`; Esc, × or a press outside closes it, and so does the face growing). Stored layouts are read through the layout repair (a part this build can't use is dropped; the layout opens unsaved). A layout's optional **hue** (D19) colours its tab, its cell headers and the focus ring inside it; it is set with the name in Edit… (the layout tab's menu; the Edit layout dialog) and saved at once. Layout edits make the working copy unsaved until Save (kept in the browser across a reload, never in the database); the layouts' order and view state (pane sizes from the dividers, active tab, collapse, calendar view, row details width, the phone's column) save at once — a size among parts an unsaved edit added stays with that edit until Save. On a phone one column or band shows at a time — its rows top to bottom, each row's cells in order, a fit row two up while two fit (each ≥ 140px); no cell is headless there, and a glance cell takes a 30px header —; each layout reopens on the one it was left on (`activeColumnId`, view state).
   **Lenses** (D15) are named screen filters defined once (Settings › Tasks › Lenses, the `lenses` settings row; four presets seeded on its first open; a lens's filter edits are saved or reverted — a draft until Save, the top bar keeping the saved lens, and leaving it with a draft asks Save / Discard / Keep editing, cr25) and **picked in the top bar** — one pick for every layout, no part of any layout (`settings-store.activeLensId`, the `activeLensId` settings row: saved at once, no unsaved state, no undo step; a layout switch keeps it). The lens control sits between the layout tabs and the screen-filter tray, its own part of the bar (never folds; outside the tray, never lifted with it), and while a lens is on the whole control takes the accent as the tray takes red for a chip. Wherever the screen filter applies — lists, the Eisenhower, the glance widgets, the Neglect map, the calendar, the filtered-tasks panel and its counts — the top bar's lens composes under its chips (`stores/screen-filter`: `FilterCriteria.lens`, its own clauses, "is not" switches and expression ANDed, completion left to the chips). The chips stay ad hoc on top: Clear all clears them only; the tray turns red for chips only. **Search tokens** (D16): what is typed in the top bar's search (or the phone sheet's) — `@person`, `#tag`, `!status`, `/urgent` · `/important` · `/focus` (several of a kind OR), `overdue`, `due ⟨phrase⟩`, `followup ⟨phrase⟩`, `no due`, `done` — becomes those chips as each token completes (`services/search-tokens` over Quick Add's parser → `filter-store.applySearchTokens`); the words left are the text search; Backspace in the empty box takes the last box-made chip back. The lens control's glasses lift the lens for now (`ui-store.lensLifted`) until a second click, a pick or a reload (a layout switch keeps it); the counter `61 of 109` says what the lens and chips keep of every open task — and, while they let completed tasks through, of the completed ones they admit (Show completed: every one; a chips' Completed range: the ones in it; a lens's own Completed range: the ones the whole lens keeps), so `of N` never grows with the whole history and its tooltip's `<lens> hides N` (`total − kept`) is the lens picker's number (open tasks the lens hides). Deleting the picked lens puts the top bar on No lens (no prompt; one undo step brings back both).
5. **Navigation**: desktop is one page — the workspace under one top bar; Settings is a modal over it (gear, `G S`, the palette, the storage pill, `#/settings`), so it never changes the route. On a phone the bottom tab bar routes between `/` and `/settings`, and the workspace's `useBlocker` asks before unsaved work is left.
6. **Lists**: a list tab runs its definition through `useBuiltList` with the top-bar (screen) filter — the chips with the top bar's lens — composed in (narrowing clauses AND, Show completed ORs). A filter keys a date clause by one of six dates (schema v70, D22): Due, Next follow-up, Last follow-up, Completed, Created, Modified — the date panel's two rows of three; the panel's Show row picks how a range is entered — **Calendar** (each end a date, with Set to… presets) or **Relative** (each end a number of days ago / ahead or a rolling day, its day today under it; a new range opens here) — and, on the optional dates, **Any** / **None** (cr25 P8, D23 board B; switching converts the ends, nothing stored changes); Last follow-up is optional like the due date and the next follow-up (Any / None, "also tasks never followed up"), a range may be **is not** (schema v71: the date outside it, a task without the date kept — "Last follow-up is not 1 week ago – Today"; not on Completed), Completed is a range only, and **a Completed range among the chips or a top-level `and` term of an expression — in a list's filter, the top bar's lens or its chips — lets completed tasks through as Show completed would** (`filter-criteria.admitsCompleted`), the range then keeping only those completed in it. Lists also sort by Last followed up (oldest first) and Completed (picked newest first). A list's filter — like a lens's, a pane's and the check-in's — is **Graphical or an expression** (schema v75, `models/filter-expression`): Graphical is its chips, ANDed, one per field (Priority may repeat, below); an expression (`TodoPredicate.expression`, the chips' clauses then empty) is typed text — `@person`, `#tag`, `!status`, `/urgent` · `/important` · `/focus`, `no` / `any` person · tag · status · priority, a date word (due, followup, followed, created, modified, completed) with a day, a period, `before` / `by` / `after` / `from`, `a..b`, `within [last|next] N days`, `any` / `none`, the shortcuts `overdue`, `followup late`, `never followed`, a quoted phrase for text contains (bare words are quoted when the field settles), joined by `and` / `or` / `not` and parentheses (`utils/filter-expression`: parse, print, convert, tree). An editor shows a **Graphical / Expression** switch over the filter (`PredicateChips`; its ⓘ explains); Expression turns the chips into the text that filters the same, and Graphical over an expression turns a plain `and` of one-per-field terms back into chips — anything else is locked (Edit expression / Clear and use Graphical). The field (`ExpressionField`, `hooks/use-expression-field`) tints the tokens, autocompletes names after `@` `#` `!` `/` (`services/filter-expression-field`), writes once the text reads (after a pause, on blur or Enter) and never a text that doesn't (an error line says where, its hint in a tooltip), Esc puts the written text back, settling prints it canonically; under it **Reads as** lists what is kept and dropped as chips, and **Syntax…** opens the cheat sheet. The check-in's filter refuses people (each email is one person's). The top bar stays flat chips (an OR there goes through a lens). On a list's filter line an expression is one chip (the whole text in its tooltip) that opens Edit list. A new task's seeds, a Prompt for pick and the People / Tag group restriction read only the top-level `and` terms a chip could say (`predicate-expression.topLevelPredicate`); a list whose filter is an expression still offers Add task. Stored or groups (schema v69 – v74) are converted by v75 into the expression that filters the same — the clauses ANDed, each group an `or` of its terms. Everywhere a chip's picker opens as a popover under the row; + Filter (in an editor with a row already, **+ Another filter (AND)**) adds a chip; the editors (Edit list, Lenses, the Eisenhower panes, the check-in) stack one chip per row, in the order they were added (a new filter goes last), a chip's text wrapping to the block's width. A chip with several values reads them with `or` (`Aisha or Ben`). **Priority filters read as Status's** (schema v74): is / is not, several values OR, `No priority` (a task with no marker, effective Urgent counted) — `markers` is a list of conditions (`MarkerClause`), a chip each (`FilterChip.markerIndex`, as a date chip's `dateField`). Priority alone may repeat in Graphical: its chips AND (the default Eisenhower Do pane is Urgent and Important). The top bar holds one (AND there goes through a lens). A one-value `is` seeds and drops that flag and an `is not` clears its flags (`markerConditions`); several values or `No priority` imply nothing, as Status's. Every summary in words (a lens's row and picker line, Copy from's list hints, an Eisenhower pane's subtitle, a list's empty state) spells an expression as its text. **Grouped by People or Tag, the "is" picks narrow the groups** (`build-list.groupRestrictions`): those of the list's own filter, of the top bar's chips and of its lens — an expression's top-level terms only, never an "is not" — so `@Alice` in the top bar shows a task of Alice and Bob under Alice alone, as `People is Alice` in the list would; picks on both sides intersect (a task that has none of the people every side picks shows under each one any side picks, so no member drops), the trailing Unassigned / No tags section staying only while every pick has `0`. The filtered-tasks panel grouped so follows the same rule. Its desktop rows are quiet (D17): a set date is its text alone — in words by default (D25 D1, `utils/date.formatRowDate`: `Today`, the next six days' weekday, else `11/20` — an overdue date too, bold, and another year's, with no year (the date column is 45px a part); the phone row's due chip too; the tooltip and name keep the full date), or `MM/DD` under Settings › Appearance › Dates (`rowDates`); everything else that shows a day (the calendar, pickers, status updates, check-ins, exports) keeps `MM/DD` —, colour goes only to what needs action now (an overdue or due-soon due date, a follow-up today or late; avatars, tags and the status glyph are muted until the row is hovered), **a task's priority is drawn on its checkbox, the same at every zoom** (D25 B, `shared/PriorityRing` over `utils/markers.priorityRing`: Urgent and Important are outlines — a 2px ring in the marker's colour with a faint fill; Urgent + Important a split ring, top-right urgent, bottom-left important; urgent only by its due date finely dashed; Focus never an outline but a tight glow in the Focus colour around the box (4px blur at 18px), with a ring or around the box's own plain border; none on a completed row — on the phone row too; the priority menu opens from a slim gutter before the box, empty at rest, a flag on row hover / focus, and from the task menu), titles at 500 over 11.5px tabular meta in the muted grey, 30px rows, a flat list's hairline from the title's start, and **a priority adds what Settings › Tasks › Priority cues says beside its ring** (`utils/priority-cues`: a glow from the row's left edge, several blending along the row, and a semibold title; by default Urgent glows, Important glows and is semibold, Focus adds nothing; urgent only by its due date glows less; completed rows have none), a task untouched for Settings' `staleAfterDays` (default 30) is faded. **A list tab has a zoom** (D25 C + I1; `ListTabViewState.zoom`, view state saved at once — never an unsaved edit; no schema step): **Stacked** (the title on its own line, up to two, the details on a line under it — due · follow-up · checklist · people · tags, clipped from the right; no notes or status cell), **Rows** (the row above), **Lines** (15px: a small box where the checkbox was — its ring the priority as on a row's checkbox, Focus's glow too; its fill the date state: late, due soon, follow-up late, stale; a plain task's empty with a neutral border —, the title, and at the line's end the one date that matters (the follow-up while today or late, else the due date, else the next follow-up), coloured as the Rows date cells; a click opens the editor, the hover the row's details, a right-click the task menu (Shift+F10 on the focused line too: a line is a tab stop); a stored Strips, the level once below it, reads as Lines). Ctrl + wheel over the list, the tab menu's Zoom − / + and the palette's Zoom List In / Out step it; a tab that hasn't picked one shows Settings › Appearance › **Default list zoom** (the old row density's row: Comfortable reads as Stacked, Compact as Rows). Group headers shrink at Lines; Eisenhower, glance-widget and dialog rows stay at Rows, and the phone has one density. **A list tab shows a badge** (`hooks/use-tab-badges` over `utils/tab-badges`): one capsule with how many open tasks it shows on opening — its filter as edited, its prompt pick and the screen filter — are due (magenta) and due for a follow-up (yellow), each inside a range from Settings › Tasks (default overdue and the next 3 days; overdue and today) or the list's own from Edit list (`ListDefinition.tabBadges`: off, or its ranges); a part is solid while any of it is overdue; the tab's title gives way first and its tooltip spells it out; tabs folded into `+N` carry theirs into that menu; a list still waiting on its prompt has none. **A list can ignore the top bar's lens** (`ListDefinition.ignoreLens`, saved at once — never a draft edit): its filter line ends with the lens switch — glasses and `−N` while the lens hides tasks there, slashed while the list ignores it — then the list's count (`32 of 40`, no longer on the tab), before group · sort; the tab menu has the same switch, and a list whose filter line is hidden keeps its count on the tab with the glasses beside it. The list's chips, its tab badge and everything it shows follow the switch. The top bar's counter (and the phone's pill) carries the same badge over the tasks the screen filter shows, in the app's ranges. Group headers breathe (D25 A1: 18px of space above every group but the first on desktop, the name bold with its count and a rule to the line's end; a grouped body's rows draw no hairline) and stick to the top of the body while their group scrolls, a hairline under one only while it is stuck; a list tab's menu collapses or expands every group. Edits from a widget go to `list-draft-store` — every widget showing the list shows the draft unsaved until Save or Revert; kept across a reload. Manual order is per list and saves at once. A dragged list row is **lifted** (D25 E4, `DragOverlayTask`): on grab it scales to 1.02 with the drag shadow (no tilt); a reorder or a cancel settles it, shrinking back, onto its new spot or back where it came from, and a drop the row follows later (another group, a calendar day, an Eisenhower pane) settles and fades where it was let go — reduced motion: no scale, gone at once; where it would land is always a blank slot a row high (`DropSlot` — a reorder, another group, an Eisenhower pane; in a sorted list dashed, holding the "drop to switch to manual" hint). **Every list belongs to one layout** (`owner: { layoutId }`) and is offered only there: a layout's Save deletes its lists no saved tab shows, Save as copies the ones it shows, Delete takes them with it. The Eisenhower has its own hidden list (`owner: { eisenhower: true }`), shown by every Eisenhower tab and the Eisenhower summary widget, under the app-wide panes (Settings › Tasks › Eisenhower).
7. **People / tags**: many-to-many via `todoPeople` / `todoTags`, cached in the person / tag stores' assignment maps. Assigning or unassigning one — a row's picker, the editor, the bulk bar — is activity on the task: it stamps its `modifiedAt` in the same transaction (cr32; its undo puts the earlier stamp back); a create's people and tags are stamped once, as the create. Renaming or deleting the person or tag itself, and Find unused…'s removal, are housekeeping: they leave the tasks' `modifiedAt` alone. A person's optional email is where check-ins go. `Org: <name>` people and `Project: <name>` tags (from the old org / project migrations) are naming conventions only. Every People / Status / Tags filter has a "none" choice, id 0 (Unassigned, No status, No tags): `Tags is No tags` keeps untagged tasks (a triage list), `Tags is not No tags` reads "has a tag". Settings › People, statuses & tags › Find unused… (Unused people & tags, a dialog) lists the ones no task has (optionally ignoring completed tasks, noting the filters that name them) and removes the ticked ones with their assignments as one undo step; filters naming them keep the ids and stop matching, as after a single delete.
8. **Glance widgets** (D25 N, `components/workspace/glance/`) replace the Dashboard, which retired at schema v77: each of its pieces is a widget kind of its own, composed with the layout's rows and cells (the add-widget and Change widget menus list them in their **Numbers & charts** submenu, after the **Tasks** kinds). A **Number** (`number`, config `{ metric, breakdown? }`) is one count — Open, Focus, Urgent, Overdue, Follow-up due, Due today, Due in the next 7 days, No follow-up date, Closed this week (a new one: Overdue) —, `shown of total` under the screen filter, lit only when its count asks for action (D18, `litWhen`), a click opening its tasks in the task dialog; Open, Overdue, Due today and Closed this week add a 14-day sparkline and a change against yesterday, rebuilt from the tasks and their `todoEvents` (`services/stats/metric-history`; follow-up dates and the Focus / Urgent markers aren't logged, so the others have none). The old sections are a kind each — Needs follow-up, Next 7 days, Created vs completed, Status, People, Tags, Stale tasks, Recently completed, Eisenhower summary —, their options (look ahead, range, Unassigned / No tag shown, days) set in the tab menu as layout config. The morning brief is composed, not a widget (D25 L): **What changed** (`changes`) is template sentences from `services/stats/changes` (went late since yesterday — tasks there at yesterday's end only —, the follow-ups due and how many are late, the picked tag with the most late tasks, a status stuck 3+ weeks, due today, closed this week against the 4-week average, its weeks inside the completed-task retention), each opening its tasks; **Today** (`today`) is the open Focus tasks plus up to five suggestions (due today, then the Neglect map's Slipping corner), each with a **+** that sets Focus, and its menu's **Clear Focus…** keeps the open ones for tomorrow or clears them all — either one undo step, housekeeping that stamps no `modifiedAt` (a **+** stamps, as any priority flag) (`services/today-focus`); **Project pulse** (`pulse`) is a card per picked tag (a new one's are the `Project: …` tags): a ring for the late share, 4 weeks of added and closed, open / late / stale and a momentum line (`services/stats/pulse`). Needs follow-up, Stale tasks, Recently completed and Today show task rows, each its own selection scope and bulk bar; every glance tab's menu ends with **Copy** (its lines). Each widget has a small and a medium face (item 4): a Number's small face is its label and count, its large one adds a breakdown by person or tag; a section's small face is its title and headline number. Every statistic is a pure `services/stats/*` function over the screen-filtered tasks and over all tasks (`hooks/use-glance-data`: a hook per part over one shared base, each part a `utils/shared-memo.sharedMemo` keyed by its inputs' identity, so a dozen widgets on screen — the calendar, the Neglect map and the Eisenhower among them (`useScreenTasks`) — filter the tasks once and compute each statistic once; a write that leaves the shown tasks as they were recomputes none); the trend, a Number's history and What changed read `todoEvents` through `trend-events-store` and replay them one way (`services/stats/task-history`). Closed this week's change is against the same point of last week, the others' against yesterday. People and Tags narrow their rows by the top bar's `@` / `#` picks, as a list grouped by them does (`build-list.groupRestrictions`). A glance click's task dialog is built in `glance/glance-drills`. **v77** converted every saved Dashboard tab into these widgets: alone in its cell, the cell becomes rows — its Numbers first in fit rows of up to six, then a row of short List cells for its list tiles, then its sections packed into rows by their old spans, a span becoming the cell's width weight; sharing its cell, the cell keeps its other tabs and the new rows go just below it; in a band, every part becomes a cell of the band's row. The **Neglect map** (D25 board H, widget kind `neglect`, independent of the Eisenhower) plots every open task the screen filter keeps by days untouched (`modifiedAt`, capped at 60) against days until due (14 late … 30 ahead), the pure placement in `utils/neglect-map`: due soon (Settings' due-soon range) or late and untouched for the tab's threshold (default 14 days) is **Slipping** — the shaded corner, listed beside the plot — the other corners In hand / Planned / Drifting, and a strip under it holds the tasks without a due date (**Forgotten** once untouched). Its config (layout config, no schema step: Colour by the picked tags — a new map's are the `Project: …` tags — / People / None, and the threshold) is set in the tab menu; a dot opens the editor, a drag on empty plot lassoes dots into the widget selection the bulk bar acts on.
9. **Email check-ins** (no mail API): `services/checkin-email` builds each person's email from their open tasks under the saved check-in filter (a `Ref` per task; each task's box: Completed, Status — its newest status update, `(MM/DD) text` — and Notes), hands it to the mail app (clipboard + `mailto:`, or an `.eml` draft) and marks the tasks followed up as one undo entry. A person's envelope (a People group header, the person task dialog) offers the choice: Send check-in, or Paste reply. A reply comes back by paste (the import dialog, which reads the person from the reply): `checkin-reply` parses it, diffs it against the tasks, and applies the ticked changes as one undo group (a changed Status — read without its `(MM/DD)` — adds a status update dated today; a reply never removes one).
10. **Status updates** (cr27, schema v72): a task's dated lines of text — what happened, as of a day — in their own table (`statusUpdates`, `status-update-repository` → `status-update-store`; not on the task row, but each write — add, edit, remove — stamps the task's `modifiedAt` in the same transaction, so updates keep a task from going stale, and its undo / redo puts the earlier / its own stamp back), newest first by day, then by when written. They replaced the one-line Progress field (the v72 upgrade made each task's Progress its first entry, dated its `modifiedAt`); the Status picker (`statusId`) is a separate field. Added / edited / removed in the editor's Status updates section (each its own undo step), added from the notes popover's Status line (today) and from the follow-up popover's optional **Status update** line — with text, Mark followed up adds the entry dated today (`followedUp`) in the same undo step (`services/mark-followed-up`; from the bulk bar, to every selected task). **Entering one on an open task counts as following up on its day** (`addStatusUpdate`): a day after the task's last follow-up is Mark followed up for that day — the last follow-up moves to it, the next follow-up by the rule counted from it, entry `followedUp`, one undo step with the snackbar; an older or same day only adds the entry, and so does any entry on a **completed** task (nothing is chased on it any more: its follow-up dates stay, the entry isn't `followedUp`); a new task's entries set its Last follow-up to the newest's day (a new task is always created open). The follow-up popover's Mark followed up (and the bulk bar's, and a check-in reply's Record a follow-up) is the user's explicit choice and records the follow-up on a completed task too. Editing an entry's day doesn't, nor does a check-in reply without Record a follow-up. The newest shows on the row's notes tooltip and the phone row's chip (`MM/DD text`); the text search reads every entry. A task delete takes its entries, and its undo brings them back; Duplicate copies them. They travel with exports, backups, the sync file, task archives and the append import; the audit deletes orphans
11. **Subtasks** (cr28, schema v73): a task's checklist — each line a title and whether it is done, nothing else, one level — in its own table (`subtasks`, `subtask-repository` → `subtask-store`, ordered by `sortOrder`). A subtask is never a list row, never counted, filtered, grouped or sorted, and never a search result of its own; **the text search finds the task by its subtasks' words** (a Subtasks group in the top bar, the line as the snippet; the screen filter, lists, lenses, panes and counts keep the task likewise). Every task row shows a `2/5` count after its title — a 12px pie before it filling by the share done, the accent once all are (D25 D2) — that opens the checklist as a popover (check, rename, add, ⋯: Rename · Make a task · Move to another task… · Delete); the phone's chip opens it as a bottom sheet; the editor has a Subtasks section (drag to reorder) — in create mode too, written with the task. The task menu offers **Add subtask…** and **Make subtask of…** (a task picker; the task keeps only its title and done state — a prompt lists what goes unless it holds only its title — its own subtasks move to the parent; one undo step brings it back whole; `services/subtask-convert`); **Make a task** gives a subtask the parent's people, tags, status, due date, next follow-up and markers (not its notes, status updates or repeat). Every subtask write stamps the task's `modifiedAt` as status updates do (`stores/task-hooks`); checking the last open one offers **Complete task** in the undo snackbar (never automatic); completing a task with open subtasks asks nothing; a recurring completion unchecks the checklist in the same undo step; a delete takes the checklist and its undo brings it back; Duplicate copies it unchecked; purge removes it. Notes → tasks (the toolbar's Convert, Alt+T, or the convert icon in the editor's left margin beside the line under the pointer; one line opens Quick Add on its text, Details handing off to the editor; two or more open a preview that shows drafts on task rows edited in place, nothing stored until it is confirmed; a draft checked off makes no task and its line goes on confirm, in the one note edit that a Ctrl+Z undoes; Settings › Task defaults' Remove note lines after converting (off by default) makes every converted line go that way too, asking nothing, instead of `✓ <title>`; × leaves the line) makes the indented list lines under a bullet its task's subtasks (plain titles), and Tab / ⇧Tab — or the toolbar's Indent / Outdent — indent list lines in every notes editor. **A task's own notes** (the editor's, the notes popover's) convert to that task's subtasks instead, the same three ways and with no dialog (`services/note-subtasks`): each line a plain title, the lines under it beside it (one level), a done box done; the lines turn `✓` or go as above, all one undo step with the snackbar; in create mode they join the pending subtasks. Check-in emails list a task's open subtasks under it for context (never read back); the Markdown export and Copy write indented `- [ ]` / `- [x]` lines under the task. It travels with exports, backups, the sync file, task archives and the append import; the audit deletes orphans
12. **Ambience** (desktop only; Settings › Appearance › Ambience — on by default): quiet signs of the time of day and the season in the chrome, never over a task's text and never in a colour that means something. `hooks/use-ambience` computes the `utils/sky` scene once a minute from the clock and the place (a typed latitude / longitude, else the time zone's main city — `utils/sun`; no location prompt, no network, so the offline file stays clean). `components/ambience` draws it: in the top bar, the sky over the glass at the share the glass lets through, the sun and moon as soft discs, stars, cumulus, the winter aurora, morning mist, the season's weather (snow, leaves, petals, seeds, fireflies — CSS-animated) and the sun's point on the hairline; in the workspace, the sunbeam and weather behind the cells and lamplight over them; a task completed on screen sends a ripple along the hairline and a burst from its box. Sky strength scales the sky, clouds, aurora, mist and sunbeam; Header motion everything that moves in the bar; Seasons the weather, the burst and the aurora. Reduced motion keeps a still sky. Its colours are `--ambience-*` tokens in `tokens.css` (each theme's own there), which the scene mixes by the time of day with `color-mix()` — no ambience file writes a colour or picks one by theme. One JSON settings row (`ambience`), no schema step

## Dismissing a popover

A change a popover shows either sticks or the user is warned. Esc or a click off saves what was typed (`FollowupPopover`, `SubtaskChecklist` in every host, the Add update popover, `TaskNotePopover`): each writes it in an unmount cleanup, so every way of closing is covered, and only a Cancel button drops it. Esc inside an inline edit — a subtask rename, a status entry — cancels that edit and leaves the popover or editor open. Text that can't be stored holds the close once, saying so; closing again drops it (a filter expression that doesn't read too: the first press outside its field, `ExpressionField`). Nothing exists yet behind Quick Add, the new-task editor and the convert preview's edited drafts, so they ask instead (Create task / Discard / Keep editing, or Discard / Keep editing with no title), and only when the form differs from how it opened; the editor's Cancel button discards without asking. Filter and picker popovers write on every change; a date panel's pending Is not, which no clause can hold yet, is kept per filter (`filters/date-pending-not`).

## Testing

Two layers, picked by what's being verified (setup, fixtures and helpers: [architecture/testing.md](architecture/testing.md)):

- **vitest (`npm test`)** — unit + JSDOM under `src/test/**`: pure logic, models, repositories, stores, services, utilities, and rendering / event dispatch that doesn't depend on real layout, focus or async DOM timing. Two projects (`isolated` for files that mock modules, `shared` for the rest); every store and every registered module state is reset before each test.
- **Playwright (`npm run test:e2e`)** — Chromium-only real-browser flows under `e2e/**`, on its own dev server (port 5173, or `PW_PORT`). Specs wait on app state, never on timers. CI (the deploy workflow) runs only vitest.

**JSDOM is not authoritative** for focus handoffs, `ResizeObserver`-driven layout, drag-and-drop hit-testing, popover placement and viewport flips, and async-store-driven re-render timing — those need a Playwright spec.

**Diagnosis vs. regression.** The Chrome DevTools MCP server (`mcp__chrome-devtools__*`) is a *spike* tool — drive an interaction live in real Chromium, then codify the regression in Playwright. See CLAUDE.md "Tools — Chrome DevTools MCP".

**Manual-testing seed.** `npm run seed:dev` writes a realistic export in the current schema to `dev-data/seed-v77.json` (gitignored) for Settings → Import / Export → Import JSON.
