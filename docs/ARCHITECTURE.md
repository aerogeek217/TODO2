# Architecture Overview

This file is the always-loaded orientation. For per-abstraction detail, load the relevant reference file under [Detail References](#detail-references).

## Tech Stack
- **Frontend**: React 19 + TypeScript, built with Vite
- **State**: Zustand stores
- **Database**: Dexie.js over IndexedDB (local-first)
- **Drag-and-Drop**: dnd-kit
- **Routing**: React Router v7 data router (`createHashRouter` + `RouterProvider`; one splat route renders the shell's `<Routes>`, so `useBlocker` is available)
- **Builds + CSP** (a `<meta>` in `index.html`, `base-uri 'none'; form-action 'none'` everywhere): the online build (`vite.config.ts`; `dist/index.html`) loads scripts from `./assets` only, so its `cdnFonts` plugin drops `script-src 'unsafe-inline'` (and adds Google Fonts) and `noInlineScripts` fails the build on any inline script; the offline single file (`vite.config.offline.ts`; `dist/todo2.html`) keeps `'unsafe-inline'` for its one inline script and allows its embedded `data:` fonts (`offlineCsp`). Dev keeps `'unsafe-inline'` for the React refresh preamble

## Data Flow

1. **Startup**: Dexie opens IndexedDB → settings load (theme + `data-theme` on `<html>`; user color overrides applied as inline styles) → `fileStorageService.initialize()` reconnects the file handle and runs the load decision — nothing on either side changes until the user resolves any disagreement (conflict / older file / unreadable file → `SyncConflictDialog` / `FileUpgradeDialog` / paused warning strip; state in `services/file-sync-state.ts`; sides that match once an older file is upgraded are not a conflict — e.g. a browser DB upgraded at open, with no sync record, and its in-sync older file → `FileUpgradeDialog`) → people / statuses / tags load. If `completedRetentionDays` is set, completed tasks past it (keyed on `TodoItem.completedAt`, `utils/completed-at.ts`) are **never purged silently**: `App.tsx` records their uids after the sync-file load and `StartupPurgePrompt` → `PurgeCompletedDialog` asks (Export & delete → task archive via `services/purge-completed` + `services/task-archive`; Delete; Not now = this launch only). `backupScheduler.start()` takes an automatic backup when the last one is a day old (or there is none), then checks hourly; each backup kind (auto / pre-op / manual / sync file) keeps its own newest few.
2. **Normal use**: UI → Zustand stores → repository methods → Dexie. If file storage is syncing, Dexie hooks debounce-save to the JSON file; while paused or awaiting permission the same hooks only mark the browser dirty (`dirtySince`), which forces a conflict prompt on the next load. Cross-cutting capture rides `QuickAddBar` (`Ctrl+Space` / the top bar's New task / mobile FAB / `command-registry.openQuickAdd`); the `TaskEditPopup` create modal is reachable via QuickAdd's Details handoff.
3. **Workspace**: `WorkspacePage` opens the active layout (`useWorkspaceStore.init()`; a fresh database gets an empty "Default" layout). Layout edits (add / move / close / split / resize widgets, layout config) make the working copy unsaved until Save; view state (active tab, collapse, calendar view / offset) is written straight away. On a phone the same layout shows one column at a time.
4. **Navigation**: desktop has one page — the workspace — under one top bar; the layout picker is the "you are here" mark. Settings is a modal over it (gear, `G S`, palette "Open Settings", the storage pill, or the `#/settings` deep link), so it never changes the route and never prompts about unsaved layouts. On mobile the BottomTabBar routes between `/` and `/settings` (the workspace's `useBlocker` prompts when leaving with unsaved work). The old page routes (`/workspace`, `/list`, `/calendar`, `/dashboard`) redirect to `/`.
5. **People / tags**: many-to-many via `todoPeople` / `todoTags` joins; `usePersonStore.assignedPeopleMap` / `useTagStore.assignedTagsMap` cache them. A person's optional `color` fills their avatar / chip / group swatch (`NEUTRAL_PERSON_COLOR` when unset). An optional `email` (Settings → People; people created on the fly have none) is what email check-ins send to. `Org: <name>` people and `Project: <name>` tags (from the org / project migrations) are naming conventions only — no special handling.
6. **List widgets**: a list tab runs its definition through `useBuiltList` with the top-bar (screen) filter composed in — narrowing clauses AND (strict, even on the same field), `showCompleted` ORs (`utils/filter-criteria.composeScreenFilter`). Edits to the definition from a widget (filter chips, List options, switch to manual) go to `list-draft-store`: every widget showing the list renders the draft and shows it unsaved until the header's save button writes it; `UnsavedPrompt` asks before a layout switch, leaving the workspace or closing the list's last widget would drop it. Prompt picks live in `list-widget-store` and are never saved. Manual order is per list (`listOrders`) and saves at once.
7. **Dashboard**: a dashboard tab computes every number with the pure `services/stats/*` functions over the tasks passing the screen filter (completed included, for the trend; `statsFilter`) and over all tasks, so counts read `shown of total`; list tiles run each list's predicate AND the screen filter (unsaved list drafts included). The trend reads `todoEvents` once per (range, day) through `trend-events-store`. What shows (tiles, list tiles, sections, their order and options) is the tab's `config`, saved with the layout.
8. **Email check-ins** (offline, no mail API): `CheckinDialog` picks people and a task scope (`utils/checkin-settings`, remembered) → `services/checkin-email` selects each person's open tasks and builds the email (HTML + plain text, a `Ref <token>` per task from its uid, a `Your update` box per task, the footer `Check-in for <name> · sent <date>`) → per person either the rich clipboard + a `mailto:` link (To + Subject; the user pastes the body) or a downloaded `.eml` draft, then `markFollowedUp` on the emailed tasks. Nothing about the send is stored. The reply comes back by paste: `CheckinImportDialog` → `checkin-reply/parse` (HTML in an inert document, else plain text; tasks found by Ref, the newest email in a thread only) → `diff` against current values (a task modified on a later day than the footer's send date is flagged and unticked) → `apply` writes the ticked changes through the todo store as one undo group.

## Testing

Two layers, picked by what's being verified:

- **vitest (`npm test`)** — unit + JSDOM under `src/test/**`. Authoritative for pure logic, models, repositories, store reducers, services, utilities, and rendering / event-handler dispatch that doesn't depend on real layout, focus, or async DOM timing. `e2e/**` is excluded from the vitest sweep. `vitest.config.ts` splits two projects: `isolated` — any test file calling `vi.mock` / `vi.doMock` (detected at config load), one fresh worker per file so module fakes can't leak; `shared` — every other file, `isolate: false` (one jsdom + module cache per worker, the bulk of the speed-up), with `src/test/setup-shared.ts` restoring at each file boundary what a fresh worker would give: every zustand store back to `getInitialState()` (a `vi.mock('zustand')` wrapper registers each store as it is created), the Dexie db deleted, Testing Library `cleanup()`, `<body>` / `<html>` attributes / storage / URL cleared, real timers, global + env stubs undone, `vi.spyOn` spies restored, and module state outside the stores put back through each module's reset (`fileStorageService.reset`, `backupScheduler.reset`, `resetFileHandleCache`, `resetFileStoragePrompts`, `resetNoteSaves`, `resetSettingsModuleState`, `resetListOrderLoad`).
- **Playwright (`npm run test:e2e`)** — Chromium-only real-browser flows under `e2e/**`. Starts its own `npm run dev` on fixed port 5173 (the everyday dev server is 5180), `reuseExistingServer`, `trace: 'retain-on-failure'`, `fullyParallel` (each test has its own browser context, so tests within one spec spread across workers). Fixtures live in `e2e/fixtures/` (`workspace.ts` seeds layouts / lists / tasks straight into IndexedDB — `seedWorkspace`, `seedTaskList` — and drives trusted-mouse tab / row drags, each ending in `releaseDrag`, which waits out dnd-kit's 50 ms post-drag click block so the next click isn't swallowed; `gotoSettingsDeepLink` / `openSettings` open the Settings modal without racing the `#/settings` deep link's effect; `seed.ts` holds the task-row locators; `sync-file.ts`'s `readSyncFile` reads an OPFS sync file only once `fileStorageService.whenIdle()` resolves — a `File` read while a save swaps the file in throws `NotFoundError`). `built-csp.spec.ts` builds both targets into a temp folder and runs them (online served over http, offline from `file://`) with no CSP violations. The app is hash-routed (`/#/`, `/#/settings`). CI is out of scope.

**Folder cycles.** `src/test/architecture/folder-cycles.test.ts` scans every relative import in `src/` (static, dynamic, CSS, `composes … from`) into a graph of folders (`components/<area>`, the other top-level folders, each top-level file) and fails on any cycle. Its allow-list of edges is empty; an entry would fail once its edge is gone.

**JSDOM is not authoritative** for: focus handoffs, `ResizeObserver`-driven layout, drag-and-drop hit-testing (workspace tab drags, list row drags, calendar day drops), popover anchor placement and viewport flips, and async-store-driven re-render timing. Those categories require a Playwright spec — JSDOM passing is not enough signal.

**Diagnosis vs. regression.** The Chrome DevTools MCP server (`mcp__chrome-devtools__*`) is a *spike* tool — drive an interaction live in real Chromium, capture state, then codify the regression in Playwright. See CLAUDE.md "Tools — Chrome DevTools MCP".

**Manual-testing seed.** `npm run seed:dev` (`scripts/dev-seed.ts`) writes a realistic v49 export (with orgs, projects, a taskboard and a canvas, so the whole upgrade path runs) with dates relative to the run day to `dev-data/seed-v49.json` (gitignored); Settings → Import / Export → Import JSON in the dev server then runs the full v49 → current upgrade. `src/test/data/dev-seed.test.ts` keeps it importable.
